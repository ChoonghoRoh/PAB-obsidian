신규 설치 5단계

1설치 스크립트 실행 — bash <번들경로>/install.sh <대상경로> 형태다. 딱 두 가지만 지키면 된다: ① 번들경로는 zip을 실제로 푼 위치, ② 대상경로는 번들과 다른 폴더(대상 ≠ 번들). 번들을 어디에 두느냐에 따라 두 방식이 있다:

방식 A — 번들을 대상 바깥 고정 위치에 두기 (권장, 재사용·upgrade 용이)

unzip pab-ssot-bundle-*.zip -d ~/        # → ~/pab-ssot-bundle/ 에 풀림
bash ~/pab-ssot-bundle/install.sh /path/to/your-project
# 기존 파일과 충돌하면 *.pab-new 로 저장됨 (수동 병합)

방식 B — 대상 폴더 안에 번들을 풀고 그 폴더에 설치 (예: work/test/에 풀고 work/test/에 설치)

cd /mnt/c/Users/chroh/work/test          # 대상 폴더로 이동
# 여기에 번들이 ./pab-ssot-bundle/ 로 풀려 있음
bash pab-ssot-bundle/install.sh .        # 번들=./pab-ssot-bundle, 대상=.(=work/test) → 서로 달라 OK
# 설치 후 번들 하위폴더 정리: rm -rf pab-ssot-bundle  (upgrade 재사용하려면 남겨둬도 됨)
⚠ ~/pab-ssot-bundle/는 예시 — 실제 푼 위치로 바꿔라
~/는 리눅스 홈(/home/<계정>/)이다. 번들을 홈에 풀지 않았는데 ~/pab-ssot-bundle/…로 넘겨짚으면 No such file or directory가 난다. 방식 B처럼 번들이 현재 폴더 하위에 있으면 상대경로 pab-ssot-bundle/install.sh로 부른다. 헷갈리면 번들 폴더에서 pwd로 절대경로를 확인해 그대로 쓴다.
⚠ 유일한 실패 조건: 대상 = 번들
. 사용 자체는 문제없다 — 현재 폴더가 번들 폴더 자신일 때만 소스=대상으로 막힌다. 즉 cd pab-ssot-bundle 후 install.sh .은 에러. 방식 B처럼 번들의 상위 폴더에서 install.sh .은 정상(대상=상위 ≠ 번들).
💡 방식 A를 권장하는 이유
번들을 대상 바깥에 두면 여러 프로젝트 설치·추후 --upgrade 재배포를 같은 명령으로 반복할 수 있다. 방식 B는 번들이 대상 안에 남아(설치 후 정리 대상) 매 upgrade마다 다시 풀어야 하므로 일회성 설치·테스트에 적합하다.
🧹 설치 후 정리 — 무엇을 지우고 무엇을 남기나
install.sh는 소스(번들)를 자동 삭제하지 않는다 — 재사용을 전제로 한 설계다. 대상별로:
  • 배포 zip(pab-ssot-bundle-*.zip) — 압축 해제 후엔 삭제해도 됨(다시 받으면 됨). rm pab-ssot-bundle-*.zip
  • 해제된 번들 폴더(~/pab-ssot-bundle/) — 남겨 둔다. 추후 --upgrade 재배포·다른 프로젝트 설치의 소스로 계속 쓰인다. 지우면 업그레이드 때 다시 받아야 한다.
  • 프로젝트 폴더 안에 잘못 푼 번들 — 설치가 끝났으면 그 하위 번들 폴더는 지운다(위 「번들 위치는 고정」 참고).

등급의미위반 시

HIGH강한 권고 — 위반 시 품질 리스크경고 + 시정 요구 (예: LOCK-5 이력 기록)
MEDIUM권장 사항참고 수준 (예: FRESH-4 리로드 시각 기록)
LOW선택적—

① Telegram 세팅 (NOTIFY-1, 구 HR-8)

알림을 받으려면 봇 토큰(API key)과 Chat ID(수신처 번호) 두 값이 필요하다. 두 값 모두 개인별 설정이다 — 저장소에는 어떤 형태로도 커밋하지 않고, 팀원 각자 자신의 셸 환경(또는 로컬 .env)에 등록한다. 아래 1)~2)는 Telegram 쪽 발급 절차, 3)~5)는 PAB 번들 쪽 등록·확인 절차다.

1) 봇 생성 — API key(봇 토큰) 발급

1Telegram 앱(모바일·데스크톱 무관)에서 @BotFather를 검색해 대화를 연다. 파란 인증 체크가 붙은 공식 계정인지 확인한다 (사칭 봇에 토큰을 입력하지 말 것).

2/newbot 입력 → 봇 표시 이름 입력 → 봇 username 입력. username은 Telegram 전체에서 유일해야 하고 반드시 bot으로 끝나야 한다:

# BotFather 대화 흐름
/newbot
→ Alright, a new bot. How are we going to call it?
PAB 알림                              # ① 표시 이름 (자유)
→ Good. Now let's choose a username for your bot.
pab_notify_bot                        # ② username (유일 + bot으로 끝남)
→ Done! ... Use this token to access the HTTP API:
123456789:AAH9xQ...j2k               # ③ 이것이 봇 토큰(API key)

3발급된 토큰(숫자:영숫자 형태)을 복사한다. 나중에 다시 보려면 BotFather에서 /mybots → 봇 선택 → API Token. 유출됐다면 같은 메뉴의 Revoke current token(/revoke)으로 즉시 재발급한다 (기존 토큰은 무효화됨).

2) Chat ID 확인

Chat ID는 봇이 어디로 보낼지를 지정하는 번호다. 개인 수신(팀원 각자 자기 개인 채팅)과 그룹 수신(팀 공용 방) 두 방식이 있다.

1개인 수신: Telegram에서 방금 만든 봇(예: @pab_notify_bot)을 검색 → 시작(Start)을 누르고 아무 메시지나 1건 보낸다. 봇은 먼저 말을 걸 수 없으므로 이 단계가 필수다.

2터미널에서 getUpdates API를 호출해 ID를 읽는다:

curl -s "https://api.telegram.org/bot{봇토큰}/getUpdates" | grep -o '"chat":{"id":[0-9-]*'
# → "chat":{"id":1234567890   ← 이 숫자가 내 Chat ID

# jq가 설치돼 있으면 더 깔끔하게:
curl -s "https://api.telegram.org/bot{봇토큰}/getUpdates" | jq '.result[].message.chat.id'

3그룹 수신(팀 공용 방으로 받을 때): 봇을 그룹에 초대 → 그룹에서 아무 메시지 1건 발송 → 위와 같은 getUpdates 호출. 그룹 Chat ID는 음수(-100...)로 나온다.

💡 결과가 빈 배열({"ok":true,"result":[]})로 나오면
① 봇에게 메시지를 아직 보내지 않았거나 ② 보낸 지 24시간이 지나 업데이트가 만료된 것 — 메시지를 다시 1건 보내고 재호출한다. 개인 Chat ID는 @userinfobot에게 아무 메시지를 보내 확인할 수도 있다 (개인 Chat ID = 본인 user ID와 동일).

3) 개인별 토큰 등록

발급받은 두 값을 팀원 각자 자신의 환경에 등록한다 — 두 방법 중 하나 (스크립트·문서에 직접 기입 금지):

# 방법 A: 환경변수 (셸 프로필에 영구 등록 — ~/.bashrc 또는 ~/.zshrc)
export PAB_TELEGRAM_BOT_TOKEN="123456789:AA..."
export PAB_TELEGRAM_CHAT_ID="1234567890"

# 방법 B: 프로젝트 루트 .env 파일 (git 커밋 금지 — .gitignore에 추가)
echo 'PAB_TELEGRAM_BOT_TOKEN="123456789:AA..."' >> .env
echo 'PAB_TELEGRAM_CHAT_ID="1234567890"'        >> .env

팀 운용 방식은 두 가지 중 선택한다 — 어느 쪽이든 등록 값은 개인 환경에만 둔다:

운용 방식봇 토큰Chat ID특징
공용 봇 + 개인 수신팀 공용 봇 1개 공유각자 자기 개인 Chat ID봇 관리 일원화, 알림은 각자 개인 채팅으로
공용 봇 + 그룹 수신팀 공용 봇 1개 공유그룹 Chat ID(음수) 공통팀 전체가 한 방에서 알림 공유

4) PROJECT.md 설정 확인

frontmatter notify_channel: "telegram" · notify_project_label: "프로젝트명" 확인 → /project-config sync. (notify_channel: none이면 발송 자체를 건너뛴다.)

5) 발송 테스트

압축(PostCompact)은 자동 발생하며 post-compact 훅이 핵심 규칙만 재주입한다. 계획적으로 세션을 넘길 때는 prepare/resume이 확실 — 압축 요약보다 손실이 적다.

/wiki "000에 대해 조사하고 정리해서 저장해줘"라고 명령하면 조사 결과가 개인 Obsidian vault에 문서규격(frontmatter 11필드 · Karpathy 3계층: 원본 SOURCE + 요약본)대로 저장된다. vault 연결 지점은 사용자마다 다르므로 아래 개인별 설정 1가지만 해두면 된다 — 나머지 규격 세팅은 전부 자동이다.

1vault 경로 지정 — WIKI_VAULT_ROOT 환경변수를 셸 프로필에 영구 등록 (사용자마다 경로가 다른 유일한 지점):

# ~/.bashrc 또는 ~/.zshrc
export WIKI_VAULT_ROOT="$HOME/Obsidian/MyVault"
# Windows(WSL) 예: export WIKI_VAULT_ROOT="/mnt/c/Users/<계정>/work/PAB-Obsidian/PAB-LLMDATA"

미설정이어도 동작은 한다 — 형제 경로에서 정본 vault를 자동 탐지(경고 후 사용)하고, 그마저 없으면 사용자 확인 후에만 프로젝트 로컬 ./wiki/를 만든다 (무단 생성 금지 — 노트 분산 방지).

2초기 규격 세팅은 자동 (부트스트랩) — vault가 백지 상태라도 첫 /wiki 호출 때 스킬 동봉 시드(.claude/skills/wiki/vault-seed/)가 폴더 구조와 문서규격을 자동 생성한다. 기존 파일은 절대 덮어쓰지 않는다 (누락분만 채움):

자동 생성 항목내용
폴더 9종00_MOC/{TYPES,DOMAINS,TOPICS} · 10_Notes · 15_Sources · 20_Lessons · 30_Constraints · 40_Templates · 99_Inbox
규격 문서 4종30_Constraints/ frontmatter-spec · naming-convention · linking-policy · toc-recommendation — keywords·topics·index·tags 규칙 정의
템플릿 8종40_Templates/ 7 TYPE 템플릿 + _schema.json
MOC 골격TYPES 7종 · DOMAINS 6종 · TOPICS/_README.md · 루트 _INDEX.md (3중 인덱스 진입점)

3사용 — 저장 시 frontmatter 11필드(keywords·topics·index(DOMAIN)·tags 등)는 스킬이 자동 결정한다:

/wiki https://example.com/article 조사하고 정리해서 저장해줘
# → 원본: ${WIKI_VAULT_ROOT}/15_Sources/YYYY-MM-DD_<slug>_source.md (immutable)
# → 요약: ${WIKI_VAULT_ROOT}/10_Notes/YYYY-MM-DD_<slug>.md (TOC 링크 + wikilink 자동)
# → 동일 TOPIC 노트 3건 누적 시 00_MOC/TOPICS/<TOPIC>.md 자동 승격
💡 Obsidian 앱에서 열기
Obsidian에서 "Open folder as vault"로 $WIKI_VAULT_ROOT 경로를 지정하면 바로 사용 가능. dataview 커뮤니티 플러그인을 설치하면 MOC 자동 수집이 활성화된다 (미설치여도 폴백 정적 링크로 동작). 공통 vault 모드(권장)에서는 여러 프로젝트의 /wiki 결과가 한 vault에 누적된다.

세팅 방법 ① — ccstatusline (서드파티 위젯 인포창)

ccstatusline은 Claude Code 전용 오픈소스 인포창 도구다. 인터랙티브 TUI 설정 화면에서 위젯(모델·컨텍스트 사용량 Ctx·메모리 Mem·컨텍스트 바·세션 %·누적 비용 Total $·Skill·Git 등)을 실시간 미리보기로 확인하며 추가/제거/재배치할 수 있다. 스크립트를 직접 짤 필요가 없어 가장 쉽다.

1설치 없이 바로 실행 (Node.js 필요):

npx -y ccstatusline@latest
# Bun 사용 시: bunx -y ccstatusline@latest

2열리는 TUI 화면에서 조정한다:

메뉴할 수 있는 것
위젯 편집여러 개의 상태 라인 구성, 위젯 추가/삭제/순서 변경
색상·테마위젯별 색상 커스터마이징, powerline 구분선·테마 설정
Install/UninstallClaude Code settings.json의 statusLine 항목에 자동 기록/제거

3TUI에서 Install을 선택하면 아래 설정이 자동 기록된다 (수동 편집 불필요):

{
  "statusLine": {
    "type": "command",
    "command": "npx -y ccstatusline@latest",
    "padding": 0
  }
}

4새 claude 세션을 열어 확인. 위젯 구성을 다시 바꾸려면 언제든 npx -y ccstatusline@latest를 재실행하면 된다. 위젯 설정 저장 위치: ~/.config/ccstatusline/settings.json

⚠ PAB 인포창과의 관계
statusLine은 하나의 command만 적용되며 우선순위는 settings.local.json > 프로젝트 settings.json > 개인 전역 ~/.claude/settings.json. ccstatusline을 개인 전역에 Install해도 프로젝트에 방법 ② 블록이 배선돼 있으면 그쪽이 우선한다 — ccstatusline을 쓰려면 프로젝트 .claude/settings.json의 statusLine 블록을 제거한다. 반대로 PAB 정보로 되돌리려면 방법 ② 블록을 다시 추가하면 된다.
💡 병행 팁 — ccstatusline 위젯 + PAB Phase 정보 함께 쓰기

ccstatusline의 Custom Command 위젯에 본 번들 스크립트를 연결하면 두 가지를 한 인포창에서 쓸 수 있다:

# TUI → 위젯 추가 → Custom Command → 명령에 입력:
bash "$CLAUDE_PROJECT_DIR/scripts/statusline.sh"

이러면 Ctx/비용 위젯 옆에 📌 프로젝트 | SSOT 버전 | ⚙ Phase 상태가 함께 표시된다. 또는 ccstatusline의 여러 줄 구성으로 1행은 위젯, 2행은 PAB 라인으로 분리해도 된다.

ccstatusline 제거 (원복)

npx -y ccstatusline@latest 재실행 → Uninstall 선택. 또는 ~/.claude/settings.json에서 statusLine 블록을 직접 삭제한다. 프로젝트의 방법 ② 설정이 남아 있으면 자동으로 PAB 인포창으로 돌아온다.

세팅 방법 ② — 번들 스크립트 배선 (PAB 정보 표시)

번들에 scripts/statusline.sh가 포함되어 있다. 기본은 미배선(개인 전역 인포창 설정을 존중) — PAB 인포창을 쓰려면 프로젝트 .claude/settings.json에 아래 블록을 추가한다:

// .claude/settings.json (프로젝트 설정 — 팀 공유)
{
  "statusLine": {
    "type": "command",
    "command": "\"$CLAUDE_PROJECT_DIR/scripts/statusline.sh\"",
    "padding": 0
  }
}

확인: 새 claude 세션을 열고 아무 대화나 한 턴 진행하면 하단에 표시된다.

세팅 방법 ③ — /statusline 명령으로 Claude에게 맡기기

Claude Code 내장 명령으로, 원하는 모양을 말로 설명하면 Claude가 스크립트를 만들어 설정까지 해준다:

/statusline 모델명과 현재 폴더, git 브랜치를 보여줘
/statusline 지금 셸 PS1 프롬프트를 그대로 재현해줘
⚠ 주의
/statusline은 보통 개인 설정(~/.claude/settings.json)에 기록한다. 우선순위는 프로젝트 설정이 개인 전역보다 높으므로, 프로젝트에 방법 ② 블록이 배선돼 있으면 /statusline으로 만든 개인 설정은 해당 프로젝트에서 보이지 않는다 — 팀 공통 인포창은 방법 ②(프로젝트 settings.json)로, 개인 취향 인포창은 프로젝트 블록 제거 후 개인 설정으로 운용한다.

세팅 방법 ④ — 수동 (다른 프로젝트·개인 전역)

1스크립트 준비 — 본 번들 것을 복사하거나 직접 작성:

cp scripts/statusline.sh ~/.claude/statusline.sh

    "command": "~/.claude/statusline.sh"

}

스크립트가 받는 입력 (stdin JSON)

❓ FAQ · 트러블슈팅

자주 겪는 문제와 해법.

스킬(/plan 등)이 인식되지 않는다

.claude/skills/{이름}/SKILL.md 경로 확인. 스킬은 새 세션 시작 시 로드되므로 설치 직후라면 세션을 재시작한다. /menu로 인식 목록 확인.

hooks.env를 수정했는데 자꾸 되돌아간다

정상이다 — hooks.env는 PROJECT.md에서 자동 생성되는 파생물. PROJECT.md frontmatter를 수정하고 /project-config sync 하라.

Team Lead가 코드 수정을 거부한다 (HR-1 차단)

팀 운영 중엔 의도된 동작. backend-dev/frontend-dev에게 위임하는 게 정석. 팀이 없는데도 차단되면 센티넬 잔재 확인: rm /tmp/agent-teams-active. 애초에 가드 범위가 잘못됐다면 PROJECT.md code_dirs 조정.

SSOT 문서를 수정하려는데 LOCK-1에 걸린다

활성 Phase의 current_state가 IDLE/DONE이 아니면 SSOT 수정이 차단된다. Phase를 완료(DONE)하거나 status.md를 BLOCKED로 전이(LOCK-2)한 뒤 수정하고, 수정 후 VERSION.md 기록(LOCK-5) + 팀원 리로드(LOCK-3).

Telegram 알림이 실패한다

① PAB_TELEGRAM_BOT_TOKEN/PAB_TELEGRAM_CHAT_ID 환경변수 확인 ② PROJECT.md notify_channel이 none이면 발송 자체를 건너뜀 ③ bash scripts/pmAuto/report_to_telegram.sh "test" "hello"로 단독 테스트. 봇 생성부터의 세팅 절차: 🗂 기록·알림 위치 §①

컨텍스트 압축 후 이상하게 동작한다

FRESH-7 절차: /ssot-reload → 활성 Phase status.md 확인 → 팀 재구성. post-compact 훅이 핵심 규칙을 자동 재주입하지만, 작업 재개 전 리로드는 수동으로 해야 한다. 긴 작업 전엔 /context-handoff prepare로 인계 문서를 미리 만들어두면 안전.

업그레이드 후 *.pab-new 파일이 생겼다

대상 프로젝트가 커스터마이징한 파일의 새 프레임워크 버전이다. diff 원본 원본.pab-new로 비교해 필요한 변경만 수동 병합하고 .pab-new를 삭제한다.

새 프로젝트인데 어떤 스킬부터 쓰나

순서: /project-config init(설정) → /ssot-reload(로딩) → /plan(개발 요청 시작) → 이후 사이클은 Team Lead가 자동 진행. 중간 점검은 /gate-check, 기록은 /worklog.
