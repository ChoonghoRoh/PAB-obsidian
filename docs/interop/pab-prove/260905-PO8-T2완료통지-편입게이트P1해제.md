## 0. 요약 (4줄)

1. ⭐ **T2가 완료됐다. 편입 게이트 `P-1`은 우리 쪽에서 해제됐다** — 귀측은 `PO2 §7`의 조건을 충족한 것으로 보고 편입을 진행해도 된다.
2. **불합격 산출물은 이제 vault에 파일로 만들어지지 않는다.** 검증이 write **앞으로** 옮겨졌다. 귀측 정본이 우리 워커의 실패로 오염될 경로가 닫혔다 — 이것이 `P-1`의 실질이다.
3. **다만 편입 = 즉시 write가 아니다.** 우리 `T3`(정본 전환 구성)은 아직 착수 전이며, 착수도 귀측 회답 이후다. 편입 직후 우리 워커가 정본에 쓰기 시작하는 일은 **없다**.
4. **`R-8`(bridge 크래시 — `pabprove` 신규 계정 실증)은 여전히 귀측 판단 사항**이다. 우리는 그 조건을 존중하며, 실증 전 편입을 재촉하지 않는다.

## 1. 무엇이 바뀌었나 — 검증 시점 이동

### 1.1 문제

종전 워커는 **쓰고 나서 검사**했다. `runner.py:_persist`가 vault 게이트 함수로 2파일을 기록한 **뒤** link-check를 돌렸고, 불합격이 나면 잡을 `failed`로 떨어뜨렸다. **그런데 롤백이 없었다** — 실패 처리는 잡 상태만 바꿀 뿐 파일은 vault에 남았다.

정본에서는 이것이 곧 오염이다. **LiveSync는 write 순간 전파**하므로 사후 삭제는 이미 늦고, SOURCE는 `AC-4` immutable이라 애초에 지우는 것이 규칙과 충돌한다.

### 1.2 조치

판정을 write **앞**으로 옮겼다. `_persist`를 `_verdict`(판정) → `_write_pair`(기록) 2단으로 분리했고, **불합격이면 write에 도달하지 않는다.**

구현은 **가상 파일 주입**이다 — `validate.build_report()`에 `pending: {경로: 원문}` 선택 인자를 신설해, 이번 잡의 2파일을 **디스크에 놓지 않고** 판정에 참여시킨다. 판정 내용은 종전과 한 글자도 다르지 않고(같은 `build_report`, 같은 "잡 귀속분" 필터), 바뀐 것은 2파일의 **입력원**뿐이다.

> **판정 기준을 "잡 상태"가 아니라 "파일 미생성"으로 잡았다.** 잡이 `failed`인 것만으로는 불충분하다 — 파일이 한 순간이라도 존재하면 동기화 계층이 이미 가져간 뒤이기 때문이다.

### 1.3 검토했다가 버린 안 2종 — 귀측에도 해당될 수 있어 적어 둔다

| 안 | 탈락 사유 |
|:-:|---|
| **하드링크 스냅샷** | 스테이징용 write가 *"게이트 밖 write 0건"* 계약 테스트에 저촉된다. 그리고 **하드링크는 기존 노트가 정본과 inode를 공유**한다 — 스테이징의 비배타 write 1회가 곧 정본 파괴다. 막으려는 사고와 같은 종류를 도구 쪽에 새로 만든다 |
| **vault 내부 임시 파일 → rename** | 동기화 계층이 vault 내부를 감시하므로 **임시 파일도 write 시점에 전파**된다. "임시니까 괜찮다"가 성립하지 않는다 |

⇒ **동기화가 걸린 트리에서는 "스테이징 위치"라는 것이 존재하지 않는다.** 판정을 메모리로 끌어올리는 것이 유일한 해였다. 귀측이 유사한 "write 후 검증" 경로를 갖고 있다면 같은 함정에 주의를 권한다.

### 1.4 검증 결과

| 항목 | 결과 |
|---|---|
| 불합격 주입 (precheck 통과 · postcheck 불합격) | 잡 `failed` + **note·source 두 경로 모두 미생성** + 게이트 write 지점 호출 **0건** |
| D24 충돌(`_2` 비켜쓰기) 경로 | 동일 — 2파일 모두 미생성, 기존 노트 바이트 불변 |
| 판정 동등성 | *"디스크에 쓴 뒤의 리포트"* == *"같은 원문을 주입한 리포트"* 완전 일치 — **시점만 옮겼다**는 직접 증거 |
| 기존 계약 | `AC-3`·`AC-4`·게이트 밖 write 0건 계약 테스트 **무수정 통과** |
| 회귀 | **1030 passed / 0 failed / 66 deselected** (기준선 1022 + 신설 8, 정확히 일치) |
| 코드 리뷰 게이트 | `G2_be` **PASS** |

### 1.5 잔여 노출 1건 — 숨기지 않고 적는다

`_write_pair`는 **SOURCE 먼저 → 요약본 나중** 순으로 쓴다. `safe_write_source` 성공 뒤 `safe_write_note`가 차단되면 **고아 SOURCE가 남는다**. 종전 코드에도 있던 구조이며, 본 Task는 검증 **시점**만 옮겼으므로 그대로다.

다만 **현 조립 경로에서는 도달 불가**임을 확인했다: ⑴ 페어링 참조 가드는 D24 `_2` 적용 시에만 발동하는데 `build_summary_note()`가 `sources`에 SOURCE wikilink를 **코드로 항상 삽입**한다 ⑵ 화이트리스트·라우팅 가드는 조립 단계가 경로를 `10_Notes/`로 만들어 걸리지 않는다 ⑶ 배타 write의 `FileExistsError`는 판정 단계가 빈 경로를 확정한 뒤라 레이스에서만 가능하다.

⇒ **"구조적으로 불가능"이 아니라 "현 경로에서는 도달 불가"** 다. 쌍 단위 원자성은 별도 사안으로 남긴다.

## 2. 귀측 편입 실행에 대하여

### 2.1 우리 상태

| 항목 | 상태 |
|---|---|
| `T2` 검증 시점 이동 | ✅ **완료**(본 통지) |
| `T1` 정본 정비 | 미착수 — **authority = 귀측**. 우리는 요청만 한다 |
| `T3` `WIKI_ENV=prod` 전환 + 실행 위치 구성 | **미착수** — 귀측 회답 수신 전까지 진입 금지로 두고 있다 |
| 정본 vault write | **0건** — 본 Task는 정본에 손대지 않고 완료했다(개발 라인에서만 작업) |
| 정본 CouchDB probe | **0건** — `PO2 R-4` 준수 |

### 2.2 `R-8`은 여전히 귀측 판단이다

`pabprove` 신규 계정 실증 전 편입 금지 조건을 우리는 그대로 존중한다. 실증 주체는 귀측 backend-dev이며 우리 소관이 아니다. **편입 시점은 전적으로 귀측이 정하면 된다.**

### 2.3 `BL-3` 해소를 인지했다 — 다만 우리에게 직접 통지된 바는 없다

귀측 ↔ PAB-Observer 왕복 문서(`OB2-D`, 2026-09-03 발신)에서 **`BL-3`(맥북 crontab 쓰기 무한 대기)가 2026-09-02 해소**됐음을 확인했다. 우리 쪽 대기 사유였으므로 인지 사실을 밝혀 둔다.

⚠️ **다만 그것은 귀측이 Observer에게 보낸 문서이지 우리에게 온 통지가 아니다.** 우리는 이를 근거로 편입 일정을 가정하지 않는다. 편입 실행 통지는 별도로 받겠다.
