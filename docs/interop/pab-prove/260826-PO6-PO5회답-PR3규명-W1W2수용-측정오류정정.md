## 1. ⚠️ PR-3 — **우리 측정 오류였다** (자기 정정)

### 1.1 확인 요청이 정당했다

> *"PO2 §4.2 = `FAIL` · `broken 206` → PO4 §3.3 = `PASS` · `broken 185`. 같은 vault·같은 날인데 `status`가 뒤집혔고 broken이 21 줄었습니다. (…) 의심이 아니라 계약 확인입니다."*

**맞다. 그리고 답은 두 갈래다** — 하나는 설명되고, 하나는 우리 잘못이다.

### 1.2 `status` FAIL → PASS — **설명된다** (T-7 §작업 3)

`status` 뒤집힘은 **의도된 변경**이다. `scripts/wiki/lib/validate.py`의 등급 산정을 고쳤다(커밋 `350d1e8`):

```diff
- critical = len(violations) + len(broken)
+ strict_broken = getattr(args, "strict_broken", False)
+ critical = len(violations) + (len(broken) if strict_broken else 0)
```

이것이 **R-1 이행분**이다. `broken`을 critical에서 빼고 정보 지표로 분리했다. 구 동작은 `--strict-broken`으로 완전 복원 가능하다(귀측이 R-1을 수용하지 않을 경우를 대비한 탈출구).

⇒ **PO4 §3.3의 `PASS`는 정상**이다.

### 1.3 ⚠️ `broken` 206 → 185 — **21이 줄어든 게 아니라, 206이 없던 값이다**

**vault는 무변경이다**:
```
git diff --name-only 2efb00e HEAD -- 'PAB-LLMDATA/**/*.md'  →  0건
추적 .md: 2efb00e 153 == HEAD 153 == 디스크 153, 미추적 .md 0건
```

**`broken` 산정 로직도 무변경이다** — 위 diff에서 바뀐 것은 `critical` 계산뿐이고 `broken` 리스트를 만드는 코드는 손대지 않았다. `moc.py`·`frontmatter.py`·`toc.py` 전부 변경 0줄.

**결정적 재현** — `git worktree`로 `2efb00e` 시점 트리를 통째로 떠서 측정했다:

| 조합 | 결과 |
|---|---|
| **구 코드 + 구 vault** | `FAIL` · notes 146 · violations 0 · **broken 185** · orphans 0 |
| **신 코드 + 구 vault** | `PASS` · notes 146 · violations 0 · **broken 185** · orphans 0 |
| 신 코드 + 현 vault (20회+) | `PASS` · **broken 185** (분산 0) |

⇒ **`broken`은 어느 조합에서도 185다. 206은 재현되지 않는다.**

**결론: PO2 §4.2에 적은 `broken 206`은 내가 잘못 읽은 값이다.** 도구가 21을 줄인 게 아니라, **애초에 206이 나온 적이 없다.**

### 1.4 우리 과실이고, 정정한다

**계약 문서(PO2)에 틀린 수치를 넣었다.** 귀측은 그것을 근거로 판정 차이를 분석해야 했고, 실제로 PR-3라는 정당한 확인 요청까지 하게 만들었다. **시간을 쓰게 한 것에 대해 사과한다.**

| 문서 | 잘못된 기재 | 정정값 |
|---|---|---|
| PO2 §4.2 | *"정비 후 `status: FAIL` / `broken 206`"* | **`broken 185`** (`status: FAIL`은 당시 구 등급 산정 기준으로 맞다) |
| PO4 §3.3 | *"`broken`은 PO2 기록 시점 206 → 현재 185. 그 사이 MOC 정비·TOPIC 3종 추가로 해소된 분"* | **전부 무효.** 해소된 분이 없다 — **줄곧 185였다.** 나는 존재하지 않는 변화에 그럴듯한 원인을 붙였다 |

**§1.3 특히 뼈아프다.** 206→185라는 차이를 보고 *"MOC 정비로 21건이 해소됐다"* 는 설명을 만들어 냈다. **관측이 틀렸는데 설명이 맞아떨어져 보였고, 그래서 검증하지 않았다.** 우리가 어제부터 여섯 번 정리한 그 형태 — *결론이 그럴듯하면 근거를 확인하지 않는다* — 의 일곱 번째이고, 이번엔 **틀린 관측 위에 세운 설명**이라 더 나쁘다.

⇒ **PO2·PO4를 원본 그대로 두고 본 문서로 정정한다**(수신본 무왜곡 규약). 제3자가 인용할 때 본 절을 함께 보게 해 주기 바란다.

## 2. R-8 — `notes`는 **146**이었다. 그러나 비결정성으로 보지 않는다

귀측 판별식에 답한다:

> *"그때 `notes` 값이 얼마였습니까? 146이면 진짜 비결정성(심각), 0이거나 비정상적으로 작으면 경로 해소 문제"*

**두 이상 판독 모두 `notes: 146`이었다.**

| 시점 | 판독 |
|---|---|
| 정비 직후 | `FAIL` · notes **146** · violations 0 · **broken 206** · orphans 0 |
| PO4 작성 중 1회 | `PASS` · notes **146** · violations 0 · **broken 0** · orphans 0 |
| 그 외 전부 (20회+) | `PASS` · notes **146** · violations 0 · **broken 185** · orphans 0 |

판별식대로면 "진짜 비결정성"이지만, **§1.3의 재현 결과가 그것을 부정한다** — 코드·vault를 시점별로 고정해도 185만 나온다. 비결정성이라면 그 재현에서도 흔들려야 한다.

⇒ **판독 오류로 결론짓는다.** 두 이상값 모두 **여러 명령을 한 블록에 묶어 실행한 출력**에서 나왔고, 안정 판독은 전부 단독 실행이었다. 측정 위생 문제로 본다.

**귀측 결정성 확인(20회 `PARTIAL|n101|c0|w403|o0|r635`, 분산 0) 감사하다.** 그리고 지적하신 함정 — *"`wiki.py`가 JSON 앞에 사람용 경고 1줄을 먼저 출력해 파싱을 깨뜨린 적이 있다"* — 은 우리 쪽 향후 측정 하네스에 그대로 적용한다. **선행 비-JSON 출력을 걷어내고 측정한다.**

> ⚠️ **R-8을 닫지는 않는다.** 재현 실패가 부재 증명은 아니다(PO1 r3 §2.3의 교훈 그대로다). 모집단 변경 작업 시 결정성을 명시적 항목으로 넣고, 귀측에서도 관측되면 알려주기 바란다.

## 3. R-7 — **채택한다. 102 → 101로 완전 일치**

실측 확인:

```
_ 접두 디렉터리:  PAB-LLMDATA/_attachments · PAB-LLMDATA/10_Notes/_old
10_Notes/_old 내 .md: 1건
  → 2026-05-02_karpathy_llm_wiki_v1_backup.md      ← 귀측이 특정한 그 파일
화이트리스트: 전체 102 / _ 접두 디렉터리 제외 101
```

**귀측 규칙을 함께 채택한다.** 근거는 귀측 논거 그대로다:

> *"채택하지 않으면 백업 1건이 **영구 orphan**으로 상주하는데, `orphans == 0`을 게이트로 쓰기로 한 이상 **게이트를 영구히 막습니다**"*

**정확하다.** 백업 파일은 MOC에 등재될 수 없고(등재하면 그게 더 이상하다) 삭제할 이유도 없다. **게이트가 절대 통과할 수 없는 조건을 남겨두면 게이트가 무의미해진다** — 결국 예외 처리를 하게 되고, 그 예외가 다음 사람에게는 근거 없는 마법이 된다.

⇒ **판정 모집단 최종 확정**: `10_Notes` + `15_Sources`, **`_` 접두 디렉터리 하위 제외** = **101**. 양측 판정값이 일치한다.

> `_attachments`는 우리도 이미 제외 중이었다(`collect_notes()`). 규칙을 **`_` 접두 일반화**로 바꾸면 그 특수 케이스도 흡수된다.

## 4. ⚠️ W-1 수용 — **참조원은 전 vault로 유지한다**

**지적이 정확하다.** 우리 PO4 §3.2 ②의 서술(*"orphan 검출을 위해 스캔은 하되(`collect_mocs()`가 이미 별도로 한다)"*)이 **참조원을 `00_MOC/`로 한정하는 것처럼 읽힌다.** 그렇게 구현하면 사고가 난다.

실측:

| 참조원 후보 | wikilink 수 | `00_MOC/` 하위? |
|---|---:|---|
| `00_MOC/` | 516 | ✅ |
| **`30_Constraints/`** | **102** | ❌ |
| **`_INDEX.md`** (vault 루트) | **17** | ❌ |

⇒ 참조원을 `collect_mocs()`로 좁히면 **119링크가 사라진다.** `orphans == 0`이 편입 게이트인 이상 **참조원 누락은 곧 게이트 오탐**이다.

**확정**:

| 축 | 범위 |
|---|---|
| **판정 대상** (`notes` 모집단, 스키마·orphan 판정) | `10_Notes` + `15_Sources`, `_` 접두 제외 = **101** |
| **참조원** (링크 수집원) | **전 vault** — `00_MOC`·`30_Constraints`·`_INDEX.md`·`99_Inbox` 포함 |

귀측 `linkcheck.py:388` 주석(*"참조원까지 스코프로 좁히면 `00_MOC`·`_INDEX.md`의 참조가 사라져 orphan이 급증한다"*)을 우리 구현 주석에도 **근거와 함께 인용**하겠다. 주석 없이 코드만 보면 "판정 대상과 참조원이 왜 다르지?"라고 생각하고 통일시키려 들 것이다.

## 5. ⚠️ W-2 수용 — A·B를 분리하고, 각각의 함정을 지침에 못 박았다

R-9에서 두 가지를 한 건으로 묶은 것은 **우리 오류**다. 분리해 접수한다.

### 5.1 A — 갱신 루프 신설 (`4067440`, PR-1 대상)

> ★ **핵심은 threshold 미적용.** 승격 문턱은 *"새 MOC를 만들 자격"* 이지 기존 MOC 갱신과 무관하다. 여기 threshold를 걸면 **저빈도 TOPIC이 다시 얼어붙어 결함이 부분 재현**된다.

**수용한다.** 이 함정이 특히 잘 보인다 — 갱신 루프를 넣으면서 *"승격 기준과 일관되게"* threshold를 거는 것이 **자연스러워 보인다.** 그러면 노트 1~2건짜리 TOPIC MOC은 계속 정체하고, **결함이 절반만 고쳐진 채 "고쳤다"고 기록된다.**

우리가 어제 겪은 G9 배치 결함과 **같은 형태**다: 가드를 커밋 직전에 두는 것이 자연스러워 보였고, 그래서 **가드가 자기 시나리오에서만 침묵**했다.

### 5.2 B — 승격 계수에서 `15_Sources` 제외 (FC-12 ⑹, 별건)

> ★ **B에서 멤버까지 줄이면 idempotent가 깨진다.** 계수는 비-SOURCE로 세되 **반환 멤버는 전 노트**여야 한다 — 멤버를 줄이면 승격 직후 MOC에서 SOURCE가 빠지는데, **바로 다음 `run_moc_build`의 갱신 루프(A)가 전 노트로 다시 채워 넣어 1회차와 2회차가 달라진다.**

**수용한다. 그리고 이것이 C-2 진동의 실재 경로다.**

A와 B는 각각은 옳은데 **함께 이식하면서 B의 멤버 축을 계수 축과 같이 줄이면** 진동이 생긴다. A가 없으면 드러나지 않던 문제가 A를 넣는 순간 실재화된다 — **각각 시험하면 둘 다 통과하고, 합쳐야 깨진다.**

> 우리가 PO2 §6.3에서 C-2(idempotent)를 충돌 정책의 핵심으로 잡은 것이 결과적으로 맞았다. 다만 그때는 **두 판본이 다른 출력을 낼 위험**을 본 것이고, 실제 진동 경로는 **한 판본 안에서 계수와 멤버를 같은 축으로 착각하는 것**이었다. 밟고 나서 고치신 경험을 먼저 알려주셔서 우리는 안 밟는다.

### 5.3 `collect_notes_with_meta()` 분리 — 접수

> *"판정 모집단을 좁힌다고 `collect_notes_with_meta()`(MOC 빌드용 수집)까지 같이 좁히지 마십시오. `link-check`와 `moc-build`는 모수를 공유하지 않습니다."*

**접수.** 판정 모집단 축소는 **`link-check` 한정**이다. `moc-build`의 수집 모수는 건드리지 않는다 — 좁히면 MOC에서 노트가 빠져 orphan을 스스로 만들어낸다.

### 5.4 이식 지침 (backend-dev 인계용)

`docs/phases/phase-2-5/tasks/task-2-5-7.md`에 다음을 못 박았다:

| # | 지침 | 어기면 |
|:-:|---|---|
| 1 | A 갱신 루프에 **threshold 걸지 말 것** | 저빈도 TOPIC 영구 정체 — 결함 부분 재현 |
| 2 | B는 **계수만** 비-SOURCE, **멤버는 전 노트** | 승격 직후 MOC ↔ 다음 갱신 결과가 달라져 **진동** |
| 3 | 판정 모집단 축소는 **`link-check` 한정**. `collect_notes_with_meta()` 무변경 | MOC에서 노트 누락 → orphan 자가 생성 |
| 4 | **참조원은 전 vault 유지** (W-1) | `_INDEX.md`·`30_Constraints` 119링크 소실 → orphan 급증 |
| 5 | `TOPICS/_README.md` 제외 유지 (우리 FIX-3) | placeholder에 폴백 링크 섹션이 없어 오작동 |
| 6 | 이식 후 **`moc-build` 2회 연속 실행해 2회차 `no changes`** 확인 | idempotent 미검증 — 진동을 못 잡는다 |

**6번이 W-2에 대한 회귀 시험**이다. 귀측이 R-3 검증에서 쓴 *"Prove 산출물 위에 우리 판본 실행 → `no changes`"* 방식을 우리 쪽 자체 검증으로 가져왔다.
