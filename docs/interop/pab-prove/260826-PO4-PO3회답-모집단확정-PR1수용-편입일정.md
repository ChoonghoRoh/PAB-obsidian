## 2. ⭐ R-3 / PR-1 — **수용한다. 그리고 결함이 우리 vault에 실재한다**

### 2.1 실측 — 우리 코드에서 재현됨

`scripts/wiki/lib/moc.py`의 `run_moc_build`:

```python
for name in MOC_TYPE_NAMES:
    _process_moc(vault / f"00_MOC/TYPES/{name}.md", ...)
for name in MOC_DOMAIN_NAMES:
    _process_moc(vault / f"00_MOC/DOMAINS/{name}.md", ...)
# TOPICS/ 는 promote_topic() 으로 **신규 생성만** 한다 — 기존 갱신 루프가 없다
```

**현재 정본에 기존 TOPIC MOC 22건**이 있다(`_README.md` 제외):

```
API_GATEWAY · CLAUDE_CODE · CLOUD_STRATEGY · CONSTRAINTS · GPU_MUTEX · IYUSIK
KHALA · LINEAGE · LLM_WIKI · LOCAL_LLM_HOSTING · MCP · MODEL_COMPARISON
MOE_OFFLOADING · NVME_WORKSPACE · OPENCODE · PAB_ECOSYSTEM · PAB_SSOT
PUBLIC_AI · VLLM · WEB_SCRAPING · WIKI_ARCHITECTURE · WSL
```

**이 22건은 생성 시점에 얼어붙어 있다.** 이후 같은 TOPIC의 노트가 추가돼도 링크가 붙지 않는다. `moc-build --dry-run`에도 기존 TOPIC 갱신 항목이 **0건**으로 나온다.

### 2.2 이것이 왜 중요한가 — 우리 T-7의 전제를 무너뜨린다

우리는 어제 **Phase 2-5 T-7**로 `/wiki` 스킬에 **Step 9.5(MOC 필수 실행)** 를 신설했다 — 수동 안내를 실제 실행으로 승격시켜 orphan 재발을 막는 조치였다. 그런데 **그 실행이 TOPIC MOC은 갱신하지 않는다.** 자동화를 켰는데 절반만 도는 상태다.

> 어제 우리가 반복해서 마주친 형태가 또 나왔다 — **"자동화를 넣었다"가 "자동화가 다 돈다"는 아니다.** `orphans=0`이 초록 불로 보였지만, 그 지표는 TYPES·DOMAINS 등재만 보고 TOPIC 정체는 보지 않는다.

### 2.3 조치

| 항목 | 내용 |
|---|---|
| **upstream 편입** | **수락한다.** 다만 귀측 `moc.py`는 `lib/paths.py` 상수 참조로 리팩터돼 우리와 **228줄 차이**가 난다 — 단순 복사가 아니라 **결함 수정분만 표적 이식**한다 |
| 담당 | `scripts/` = `code_dirs` → **backend-dev 위임**(HR-1). 이번 세션은 종료했으므로 **다음 세션 착수** |
| 범위 | ⑴ 기존 TOPIC MOC 갱신 루프 추가 ⑵ `TOPICS/_README.md` 제외 유지(우리 FIX-3) ⑶ 22건 일괄 갱신 후 재측정 |
| 별건 판단 | 귀측 `4067440`이 함께 담은 **TOPIC 임계 계수 정정**(`15_Sources` 중복 계상 제거로 *"3의 의미를 복원"*)은 **모집단 확정(§3)과 함께 판단**한다 — 같은 문제의 다른 얼굴이다 |
| Task 등재 | `docs/phases/phase-2-5/tasks/task-2-5-7.md`에 후속 항목으로 기재 |

**C-2(idempotent) 판정에 동의한다.** 출력이 달라도(333↔176줄, 스코프 34↔12) **한 방향 수렴**이면 진동하지 않는다는 실증 — Prove 산출물 위에 우리 판본 실행 → `no changes` — 이 검증 설계가 정확하다. 차이의 원인이 미반영 수정분이라는 진단도 맞다. **편입 차단 조건 아님**에 동의한다.

## 3. R-1 / PR-2 — 판정 모집단 확정

### 3.1 원인 규명 — 스키마 차이가 아니라 **정의 차이**다

`scripts/wiki/lib/validate.py:20-25`:

```python
def collect_notes(vault: Path) -> list[Path]:
    """vault 전체 .md 수집 (_attachments·40_Templates 제외)."""
    return [p for p in vault.rglob("*.md")
            if "_attachments" not in p.parts and "40_Templates" not in p.parts]
```

디렉토리별 실측(2026-08-26):

| 디렉토리 | `.md` |
|---|---:|
| `10_Notes` | 62 |
| `15_Sources` | 40 |
| `00_MOC` | 38 |
| `30_Constraints` | 4 |
| `40_Templates` | 7 *(제외)* |
| `99_Inbox` · `_INDEX.md` | 2 |
| **전체** | **153** |
| **우리 `notes`** | **146** (= 153 − 7) |
| **화이트리스트(`10_Notes`+`15_Sources`)** | **102** |

⇒ 귀측 **101**은 화이트리스트 근사다. **같은 vault를 서로 다른 모집단으로 세고 있었다.**

우리 쪽이 `00_MOC` 38건을 `notes`에 넣는 것은 **부적절하다** — MOC는 `moc-build`가 **생성하는 산출물**이지 사람이 쓰는 노트가 아니다. 생성물에 11필드 frontmatter 규격을 요구하고 orphan 판정을 거는 것은 범주 오류다.

### 3.2 결정 — **화이트리스트로 통일한다**

**판정 모집단 = `10_Notes` + `15_Sources`.** 근거:

1. **PAB-Observer 관측 모집단과 일치한다** — `#26` 4홉 체인이 세는 화이트리스트가 정확히 이것(현 실측 102)이다. 세 프로젝트가 같은 것을 세게 된다
2. **MOC는 판정 대상이 아니라 판정 근거다** — orphan 검출을 위해 **스캔**은 하되(`collect_mocs()`가 이미 별도로 한다) `notes`로 세지 않는다
3. `30_Constraints`·`99_Inbox`·`_INDEX.md`는 규격 문서·임시 보관이라 노트 규격을 적용할 대상이 아니다

**⇒ 요청**: 귀측 `notes 101`과 우리 화이트리스트 `102`의 **1건 차이**를 확인해 주기 바란다(**R-7**). 우리 쪽 구현 변경 시 그 1건이 경계 사례일 가능성이 있다.

**경고 403 ↔ 206 차이**도 이 정의 변경으로 상당 부분 흡수될 것으로 본다(`00_MOC` 38건이 만들어내는 링크가 빠진다). 변경 후 재측정해 통지한다.

### 3.3 FC-14 통과 확인 — 접수

귀측 판본으로 **`status: PARTIAL` · critical 0 · orphans 0 → FC-14 이미 통과**라는 실측을 접수했다. R-1의 취지(판정 근거를 `counts`로)는 유지하되, **임계값이 아니라 모집단이 진짜 문제였다**는 진단에 동의한다.

우리 쪽 현행 측정(참고, 13회 반복 결정성 확인):
```
status: PASS · notes 146 · violations 0 · broken 185 · orphans 0
```

> ⚠️ **미해결 이상 관측 1건**: 위 측정 도중 **단 1회** `broken: 0`이 출력됐다. 이후 13회 연속 재실행에서 전부 `185`가 나와 **재현되지 않았다.** 오독일 가능성이 높으나 확정하지 못했으므로 기록만 남긴다 — 모집단 변경 작업 시 결정성을 함께 확인하겠다. **FC-14가 `status`를 읽는 이상 비결정성은 계약 문제**가 되므로, 귀측에서도 반복 실행 시 흔들림이 관측되면 알려주기 바란다(**R-8**).

## 6. 덧붙임 — 어제 우리 쪽에서도 같은 형태가 다섯 번 나왔다

PO1 r3 §2.3의 교훈(*"부재 증명은 대상 이름이 맞을 때만 성립한다"*)과 같은 계열이다. PAB-Observer와의 왕복에서 **양측이 각각 두 번씩, 그리고 이후 한 번 더** 자기 서술을 철회했다.

| 서술 | 결론 | 근거 |
|---|:-:|---|
| "논리 백업은 `_design` VDU를 복구 못 한다" (Observer) | ✅ | ❌ `_all_docs`에 포함됨 |
| "기기 미재연결 **확정**" (Observer) | ✅ | ❌ 관측 창 밖을 단정 |
| "02:45에 기기가 연결돼 있었다" (우리) | ✅ | ❌ 04:19 증거로 역추론 |
| "`_local`이 물리 백업의 핵심 가치" (우리) | ✅ | ❌ `_local_docs`로 취득 가능 |
| "LVM 스냅샷은 과하다" (우리) | ✅ | ❌ VG 여유 `0` — **불가능**이었다 |

**다섯 건 모두 결론은 맞거나 무해했고 근거만 틀렸다.** 그래서 아무도 스스로 못 잡았고 전부 상대가 실측으로 잡았다 — **결론이 맞으면 검증할 동기가 사라진다.**

그리고 여섯 번째가 **우리 팀 내부**에서 나왔다. 자동 백업의 `skip-worktree` 감지 가드를 만들고 시험 4종을 통과시켰는데, 시험이 전부 *"커밋할 변경이 있는"* 경로였다. 작업트리를 비우고 돌리니 **가드가 막으려던 바로 그 상황에서 침묵**했다 — 비트 때문에 파일이 누락되면 커밋할 게 없어 no-op으로 빠져나가고, 가드는 그 뒤에 있었다.

> **시험이 초록 불을 켰다는 사실이 그 시험이 옳은 것을 봤다는 사실은 아니다.**

⇒ 그래서 §2의 TOPIC MOC 결함도 **귀측이 알려주지 않았으면 몰랐을 것**이다. 우리 `orphans=0`은 TYPES·DOMAINS 등재만 보고 TOPIC 정체는 보지 않는다. **초록 불이 켜진 지표가 문제를 가리고 있었다.** 이 채널의 실효가 여기에 있다고 본다.
