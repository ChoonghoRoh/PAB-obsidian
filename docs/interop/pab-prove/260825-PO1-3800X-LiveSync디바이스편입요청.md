⇒ 당초 설계했던 **아웃박스(`/home/oceanui/pab-wiki-outbox`) · 데스크톱 flush 에이전트**는 **폐기**한다.

### 1.2 AC-3(단일 writer) 판정

PAB-Prove 절대제약 AC-3의 보호 대상은 **"Prove가 CouchDB·미러에 직접 쓰지 않는다"** 이지, *CouchDB 클라이언트가 하나여야 한다*가 아니다.

| 계층 | 편입 후 |
|---|---|
| CouchDB에 쓰는 주체 | **동기 계층**(LiveSync/bridge) — Mac·Lenovo와 동일. Prove 코드는 미접촉 |

⇒ 폰이 디바이스인 것과 3800X가 디바이스인 것은 구조적으로 같다. **AC-3 무저촉**으로 판정했다. **이견이 있으면 알려주기 바란다** — vault authority 측 판단이 우선한다.

## 2. ★ 본론 — 3800X의 LiveSync 디바이스 편입 (요청 3건)

### 2.1 요청하는 구조

```
Mac        Obsidian + LiveSync  ─┐
Lenovo     Obsidian + LiveSync  ─┼─→ CouchDB pab-llmdata ─→ bridge ─→ 미러 ─:ro→ v4
3800X      PAB-LLMDATA 사본     ─┘      (3005 docs)
           ↑ Prove 워커가 여기 write
```

**신규 컴포넌트는 vault 사본 디렉토리 1개뿐**이다. 나머지는 기존 인프라를 쓴다.

> PAB-obsidian **Phase 2-1**(완료 2026-06-16, *"다기기 동기화 + 백업 인프라 — CouchDB LiveSync를 3800X에 구축"*)이 이미 세워 둔 기반 위에 **디바이스를 하나 더 얹는 요청**이다. 새 인프라를 세우자는 것이 아니다.

### 2.2 ⚠️ 현재 차단 요인 — bridge 단방향 패치

PAB-Prove가 서버 `pab-livesync-bridge` 컨테이너 내부를 실측한 결과, **PAB가 직접 넣은 단방향 패치**가 있다.

```
/app/Hub.ts:7-19  (주석 원문)
// PAB Phase 2-1 단방향 패치 (방법 A 외부연계)
// livesync-bridge 는 네이티브 one-way 옵션이 없다. 원본 Hub.dispatch 는 같은 group 의
// 모든 peer 에 put/delete 를 전파하므로, storage(미러)가 변경되면 couchdb 로 역전파한다.
// 그러면 (1) CouchDB 읽기전용 계정/validate_doc_update 에 의해 forbidden 이 발생하고,
// (2) 그 forbidden 이 uncaught LiveSyncError 로 컨테이너를 크래시시킨다.
```

```js
/app/Hub.ts:50-53
if (source.config.type === "storage" && peer.config.type === "couchdb") {
    continue;   // ← storage → CouchDB 전면 차단
}
```

**⇒ 차단 조건이 `group` 무관 전역이다.** 새 group으로 peer를 추가해도 막힌다.

> **원본 `livesync-bridge`는 양방향**이며, 그 원본 동작이 정확히 본 요청이 필요로 하는 것이다. 패치는 **미러를 읽기전용으로 만들기 위한** 조치였다.

### 2.3 패치 전제의 재검증 — 현재는 성립하지 않을 수 있다

주석이 든 두 근거를 실측했다(2026-08-25).

| 주석의 근거 | 실측 결과 |
|---|---|
| `validate_doc_update` 로 forbidden | **`_design/_auth` 부재** — `{"error":"not_found","reason":"missing"}` |
| CouchDB **읽기전용 계정** | `_security` = `{"members":{"names":["pabbridge"],"roles":["_admin","bridge_ro"]}}` → CouchDB 표준상 **member는 일반 doc 쓰기 가능** |

⚠️ **다만 실증하지 않았다.** 정본 DB에 테스트 doc을 쓰는 것은 위험하다고 판단해 중단했다(시도한 probe는 `_` 접두어 때문에 `illegal_docid`로 반려됐고 **권한 판정이 아니다**).

⇒ 패치 당시와 권한 설정이 달라졌을 가능성이 있다. **확인은 인프라 소관에서 해주기 바란다.**

## 3. 승격과의 관계 — **독립 사안이 된다** (r1에서 변경)

r1은 *"승격 먼저 vs 전환 먼저"* 순서 조율을 요청했다. **디바이스 편입 방식에서는 그 논쟁이 해소된다.**

| | **승격** (OB2 §2·§3) | **디바이스 편입** (본 문서) |
|---|---|---|
| 대상 | 서버 `pab-wiki-vault`의 **기존 262 md** | 3800X의 **새 `PAB-LLMDATA` 사본** |
| 성격 | 일회성 **병합** | 지속적 **동기 참여** |
| 상호 영향 | — | **없음** — 서로 다른 디렉토리 |

⇒ **두 작업은 병렬 진행이 가능하다.** 승격은 기존 개발 산출물의 편입 여부 문제이고, 디바이스 편입은 향후 산출물의 경로 문제다.

**다만 한 가지 조율이 남는다**: 편입 후 Prove 산출물이 계속 생성되므로, OB2 §4의 *"서버 증분 60건 선별 회수"* 기준을 정할 때 **"어느 시점 이후 산출물은 자동 편입"** 이라는 경계가 필요하다. 그 시점이 곧 편입 실행일이다.

**검증 시점 이동.** 현행 워커는 `runner.py:355-356`(write) → `:369`(postcheck) 순서로 **write 후 검사**한다. 격리 vault에서는 무해했으나 **디바이스 편입 후에는 위험하다** — 파일을 쓰는 순간 동기가 걸려 **불합격 산출물이 검사 전에 CouchDB로 나간다.**

⇒ 검증을 **write 전**으로 옮기거나 **스테이징 후 합격분만 이동**하는 구조로 바꾼다. **편입보다 반드시 먼저** 완료한다. PAB-Prove 내부 코드 작업이라 조율 대상이 아니다.

## 6. 참고 실측 — 판단에 도움이 될 수 있는 3건

전부 2026-08-25 PAB-Prove 실측이다.

### 6.1 git은 전파 경로가 아니다

`PAB-LLMDATA`의 **git 미커밋** 노트 4쌍(`local_llm_limit_ladder` · `scrapling_web_scraping` · `minimax_h3_3090_feasibility` · `qwen3_8_27b_model_card`)이 **전부 `pab-vault-mirror`에 도달**해 있다.
⇒ 동기 계층은 파일시스템을 직접 감지하며, **git·GitHub 백업은 별개 층**이다. 커밋 여부는 v4 도달과 무관하다.

### 6.2 미러 결손 3종의 원인 — 파손이 아니다

| 결손 | 원인 |
|---|---|
| `20_Lessons` 부재 | 정본에서 **빈 디렉터리**(`.gitkeep`만) |
| `_attachments` 부재 | 정본에서 **완전히 비어 있음**(0건) |
| `_INDEX.md` → `INDEX.md` | 밑줄 소실 (별개 사안) |

⇒ 앞의 2건은 **파일 단위 동기라 빈 디렉터리를 전파하지 않는** 정상 동작이다. 정본에 파일이 생기면 자동 해소된다. PAB-Prove는 **수정 대상 아님**으로 확정했다.

### 6.3 OB2 §5.1 교차 확인

OB2 §5.1의 *"로컬 전체 `.md` == 미러, 150 == 150"* 을 독립 실측으로 확인했다(정본 150 md / 61 notes, 미러 150 md / 61 notes). CouchDB `pab-llmdata` **3005 docs** · bridge 정상 가동도 확인했다.

### 6.4 OB2 §6 회답 — Khala README 정정 시점

> OB2 §6: *"PAB-Prove 측 정정은 승격 확정(OB3) 이후가 낫다 — 전달 바람"*
