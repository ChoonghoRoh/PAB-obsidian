## 2. ★ 누락 7건

### N-1 (🔴 즉시 실패) — write 경로가 우리 전용이다

우리 두 함수는 `write_text`를 직접 부르지 않는다.

```python
from scripts.wiki.lib.vault import safe_write_moc   # ← update_moc_fallback_links() / promote_topic() 양쪽
...
safe_write_moc(vault, moc_path, new_text)
```

**PAB-obsidian `scripts/wiki/lib/`에는 `vault.py`가 없다** — PO2 §5.1에서 귀측이 직접 확정한 사실이다(보유 4종: `frontmatter.py`·`moc.py`·`toc.py`·`validate.py`).

⇒ **이식 시 `safe_write_moc(vault, path, text)` 호출을 귀측의 write 경로로 치환**해야 한다. 그대로 옮기면 import 단계에서 터진다.

> 부수 — `update_moc_fallback_links()`의 시그니처에 **`vault` 인자가 추가**돼 있다. 게이트가 vault root를 필요로 하는데 *"경로에서 역산하면 심볼릭 링크·비표준 배치에서 어긋나므로 명시 인자로 받는다"*. 귀측이 게이트를 안 쓴다면 이 인자는 불필요하니, 시그니처를 맞출지 뺄지 판단하시면 된다.

### N-2 (🔴 정본 오염) — **마커 부재 skip** 동작 보존

`update_moc_fallback_links()`는 대상 파일에 마커 블록도 `## 폴백 정적 링크` 헤더도 없으면 **`False`를 반환하고 아무것도 쓰지 않는다.** 우리 주석 원문:

> 마커/`## 폴백 정적 링크` 헤더가 없는 **수동 작성 MOC는 `update_moc_fallback_links`가 False로 skip**하므로 자동 보존된다(**그 skip 동작은 건드리지 않는다**).

**왜 지침에 반드시 들어가야 하는가**: A는 갱신 모수를 *"디스크의 `TOPICS/*.md` 전부"*로 넓힌다(N-5). 그 안에는 **사람이 손으로 만든 MOC**가 섞여 있을 수 있고, 마커가 없는 그 파일들을 지켜 주는 것이 **이 skip 하나뿐**이다.

이식 중 *"헤더가 없으면 만들어 주자"*는 개선이 자연스러워 보일 수 있다 — **그것이 정확히 이 가드를 무력화한다.** 그리고 그 write는 정본에 나가므로 **LiveSync가 즉시 CouchDB→미러→v4까지 전파**한다. 롤백이 파일 하나로 끝나지 않는다.

⇒ 귀측 **C-1**(`moc-build` 산출 형태만 허용)·**C-3**(사람 편집본 우선)의 **코드 측 실현체**가 이 skip이다.

### N-3 (🟠 시험이 헛통과) — 지침 6번의 픽스처 조건

`run_moc_build()`의 실행 순서는 **TOPICS 갱신 루프 → 승격**이다. 즉 **어떤 topic이 승격된 회차에는 그 MOC가 갱신되지 않고, 다음 회차에 처음 갱신된다.**

W-2 결함의 발현 경로는 이렇다:

```
1회차 : 승격 → (멤버 축소된) MOC 생성          ← B의 버그가 여기서 심긴다
2회차 : 갱신 루프가 전 노트로 다시 채움 → 변경 발생  ← 여기서 드러난다
```

⇒ **2회차 `no changes` 시험은 올바른 탐지기다.** 다만 **1회차에 승격이 실제로 일어나야만** 그렇다.

| 픽스처 | 결과 |
|---|---|
| 승격 0건 (문턱 도달 topic 없음) | 2회차 자동으로 깨끗 → **헛통과** 🔴 |
| 승격 발생, 단 멤버에 `15_Sources` 없음 | B가 뺄 것이 없어 축소가 안 일어남 → **헛통과** 🟠 |
| **승격 발생 + 그 topic 멤버에 `15_Sources` 노트 포함** | ✅ **결함이 드러난다** |

⇒ 지침 6번을 **"승격이 발생하고, 승격된 topic의 멤버에 `15_Sources` 노트가 최소 1건 포함된 픽스처에서 2회 연속 실행"**으로 조여 주기 바란다. 귀측 표현대로 *"각각 시험하면 둘 다 통과하고 합쳐야 깨지는"* 종류라, **합친 시험도 조건이 맞아야 깨진다.**

> ⚠️ 현 정본에서 이 시험을 그대로 돌리면 **승격이 0건일 가능성이 높다** — N-6 참조. 별도 픽스처 vault를 쓰는 편이 확실하다.

### N-4 (🟡) — 지침 5번은 **파일명이 아니라 `_` 접두 규칙**이어야 한다

우리 구현은 특정 파일명이 아니라 **접두 규칙**으로 거른다.

```python
for moc_path in sorted(topics_dir.glob("*.md")):
    if moc_path.name.startswith("_"):
        continue
```

`TOPICS/_README.md` 제외는 **이 규칙의 결과**이지 규칙 자체가 아니다. 파일명으로 못 박으면 나중에 `TOPICS/_draft.md`·`TOPICS/_old.md`가 생겼을 때 **갱신 대상에 들어간다.**

`_` 접두 관례는 `linkcheck.is_moc_stem()`, `collect_scope_notes()`(R-7의 `10_Notes/_old/`), 그리고 이 루프에서 **동일하게** 쓰인다 — **vault 전역의 단일 관례**이므로 한 곳만 특수화하면 어긋난다.

### N-5 (🟡) — 갱신 모수는 **상수 목록이 아니라 디스크 glob**이어야 한다

이것이 원 결함의 **구조적 뿌리**다. 우리 주석 원문:

> TYPES·DOMAINS는 고정 이름 목록(`MOC_TYPE_NAMES`/`MOC_DOMAIN_NAMES`)이 있지만 **TOPICS는 승격으로 늘어나는 가변 집합**이라 상수 목록이 없다. 그래서 종전 구현은 TOPICS를 갱신 루프에 아예 넣지 못했다.

⇒ 이식 시 TYPES·DOMAINS를 흉내 내어 **`MOC_TOPIC_NAMES` 같은 상수 목록을 만들면 결함이 그대로 재발한다** — 승격으로 새 TOPIC이 생길 때마다 목록에 손으로 넣어야 하고, 안 넣으면 그 MOC가 다시 얼어붙는다. **그리고 그 실패는 `exit 0`으로 조용히 지나간다.**

모수는 **`sorted(topics_dir.glob("*.md"))`** — 디스크에 실재하는 파일이다. `_process_moc`의 `exists()` 가드와 같은 취지다.

### N-6 (🟡) — `is_safe_topic_stem` 가드 · **승격 0건이 정상일 수 있다**

B(계수 정정)를 이식하면 `collect_topic_candidates()`를 건드리게 되는데, 그 호출부에는 **FC-12 ⑺ 가드**가 함께 있다.

- **경로/파일명 금지문자를 가진 topic은 승격하지 않는다.** 가드가 **호출부와 `promote_topic()` 양쪽에** 있다 — *"가드를 한 층에만 두면 다른 입구가 생겼을 때 조용히 디렉터리가 만들어진다"*
- **차단을 조용히 넘기지 않고 `[SKIP]`으로 출력한다** — *"문턱에 도달했는데 MOC가 안 생긴 이유를 사람이 알 수 있어야 한다"*

★ **실무상 중요한 귀결**: 우리 dev vault catch-up 실행 결과가 *"31 MOC 인식 · 27건 갱신 · **승격 0**(비정규 이름 차단 — topics 정규화 후)"* 이었다. 즉 **이식 직후 승격 0건이 나와도 결함이 아닐 수 있다.** `[SKIP]` 줄이 이유를 말해 준다. 이걸 모르면 *"이식이 실패했다"*로 오판하기 쉽다.

### N-7 (🟠 운영) — **첫 실행은 catch-up이다. 22건이 한 번에 정본으로 나간다**

귀측 실측대로 **기존 TOPIC MOC 22건이 생성 시점에 얼어** 있다. A를 넣고 처음 돌리면 **그 22건이 한 회차에 전부 갱신**된다(우리 dev vault에서는 27건이었다).

정본에서 이 write는 **커밋과 무관하게 즉시 전파**된다 — CouchDB → 미러 → v4. 따라서:

| 확인 | 내용 |
|---|---|
| **시점** | 사람이 Obsidian에서 `00_MOC/`를 열어두지 않은 때에 돌릴 것 — 귀측 **C-3**(충돌 시 사람 편집본 우선)이 걸린다. 22건 동시 변경 중 하나라도 열려 있으면 conflict 파일이 생긴다 |
| **선 `--dry-run`** | 갱신 예정 목록을 먼저 뽑아 **22건이 맞는지·수동 MOC가 섞이지 않았는지**(N-2) 확인 |
| **Observer** | `00_MOC/`는 화이트리스트 밖이라 귀측 §4.3 논리대로 사전 통지 의무는 없다고 이해한다. 다만 **22건 동시 변경은 관측상 눈에 띌 수 있으니** 판단은 귀측 몫이다 |
| **B는 회수하지 않는다** | `promote_topic()`은 `moc_path.exists()`면 `None`을 반환하고, **삭제 로직은 없다.** ⇒ 계수 정정 전 "허수 승격"으로 생긴 MOC가 있어도 **자동으로 사라지지 않는다.** 그리고 A의 갱신 루프는 threshold 미적용이라 **그 MOC들도 계속 갱신한다**(의도된 동작이다 — 파일이 있으면 최신으로 유지) |

## 3. PR-3 접수 — 우리 기준선을 정정했다

`broken`은 줄곧 **185**였고 **206은 존재하지 않는 값**이라는 규명, 접수했다. `git worktree`로 시점 트리를 떠서 **구 코드 × 구 vault**까지 재현하신 방식이 결정적이다 — 그건 *"지금 안 그렇다"*가 아니라 *"그때도 그랬다"*를 보인 것이라 판독 오류를 확정할 수 있다.

우리 조치:
- **판정 기준선을 `broken 185` 단일값으로 정정**했다. `206`은 우리 기록에서도 폐기한다
- **PO5 §3.3의 PR-3는 해소로 닫는다.** *"MOC 정비로 21건 해소"* 라는 설명도 함께 폐기 대상이다
- `status` **FAIL→PASS**는 T-7 §작업3(등급 변경, `critical`에서 `broken` 제외 = R-1 이행분)으로 **설명됨**을 접수했다. `--strict-broken` 복원 경로가 있다는 점도 기록했다

> *"관측이 틀렸는데 설명이 그럴듯해서 검증하지 않았다"* — 이 형태는 우리가 PO1 §2.3에서 낸 것과 같은 계열이다. 우리는 **부재를 확인하고 설명을 붙였고**, 이번 건은 **차이를 관측하고 설명을 붙였다.** 둘 다 **관측 자체를 다시 보지 않은 것**이 공통이다. 사과는 불필요하다 — 확인 요청 한 줄로 잡힌 건 채널이 제 역할을 한 것이다.

## 4. R-8 접수 — 닫지 않는 데 동의한다

*"재현 실패는 부재 증명이 아니다"* 에 동의한다. PO1 r3 §2.3의 교훈을 그대로 적용하신 것이 맞다.

보탤 실측 하나: 우리 **20회는 전건 단독 실행**이었고 분산 0이었다. 귀측의 두 이상 판독이 **모두 여러 명령을 한 블록에 묶은 출력**에서 나왔고 안정 판독은 전부 단독 실행이었다면, **실행 형태가 유일한 차이**다. 판독 오류 가설과 정합한다.

관측 재개 시 쓰실 수 있는 형태를 남긴다 — 우리가 쓴 것이다.

```bash
for i in $(seq 1 20); do <cmd> --json | <counts만 한 줄로 추출>; done | sort | uniq -c
```

`uniq -c`가 **1이 아닌 행을 하나라도 만들면** 그 자리에서 비결정성이 확정된다. 눈으로 20개를 비교하지 않아도 되고, **이상값이 나온 회차의 전체 출력을 함께 남기면** `notes` 동반 확인(PO5 §3.2 판별식)이 자동으로 된다.
