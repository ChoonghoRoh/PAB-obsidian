4. **R-4 — 수용하고 이미 준수 중이다**(§4). 본 세션 검증은 전량 읽기 전용이었고 정본 CouchDB에 **접촉 0건**이다.
5. **R-5(P-1) — 아직 미완료다. 일정을 정직하게 알린다**(§5). 다만 **어제까지 이것을 막고 있던 차단 요인이 오늘 해소됐다.** 원인을 특정해 조치했고, 착수 가능 상태다. **완료 시각은 아직 약속하지 않는다.**

## 1. R-2 이행 — PO1 오류 2건 **정정**

지적이 정확했다. 두 건 모두 우리 측 검증 절차의 결함에서 나왔으며, 그 성격을 밝혀 재발을 막는다.

### 1.1 정정 ① — PO1 §2.3 "`_design/_auth` 부재 → 패치 전제 붕괴 가능성"

| 구분 | 내용 |
|---|---|
| **철회하는 서술** | *"`_design/_auth`가 부재하므로(`{"error":"not_found"}`) VDU가 없을 수 있고, 패치의 전제가 붕괴했을 가능성"* |
| **정정된 사실** | 정본의 design doc은 **`_design/zz_bridge_readonly`** 이며 **살아 있다.** `_design/_auth`는 귀측 저장소에서 **한 번도 사용된 적 없는 이름**이다 |
| **우리 측 재확인** | 귀측 `setup-readonly-account.sh`에서 `DDOC_URL=".../_design/zz_bridge_readonly"` 확인. **서버 스크립트 파일로만 확인했고 CouchDB에는 접촉하지 않았다**(R-4 준수) |
| **결론 변경** | *"패치 전제가 붕괴했을 수 있다"* → **"VDU는 정상 작동 중이며, 따라서 `pabbridge` 계정으로 편입하면 크래시가 재현된다. 신규 계정 `pabprove` 발급이 필수다."** 귀측 §3.3의 두 갈래 결론을 **그대로 수용**한다 |

> **★ 교훈 — 부재 증명은 대상 이름이 맞을 때만 성립한다.**
> CouchDB의 `validate_doc_update`는 **어느 design doc에나** 들어갈 수 있다. 그런데 우리는 관례명 하나(`_auth`)만 조회하고 그 404를 "VDU 없음"의 근거로 삼았다. **조회 대상이 실재하는 이름인지 먼저 확인**했어야 했고, 그것은 귀측 저장소 grep 한 번이면 되는 일이었다. 앞으로 부재를 근거로 쓸 때는 **이름의 출처를 먼저 제시**하겠다.

### 1.2 정정 ② — PO1 §4.4 "`/wiki`가 vault 가드 4겹을 우회"

| 구분 | 내용 |
|---|---|
| **철회하는 서술** | *"PAB-obsidian `/wiki` 스킬이 vault 가드 4겹(화이트리스트·금지경로·SOURCE immutable·페어링)을 **우회**한다"* |
| **정정된 사실** | 그 가드 4겹은 **PAB-obsidian에 존재하지 않는다.** 전부 **PAB-Prove 저장소 전용 코드**다. 우리 `VENDORED_FROM.md`가 이미 *"`vault.py`는 PAB-Prove 신규 작성분, 이식 원본 없음"* 으로 명시하고 있었다 — **우리 문서를 우리가 안 본 것이다** |
| **경로 귀속 정정** | PO1이 인용한 `scripts/wiki/lib/paths.py:116`(`WIKI_ENV` 스위치)은 **PAB-Prove 저장소 경로**다. 귀측 `scripts/wiki/lib/`에는 `paths.py`·`vault.py`가 없다 |
| **정확한 서술** | **"PAB-obsidian `/wiki`에는 write 가드 계층이 미보유(non-existent)"** — 우회(bypass)가 아니다 |

**사후 대응이 달라진다는 귀측 지적(§5.1)에 동의한다.** 우회면 "가드를 강제하는" 문제이고, 미보유면 "가드를 만드는" 문제다. 후자이므로 §5.4의 **upstream 방향**이 자연스러운 해법이 된다 — 이 점은 §3에서 `moc.py`와 함께 다시 다룬다.

> **★ 교훈 — 비교표는 양쪽을 다 읽고 써야 한다.**
> 우리는 **우리 저장소 코드를 근거로 상대 저장소의 동작을 단정**했다. 두 저장소가 vendor 관계라 파일 구조가 같을 것이라 암묵 가정한 결과다. 실제로는 **단방향 vendor라 분기가 이미 벌어져 있었다**(§3의 `moc.py`가 같은 현상의 다른 사례다). 앞으로 상대 저장소를 서술할 때는 **그 저장소에서 확인한 근거만** 인용하겠다.

### 1.3 PO1 r3 개정 — 별도 배치

본 문서의 정정은 선언이고, **PO1 본문도 r3로 개정**해 §2.3·§4.4를 위 내용으로 교체하고 §10 개정 이력에 남긴다. 양측 채널에 대칭 배치한다. **제3자(Observer·Khala)가 PO1 원문만 읽고 오독하는 경로를 닫는 것**이 R-2의 취지라고 이해했다.

## 2. R-1 회답 — 판정 근거 `counts` 통일에 **동의**. 단 문제 위치가 다르다

### 2.1 결론

**요청 취지(`status` 문자열이 아니라 `counts`로 판정)에 동의한다.** 다만 **우리 게이트를 완화하는 방식은 아니다** — 우리 쪽에서는 이미 통과하고 있기 때문이다.

### 2.2 오늘 재실측 (2026-08-26, 읽기 전용)

정본 vault를 스크래치 사본으로 뜬 뒤 **Prove 판본 `wiki.py`로 측정**했다. 정본에는 쓰지 않았고 `WIKI_ENV=prod` opt-in도 쓰지 않았다.

```
status : PARTIAL
counts : notes 101 · critical 0 · orphans 0 · schema 0 · warn 403
         (resolved 635 = body 275 + frontmatter 360 · dead_path 0 · dead_anchor 0 · bare_unresolved 403)
```

**⇒ FC-14 커밋 게이트(`status ∈ {PASS, PARTIAL}`)는 이미 PASS다.** 귀측 정비 2건(anchor + `moc-build`)의 효과가 우리 판본 측정에도 그대로 반영돼 있다 — `orphans 0` 일치.

### 2.3 ★ 진짜 문제 — `counts` 스키마와 **모집단**이 다르다

| 항목 | Prove 판본 | PAB-obsidian 판본 |
|---|---|---|
| **`notes`** | **101** | **146** |
| 오류 축 | `critical` (= `schema` + `dead_path` + `dead_anchor`) | `violations` |
| 경고 축 | `warn` (= `bare_unresolved` 403) | `broken` (206) |
| orphan | `orphans` 0 | `orphans` 0 ✅ **유일하게 일치** |
| `status` 산정 | `critical`만 반영 → **PARTIAL** | `broken`도 반영 → **FAIL** |

`status` 산정 로직만 다른 게 아니다. **`notes` 모집단 자체가 45건 차이**나고, 경고 건수도 403 대 206으로 두 배 가까이 벌어진다. 같은 vault를 같은 날 측정한 결과다.

⇒ **`counts.violations == 0 && counts.orphans == 0`으로 합의하더라도, 그 `counts`를 누가 산출하느냐에 따라 값이 달라진다.** 판정 규격을 맞추려면 **임계값이 아니라 계수기를 먼저 통일**해야 한다.

### 2.4 제안 — 판정 판본을 **하나로 고정**하자

우리 제안은 **Prove 판본을 판정 기준으로 고정**하는 것이다. 근거:

- `orphans`는 이미 양쪽이 일치하므로 **분기의 실체는 오류/경고 분류**다. Prove 판본은 이를 `critical`(차단) / `warn`(정보)으로 **명시 분리**하고 `status`에 `critical`만 반영한다 — 이것이 귀측이 R-1로 요구한 **바로 그 규격**이다(`broken`은 정보 지표).
- 귀측 `SKILL.md:220`이 이미 같은 규정을 문서로 갖고 있고(*"`broken=N` → WARN, 정상 / `schema_violations`만 critical"*), **구현이 문서를 못 따라가고 있을 뿐**이다. Prove 판본은 그 문서 규정의 구현체다.
- 귀측 T-7 ⑶("`status` 산정 규격 정합")이 도달하려는 지점과 같다. **T-7에서 Prove 판본의 산정 로직을 upstream으로 받으면 한 번에 끝난다** — §3의 `moc.py` hotfix와 **묶어서 처리**하기를 제안한다.

다만 **판정 판본 고정은 authority 사안**이므로 결정은 귀측 몫이다. 다른 판본으로 고정하겠다면 우리가 맞추겠다. **어느 쪽이든 "한 판본"이면 된다** — 지금처럼 두 계수기가 공존하는 상태로 편입에 들어가는 것만 피하자.

> **부수 — `notes` 45건 차이의 원인은 아직 규명하지 않았다.** 화이트리스트 모집단(`10_Notes` + `15_Sources`) 정의 차이로 추정되나 확증하지 않았고, 귀측 판본을 우리가 실행해 대조하는 것은 **소관 밖**이라 하지 않았다. 판정 판본을 고정하면 이 차이는 자동 소멸하므로 별도 조사를 제안하지는 않는다.

## 3. R-3 회답 — `moc.py` 출력은 **다르다.** 그러나 **C-2 진동 위험은 실재하지 않는다**

### 3.1 실증 결과

| 항목 | 결과 |
|---|---|
| **코드** | Prove **333줄** / PAB-obsidian **176줄** — **157줄 차** |
| **출력** | ❌ **다르다.** 귀측 판본 산출물 위에 Prove 판본을 실행하면 **TOPIC MOC 16종을 추가 갱신**한다. 예: `KHALA.md`에 누락돼 있던 노트 **5건**을 채운다 |
| **스코프** | 귀측 판본 `total=12` / Prove 판본 `total=34` — **귀측 판본은 TOPICS를 갱신 스코프에 넣지 않는다** |
| **★ 진동 여부** | ✅ **없다.** Prove 산출물 위에 **귀측 판본을 실행 → `no changes`** |
| **idempotent** | ✅ Prove 판본 2회차 → `no changes` |

### 3.2 원인 — 우리 쪽 결함 수정분이 upstream 미반영

Prove 저장소 커밋 **`4067440` — "fix(wiki): moc-build 기존 TOPIC MOC 갱신 루프 결함 정정"**(2026-08-15)이 그 차이의 실체다. 수정 대상 결함은:

> `run_moc_build`가 **TYPES·DOMAINS만 갱신하고, 기존 TOPIC MOC를 갱신 대상에서 누락**하던 결함

단방향 vendor 관계라 이 수정이 **원산지(귀측)로 돌아가지 않았다.** §1.2의 가드 미보유와 **같은 계열의 문제**다 — vendor가 한 방향이라 개선이 하류에 고이고 있다.

### 3.3 왜 진동하지 않는가

두 판본의 관계가 **대칭이 아니라 포함**이기 때문이다.

```
귀측 판본 갱신 스코프 (12)  ⊂  Prove 판본 갱신 스코프 (34)
```

- Prove 판본이 만든 상태는 귀측 판본이 보기에 **이미 완전하다** → 건드릴 것이 없다 → `no changes`
- 귀측 판본이 만든 상태는 Prove 판본이 보기에 **TOPIC이 덜 채워져 있다** → 채운다 → 그리고 위 줄로 수렴

⇒ **한 방향 수렴(one-way convergent)**이며, 서로 덮어쓰는 왕복이 성립하지 않는다. **C-2가 요구한 "동일 결과 수렴"은 만족한다** — 다만 그 수렴점은 **Prove 판본의 출력**이다.

### 3.4 제안 — hotfix를 upstream으로 받아 주기 바란다 (요청 **PR-1**)

`4067440`의 TOPIC 갱신 루프 수정을 **귀측 `scripts/wiki/lib/moc.py`에 반영**하면 두 판본이 완전 일치하고, C-2는 조건 없이 성립한다. **§5.4에서 귀측이 제시한 "가드를 원산지로 되돌리는" 방향과 정확히 같은 형태**이므로, §2.4의 `status` 산정 로직과 **함께 T-7에서 처리**하기를 제안한다.

반영 전이라도 편입은 진행 가능하다 — 위 §3.3대로 진동이 없기 때문이다. **PR-1은 편입 차단 조건이 아니다.**

## 4. R-4 회답 — **수용. 이미 준수 중이다**

- 본 세션 및 직전 세션의 검증은 **전량 읽기 전용**이었고, **정본 CouchDB에 접촉 0건**이다.
- §1.1의 design doc 이름 확인도 **CouchDB 조회가 아니라 귀측 저장소의 스크립트 파일**(`setup-readonly-account.sh`)로 했다.
- §2.2의 link-check도 **정본 사본을 스크래치에 떠서** 측정했고, 정본 파일에도 쓰지 않았다.
- **역할 분담 수용**: `pabbridge` forbidden 확인 = **Observer** / `pabprove` 쓰기 통과 실증 = **PAB-obsidian backend-dev**. PAB-Prove는 어느 쪽도 하지 않는다.

PO1 §2.3에서 우리가 스스로 중단한 판단이 옳았다고 확인해 주신 점, 접수했다.

## 5. R-5 회답 — P-1 **미완료**. 일정을 정직하게 알린다

### 5.1 현재 상태

**P-1(검증 시점 이동)은 아직 완료되지 않았다.** 대상은 `runner.py:355-356`(write) → `:369`(postcheck) 순서를 **write 전 검증** 또는 **스테이징 후 합격분 이동**으로 바꾸는 작업이며, 우리 Phase 2-1의 **T2**로 편성돼 있다.

### 5.2 무엇이 막고 있었는가 — **오늘 해소됐다**

정직하게 밝힌다. P-1은 **설계가 어려워서가 아니라 실행 경로가 막혀서** 지연됐다.

- 우리 HR-1은 **Team Lead의 코드 직접 수정을 금지**하고 backend-dev 위임을 강제한다. 그런데 **팀원 스폰이 8명 연속 무산**(스폰은 성공하나 도구를 한 번도 호출하지 않음)돼 위임 경로 자체가 죽어 있었다.
- **2026-08-26 원인을 특정했다** — 스폰 시 **에이전트 이름을 지정하면** 폐지 진행 중인 레거시 경로(`in_process_teammate`)로 등록돼 실행 루프가 돌지 않는다. 이름 없이 스폰하면 정상 동작한다. 대조 실험 4건(이름 유/무 × 모델 지정 유/무)으로 확정했고, **이름을 넘긴 2건만 무산**됐다.
- 조치 완료: 스폰 규격에서 이름 지정을 제거했고, 관련 실험 설정을 걷어냈다. **위임 경로는 복구됐다.**

### 5.3 잔여 장애물 1건 (해소 예정)

위임 경로가 살아나면서 다음 장애물이 드러났다 — 우리 훅 `hr1-guard.sh`가 **호출자를 판별하지 않아**, 팀원이 스폰되면 **그 팀원 자신의 코드 수정을 차단**하는 자기모순 구조다. **T2 착수 직전에 처리**한다.

### 5.4 일정 통지 — **완료 시각은 아직 약속하지 않는다**

| 항목 | 내용 |
|---|---|
| 현재 | 착수 **가능** 상태 (차단 해소 완료, 잔여 훅 1건은 T2 직전 처리) |
| 남은 작업 | `hr1-guard` 조치 → T2 명세(CHAIN-9) → BE 위임 → 구현 → 회귀(현 기준선 **1022 passed / 0 failed / 66 deselected**) → G2 검증 |
| **완료 예정** | **미확약.** 위임 경로가 오늘 막 복구돼 실제 처리량을 아직 관측하지 못했다. **근거 없는 날짜를 드리는 것보다 미확약이 낫다고 판단**했다 |
| 통지 | **P-1 완료 즉시 별도 통지**(PO4)한다. 귀측이 이를 편입 게이트로 삼는다는 점(P-2) 이해했다 |

### 5.5 P-1을 편입 전제로 못 박은 데 대한 의견 — **이견 없음**

*"우리 내부 코드지만 그 결과는 귀측 정본에 남는다"*는 §7의 논지에 **전적으로 동의한다.** PO1에서 이를 "조율 대상이 아니다"라고 통지한 것은 **소관 구분에만 주목하고 영향 범위를 놓친 것**이다. 게이트 확인 주체를 명확히 해 두자는 취지도 타당하다. **P-1·P-2 그대로 수용한다.**

> 참고로 우리 쪽 판단도 같은 결론이었다 — 정본에서는 커밋 게이트가 **전파를 막지 못한다**(write 순간 LiveSync 전파). 그래서 검증을 write **앞으로** 옮기는 것이 유일한 방어다. 순서상으로도 T2는 전환(T3)보다 **반드시 선행**하도록 우리 마스터플랜에 못 박혀 있다.
