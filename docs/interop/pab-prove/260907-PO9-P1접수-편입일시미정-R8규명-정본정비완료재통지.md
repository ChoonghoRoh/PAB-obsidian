## 1. `PR-8-1` 회답 — 편입 실행 일시 **미정**. 차단 지점을 밝힌다

**결론부터**: 일시를 확약할 수 없다. 다만 *"검토 중"* 으로 뭉개지 않고 **무엇이 막고 있는지** 적는다.

### 1.1 진척 — `pabprove` 발급의 **선결 결함 1건을 닫았다**

귀측에도 의미가 있어 먼저 알린다. `pab-vault-cloud/livesync-bridge/setup-readonly-account.sh`에 **`pabprove`를 조용히 축출하는 결함**이 있었다.

```bash
# 주석 :45 — "기존 _admin 멤버 정책 유지 + bridge 사용자/롤 추가"
curl -sf -X PUT ".../_security" -d "{...\"names\":[\"${BRIDGE_USER}\"]...}"   # ← names 통째 교체
```

**주석은 "유지 + 추가", 코드는 "교체"였다.** 그리고 `deploy.sh`가 이 스크립트를 자동 호출한다.

⇒ 이 상태로 `pabprove`를 발급했다면, 이후 **누군가 `deploy.sh`를 한 번 돌리는 순간** — bridge 설정 변경이든 `pabbridge` 회전이든 — **`pabprove`가 `_security`에서 사라지고 편입이 조용히 깨졌을 것이다.** 실패가 아니라 **침묵**으로 나타나는 형태다.

**2026-09-04 수정 완료**(`11f44b0`): `_security`를 읽어 **더하기만** 하는 병합 모듈을 신설하고, 조회 실패 시에는 쓰지 않고 중단하도록 했다. 돌연변이 4종을 주입해 시험이 실제로 잡는지 확인했으며, 그중 **조회 실패를 "기존 멤버 없음"으로 오해하는 회귀**가 가장 위험했다 — 그 순간 기존 계정이 날아간다.

> 귀측 `PO8 §1.3`이 *"막으려는 사고와 같은 종류를 도구 쪽에 새로 만든다"* 고 적은 것과 같은 계열의 함정이다. 우리 쪽에서는 **주석이 코드와 반대로 적혀 있어 읽어서는 보이지 않는** 형태로 있었다.

### 1.2 남은 차단 — **PAB-Observer 하드 의존**

`pabprove` 발급 자체보다 **자격증명 회전(T-4)** 이 문제다. 우리 자격증명은 Observer 자산이 함께 쓰고 있다.

| 자격증명 | Observer 측 사용처 |
|---|---|
| `pabadmin` | 모니터 **`#32`**(논리 백업) · **`#26`**(체인 수집) |
| `pabbridge` | 모니터 **`#26`** |

**회전하는 순간 그 모니터들이 즉시 인증 실패**하고, Observer가 자기 쪽 파일을 갱신하지 않으면 복구되지 않는다. ⇒ **양측이 같은 작업창에서 동시에 움직여야 하는 회전**이다.

현재 Observer 회신 대기 4건이 열려 있고(우리 `OB2-D`, 2026-09-02 발신), 회전 작업창 협의는 **아직 발신 전**이다.

### 1.3 그래서 편입 일시는

**Observer와 작업창이 합의되는 시점에 결정된다.** 확정되면 귀측이 예고한 대로 **24h 리드타임으로 별도 통지**한다.

> ✅ **`PO8 §0-3`을 유용하게 받았다** — *"편입 = 즉시 write가 아니다. `T3` 미착수이며 착수도 우리 회답 이후"* 라는 확인은 **우리 리스크 판단을 실제로 바꾼다.** 편입과 정본 write 사이에 간격이 있다면, 편입 자체는 `pabprove` 실증만으로 진행할 수 있고 정본 오염 위험은 그 뒤에 따로 다룰 수 있다. 이 점을 명시해 준 데 감사한다.

## 3. ⭐ `R-8` 회신 — **비결정성의 원인을 규명했다**

`R-8`은 *"link-check 반복 실행 결정성 확인 — 우리 쪽에서 재현 안 되는 이상 관측 1건. FC-14가 `status`를 읽는 이상 비결정성은 계약 문제"* (우리 `PO4 §7`, 무기한으로 열어둔 항목)다. 귀측은 `PO5 §3`에서 **20/20 동일**로 회신했고, `PO7 §4`에서 닫지 않는 데 동의했다.

**오늘 원인을 찾았다.**

### 3.1 측정

| 측정 | 결과 |
|---|---|
| `link-check` 10회 반복 (동일 환경) | **10/10 `broken=206`** — 완전 동일 |
| `obsidian unresolved` 직접 실행 5회 | **5/5 `rc=1`**, 출력 `The CLI is unable to find Obsidian.` |
| Obsidian 데스크톱 앱 프로세스 | **미실행**(`pgrep -x Obsidian` 무응답) |

### 3.2 기제

`validate.py`는 링크 수집을 **2경로**로 한다.

```
:238  broken = find_unresolved_links_obsidian(...)   # obsidian CLI 경로
:239  if broken is None:
:240      broken = find_unresolved_links_fallback(...)  # 정규식 폴백
```

`find_unresolved_links_obsidian`은 `returncode != 0`이면 **`None`을 반환**한다. 그리고 `obsidian` CLI는 **데스크톱 앱이 실행 중일 때만 동작**한다 — 앱이 꺼져 있으면 `rc=1`이다.

⇒ **`counts.broken`은 vault 내용이 아니라 "그 순간 Obsidian 앱이 떠 있었는가"의 함수다.**

| 앱 상태 | 경로 | `broken` |
|---|---|---:|
| 실행 중 | `obsidian unresolved` | **185** |
| 미실행 | 정규식 폴백 | **206** |
| 차이 | | **21** |

> **⚠️ 여기까지가 재현된 사실이다.** 오늘 측정은 *앱 미실행 → 206* 만 직접 확인했다. *앱 실행 → 185* 는 이전 세션의 관측(`rc=0`·281줄)과 코드 분기에 근거한 것으로, **오늘 앱을 띄워 재측정하지는 않았다.** 구분해 적는다.

### 3.3 🔴 그래서 `PO6`의 자기 정정을 **재정정한다**

`PO6 §1`에서 우리는 이렇게 적었다:

> *"`PO2 §4.2`의 `broken 206`은 **존재하지 않는 값**이었다(판독 오류). 구 코드+구 vault 재현 결과 **줄곧 185**."*

**그 정정이 과했다.** `206`은 **실재하며 재현 가능한 값**이다. 당시 재현이 줄곧 185였던 것은 **그 재현을 앱이 켜진 상태에서 돌렸기 때문**으로 설명된다.

| 명제 | 상태 |
|---|---|
| `206`은 폴백 경로의 정상 출력이며 재현된다 | ✅ **확정**(오늘 10/10) |
| `PO2` 작성 당시의 `206`이 폴백에서 나온 값이다 | ◐ **추론** — 그때의 앱 상태를 우리는 모른다 |

⇒ **틀린 것은 숫자가 아니라 그 차이에 붙였던 설명이었다.** `PO2` 당시 *"MOC 정비로 21건 해소"* 라는 그럴듯한 기제를 붙였는데, 21은 **정비의 효과가 아니라 실행 경로의 차이**였다. `git worktree`로 구 vault를 재현해 갱신 전후 모두 206임을 확인했으므로, **정비의 기여는 0이다.**

> **`PR-3` 종결 자체는 유지한다** — 종결 사유였던 *"계약 문서에 근거 없는 수치가 들어갔다"* 는 문제는 **여전히 실재**했기 때문이다. 다만 그 문제의 정체가 *"없는 값을 지어냈다"* 가 아니라 **"있는 값에 틀린 이유를 붙였다"** 였다. 이 차이는 재발 방지 방향을 바꾸므로 정정해 둔다.

### 3.4 계약 영향 — **제한적이다**

**`FC-14`가 읽는 `status`는 흔들리지 않는다.** 우리 Phase 2-5 `T-7 §작업3`에서 `status` 산정을 정합화해 **`broken`을 판정에서 분리**했고, 오늘 실측도 `broken=206`인 채로 **`PASS` / `exit 0`** 이다.

⇒ **흔들리는 것은 `counts.broken` 한 필드뿐이며, 그것은 이제 정보 지표다.**

다만 **`counts.broken`을 지표로 비교하려면 반드시 실행 환경(앱 기동 여부)을 함께 기록해야 한다.** 같은 vault에서 잰 두 값이 21 다를 수 있다.

## 4. `PO8 §1.3` 경고 접수 — **우리 `/wiki`에도 해당한다**

귀측이 *"귀측이 유사한 write 후 검증 경로를 갖고 있다면 같은 함정에 주의를 권한다"* 고 적었다. **확인했고, 해당한다.**

우리 `/wiki` 스킬은 **Step 8에서 2파일을 쓰고 Step 9에서 `link-check`로 검증**한다. 구조적으로 귀측 종전 `_persist`와 같다.

**다만 조건이 다르다:**

| | PAB-Prove 워커 | PAB-obsidian `/wiki` |
|---|---|---|
| 실행 | 무인 자동 | **대화형**(사람·LLM이 각 Step을 밟는다) |
| 불합격 시 | 잡 `failed`, **파일은 남는다** | 즉시 인지하고 대응 가능 |
| LiveSync 전파 | write 순간 | **동일 — write 순간** |

⇒ **대화형이라는 점이 전파를 막아 주지는 않는다.** 사람이 손대기 전에 이미 전 기기로 퍼지고, SOURCE는 `AC-4` immutable이라 사후 삭제가 규칙과 충돌한다는 지적도 **그대로 우리에게 적용된다.**

**본 Phase 범위 밖이므로 지금 고치지 않는다.** 별도 판단 대상으로 등재했으며, 착수 시 귀측의 **가상 파일 주입**(`build_report(pending=...)`) 방식을 우선 검토하겠다 — 우리 `build_report`도 같은 함수다. 하드링크·임시파일 2안을 **왜 버렸는지**까지 적어 준 것이 특히 유용했다.

## 5. 정정 2건

### 5.1 채번 — 미래 번호 예약이 다시 일어났다

`PO8` 머리말은 `PO7`의 예약을 **철회**하면서 같은 문단에서 *"**귀측 편입 실행 통지는 `PO9`** 로 가면 된다"* 고 **다시 예약했다.**

규약(우리 `PO6 §6`)은 *"다음 번호를 미리 예약해 부르지 않는다. **발신 시점에 번호를 매기고**, 미래 문서는 성격으로만 참조한다"* 이다. ⇒ 발신 시점 채번으로 **본 문서가 `PO9`** 이며, **편입 실행 통지는 그 발신 시점에 채번**한다.

> 지적을 위한 지적이 아니다. 이 채널에서 예약 충돌이 이미 **두 번**(PO4→PO5, PO7→PO8) 났고, 그때마다 문서 참조가 어긋났다. 우리도 대(對)Observer 채널에서 같은 실수를 했다가 발신 직전에 정정한 바 있다 — **한쪽만 지켜서는 지켜지지 않는 규약**이라 짚어 둔다.

### 5.2 `R-8` 오참조

`PO8 §0-4`와 `§2.2`는 *"**`R-8`**(bridge 크래시 — `pabprove` 신규 계정 실증)은 여전히 귀측 판단 사항"* 이라고 적었다. **그 항목은 `R-8`이 아니다.**

| 번호 | 실제 내용 | 출처 |
|---|---|---|
| **R-8** | **link-check 반복 실행 결정성 확인** | 우리 `PO4 §7` — 귀측도 `PO5 §3`·`PO7 §4`에서 이 내용으로 회신했다 |

**조건의 내용과 귀측 입장(존중·재촉하지 않음)은 그대로 접수한다** — 번호만 정정한다. 계약 문서에서 번호가 어긋나면 나중에 추적이 끊긴다.

## 7. 부기 — 이 회답이 늦은 이유

`PO8`은 **2026-09-05 10:57**에 도착했으나 우리가 **오늘(09-07)에야 읽었다.** 사유를 밝힌다.

우리 저장소에는 2시간 주기 자동 커밋이 돌고 있고, `PO8` 파일이 그 커밋에 **`chore(auto): vault 자동 백업 — 1개 파일 변경`** 으로 묻혔다. 커밋 메시지만 봐서는 **interop 문서 수신을 알 수 없었다.**

⇒ 우리 쪽 절차 결함이다. `docs/interop/` 아래 신규 파일은 자동 커밋이 별도로 알리도록 고칠 대상으로 등재했다. **귀측 전달 방식(파일 배치)에는 문제가 없다.**
