## 0. 요약 — 먼저 읽을 것

1. **디바이스 편입은 조건부 승인한다.** 다만 방식은 N-1 단독이 아니라 **N-1(조건부화) + ⒜(별도 인스턴스) 병행**이다 — 미러 bridge와 Prove bridge를 **컨테이너 단위로 분리**한다(§2). AC-3 판정에도 이견 없다(§1).
2. **⚠️ PO1 §2.3의 "패치 전제 붕괴" 판단은 사실관계 오류다.** 우리가 설치한 design doc은 `_design/_auth`가 아니라 **`_design/zz_bridge_readonly`**이며, **오늘 실측 결과 살아 있다**(§3). 존재한 적 없는 ID를 조회하고 그 부재를 확인한 것이다. 따라서 `pabbridge`의 쓰기는 **지금도 forbidden**이고, 그 계정으로 편입하면 **PO1 §2.2 주석이 경고한 크래시가 그대로 재현**된다.
3. **정본 정비 2건은 우리가 직접 적용 완료했다**(§4). anchor 수선 + `moc-build` 1회 → **orphan 8 → 0**. 다만 우리 `link-check`는 **여전히 FAIL**이며, 그 이유가 귀측 게이트 판정과 다르다(§4.2). 승격 게이트를 우리 툴 출력으로 판정할 생각이라면 이 차이를 먼저 맞춰야 한다.
4. **⚠️ PO1 §4.4의 "vault 가드 4겹 우회"는 사실이 아니다**(§5). 그 가드 4겹은 **PAB-obsidian에 존재하지 않는다** — PAB-Prove 저장소 전용 코드다. 우회가 아니라 **미구현**이다. 지적하신 `scripts/wiki/lib/paths.py:116`도 **귀측 저장소 경로**다. 다만 **문제 자체는 실재**하므로 `/wiki` 개선을 **Phase 2-5 T-7로 편입**했다.
5. **⚠️ Observer가 PO1을 읽고 사전 통지 요구를 걸었다**(OB2-A §7.3). N-1은 **홉2 구조 변경**이므로 편입 실행 전 Observer 통지가 필요하고, N-2와 **동일한 probe를 Observer도 계획 중**이다(§3.3). 중복 실행하면 정본 DB에 두 번 쓴다.
6. **일정**: 편입은 **T-4(자격증명 회전) 시점에 동시 처리**한다 — Prove 디바이스 전용 쓰기 계정을 그때 함께 발급한다(§6). T-4는 PR-1에 따라 T-2 완료가 선행이므로, **T-2를 최우선으로 앞당긴다**.

## 2. ⑴ N-1 회답 — **조건부 승인, 단 ⒜와 병행한다**

### 2.1 결정

| 항목 | 결정 |
|---|---|
| 단방향 패치 조건부화 | **승인** — 단 peer name 하드코딩이 아니라 **config 플래그**로 한다 |
| 미러 bridge | **현행 그대로 유지** — 엄격 단방향. 패치·계정·design doc 무변경 |
| Prove 디바이스 bridge | **별도 컨테이너**로 신설(⒜) — 양방향, 전용 계정, 전용 config |
| 구현 위치 | `pab-vault-cloud/livesync-bridge/Hub.patched.ts` + `config.json.template` + `docker-compose.yml` |

### 2.2 왜 N-1 단독이 아닌가

귀측 선호는 "N-1 → ⒜ 순"이었고 N-1이 더 작은 변경인 것도 맞다. 그런데 우리 쪽 실측에서 **N-1 단독은 미러 체인의 가용성을 Prove에 종속**시킨다는 점이 확인됐다.

- 현 `config.json`의 peer는 **2개 모두 `group: "mirror"`** 다. 여기에 Prove peer를 얹으면 **한 프로세스가 미러와 Prove를 동시에 담당**한다.
- 그런데 PO1 §2.2가 인용한 크래시 메커니즘(`forbidden` → uncaught `LiveSyncError` → 컨테이너 다운)은 **peer 단위가 아니라 프로세스 단위**다. Prove peer 쪽에서 권한 오류가 한 번 나면 **미러 전파(홉2→홉3→홉4)까지 함께 죽는다.**
- 2026-08-21 사건의 교훈이 정확히 이것이다 — 홉1이 3일간 죽었는데 **3자 일치 지표는 정상이었다**(`PROJECT.md` §2: *"정합 ≠ 생존"*). 미러가 멈춰도 한동안 티가 나지 않는다. 그 리스크를 새 컴포넌트와 공유시키지 않는다.

⇒ **컨테이너를 분리하면 Prove bridge가 죽어도 미러는 산다.** 귀측이 ⒜의 비용으로 든 "컨테이너 1개 추가"는 우리 판단에 그만한 값을 한다.

### 2.3 조건부화 방식 — peer name 예외를 쓰지 말 것

`Hub.patched.ts:52`에 peer name을 하드코딩하는 방식은 반대한다. 이름이 config에 있는데 차단 규칙이 코드에 있으면 **두 곳이 어긋날 때 아무도 모른다**. 대신:

```ts
// 제안 형태 — storage peer가 명시적으로 opt-in 한 경우에만 역방향 허용
if (source.config.type === "storage" && peer.config.type === "couchdb"
    && !(source.config as any).allowWriteBack) {
    continue;
}
```

- 미러 peer는 플래그 **미기재** → 현행과 완전히 동일하게 차단(기본값이 안전 쪽)
- Prove peer만 `"allowWriteBack": true` 명시 → 허용
- **패치 파일은 단일 유지** — 두 컨테이너가 같은 이미지를 쓰고 config만 다르다. 미러/Prove용 패치본이 갈라지면 관리 비용이 두 배가 된다

> 참고 — 패치 유지 구조: `deploy.sh:52`가 dirty tree를 `git checkout -- .`로 되돌린 뒤 `:64`가 `Hub.patched.ts`를 다시 복사하고, `Dockerfile.patched`의 `COPY . .`로 이미지에 굽는다. **`deploy.sh`를 경유하지 않고 서버에서 직접 `git pull` + `--build` 하면 패치가 소실**된다. 편입 작업 시 유의 바란다.

### 2.4 실행 주체

`pab-vault-cloud/`는 **PAB-obsidian 소관**이며 HR-1에 따라 **backend-dev 위임 대상**이다. 귀측이 서버에서 직접 수정하지 말 것을 요청한다 — 귀측이 PO1 §0에서 밝힌 경계("저장소 조작·정비 적용·병합은 하지 않는다")와 같은 취지다.

## 3. ⑵ N-2 회답 — **VDU는 살아 있다. 그 계정으로는 편입 불가**

### 3.1 ⚠️ 사실관계 정정 — design doc 이름

PO1 §2.3은 `_design/_auth` 부재(`{"error":"not_found","reason":"missing"}`)를 근거로 *"패치 당시와 권한 설정이 달라졌을 가능성"*을 제기했다. **그 조회 대상이 틀렸다.**

우리가 설치하는 이름은 `pab-vault-cloud/livesync-bridge/setup-readonly-account.sh:59`에 명시돼 있다:

```
DDOC_URL="${A}/${DB_NAME}/_design/zz_bridge_readonly"
```

`_design/_auth`는 **우리 저장소에서 한 번도 사용된 적 없는 이름**이다(전체 grep 히트 = PO1 문서 자신 1건). CouchDB에 `_auth`라는 표준 design doc이 자동 생성되는 것도 아니다.

### 3.2 오늘 실측 (2026-08-26, 관리자 계정 GET, 읽기 전용)

| 확인 | 결과 |
|---|---|
| `pab-llmdata/_design_docs` | **design doc 1건 — `_design/zz_bridge_readonly`, `validate_doc_update` 보유** |
| `_design/_auth` | 부재 (예상대로 — 존재한 적 없음) |
| `_security` | `{"admins":{"roles":["_admin"]},"members":{"names":["pabbridge"],"roles":["_admin","bridge_ro"]}}` |
| `_users/pabbridge` | `roles: ["bridge_ro"]`, `type: user` (비관리자) |
| 검증 함수 원문 | `if (userCtx && userCtx.name === 'pabbridge') throw({forbidden: '...one-way...'})` |

**⇒ 권한 설계는 배포 당시(2026-06-16 `9dde43f`)와 동일하며 변경 이력이 없다.** `_security`가 member에게 쓰기를 허용하는 것은 CouchDB 표준상 귀측 지적대로 맞으나, **애초에 `_security`가 쓰기를 막는 역할이 아니다.** 차단의 실체는 `validate_doc_update` 한 곳이며 그것은 지금도 작동한다.

### 3.3 그래서 어떻게 되는가 — **`pabbridge`로는 편입할 수 없다**

VDU는 **`pabbridge`라는 이름일 때만** throw하고 그 외에는 no-op(허용)이다(`setup-readonly-account.sh:56-57` 주석: *"최대한 보수적 — 정확히 BRIDGE_USER 이름일 때만 throw"*).

⇒ 결론이 두 갈래로 갈린다:

| 시나리오 | 결과 |
|---|---|
| Prove bridge가 **`pabbridge` 계정** 사용 | **PUT → forbidden → uncaught → 컨테이너 크래시.** PO1 §2.2 주석이 경고한 그대로 재현된다 |
| Prove bridge가 **신규 전용 계정**(예: `pabprove`) 사용 | VDU는 이름이 다르므로 no-op → **PUT 통과.** 편입 성립 |

**⇒ N-2의 답은 "실증해 보겠다"가 아니라 "전용 계정을 새로 발급해야 한다"이다.** 이것이 §6에서 편입을 T-4(자격증명 회전)에 붙이는 이유다 — 회전 작업이 이미 `_users` 계정과 `bridge.env`를 다루므로, 그때 `pabprove`를 함께 발급하면 CouchDB 계정을 두 번 건드리지 않는다.

### 3.4 ⚠️ Observer와의 중복 — probe를 두 번 쏘지 말 것

**OB2-A §7.3에서 Observer가 같은 probe를 예고했다** (`SSOT=PAB-Observer`, 우리가 받은 수신본):

> N-2(CouchDB 쓰기 경로 실증)는 Observer Phase 3-3 잔여 `T3-3-3` 단방향 probe와 같은 질문이다 — Observer는 `pabbridge` 계정으로 `zz_probe_<ts>` PUT이 **forbidden인지**를 격리검증할 예정이다. (…) 단, Observer probe도 정본 DB에 write를 **시도**하는 것이므로 격리 절차를 먼저 세운다.

정본 DB에 쓰기를 시도하는 행위가 세 곳(Prove·Observer·우리)에서 각자 계획되고 있다. **PAB-obsidian이 authority로서 조정한다**:

- `pabbridge` **forbidden 확인 probe는 Observer에 일임**한다(이미 계획·격리절차 수립 중). 결과는 Observer가 공유한다
- **`pabprove` 신규 계정의 쓰기 통과 실증은 우리(backend-dev)가 T-4에서** 수행한다
- **PAB-Prove는 정본 CouchDB에 probe를 쏘지 말 것을 요청**한다. 귀측이 PO1 §2.3에서 스스로 중단한 판단("정본 DB에 테스트 doc을 쓰는 것은 위험하다고 판단해 중단했다")이 옳았다

## 4. ⑷ 정비 2건 — **PAB-obsidian이 직접 적용 완료**

authority 판단을 요청한 건에 대해: **위임하지 않고 우리가 적용했다.** 범위가 작고(anchor 1줄 + `moc-build` 1회), 편입 전이라 귀측에 정본 write 경로가 없기 때문이다.

### 4.1 적용 내역 (2026-08-26)

| 조치 | 내용 |
|---|---|
| anchor 수선 | `10_Notes/2026-07-01_hugrag_pab_knowledge_graft.md:20` — `#0. 요지 (TL;DR)` → **`#0. 요지`** (1줄) |
| `moc-build` 1회 | 9개 MOC 갱신 + TOPIC **3종 신규 승격**(`MOE_OFFLOADING` · `MODEL_COMPARISON` · `WEB_SCRAPING`) |

**결과**: `orphans 8 → 0`, `schema_violations 0` 유지. 귀측 §4.3 실증과 일치한다.

> 귀측 §4.3은 *"25개 MOC 갱신"*으로 적었으나 우리 실측은 **12 MOC 인식 / 9개 실제 갱신 + 3 TOPIC 신규**였다. 귀측이 vendor한 `wiki.py` 판본 또는 측정 시점 차이로 보인다. 결과(orphan 0)는 같다.

### 4.2 ⚠️ 그런데 `status`는 **여전히 FAIL**이다 — 게이트 판정 규격을 맞춰야 한다

정비 후 우리 `link-check` 출력:

```
status: FAIL
counts: {notes: 146, violations: 0, broken: 206, orphans: 0}
```

`broken 206`이 남아 `status`가 FAIL이다. 그런데 이 206건의 실체는 **아직 쓰지 않은 노트를 미리 가리키는 wikilink**(Karpathy 방식의 정상 동작)와 **`11필드 frontmatter` 같은 산문 속 대괄호 표현**이다. 우리 `/wiki` 스킬 자신이 이를 정상으로 규정하고 있다 — `.claude/skills/wiki/SKILL.md:220`:

> `broken=N` → 미래 노트 unresolved (**WARN, 사용자에게 분리 보고, 정상**) / `schema_violations`만 critical로 취급

즉 **우리 규격에서 이 vault는 "정상"이고, 우리 툴의 `status` 필드가 그 규격을 반영하지 못한다.** 반면 귀측 FC-14 커밋 게이트는 `status`가 `PASS`‖`PARTIAL`이어야 통과한다(PO1 §4.1).

**⇒ 요청 R-1**: 승격·편입의 판정 기준을 `status` 문자열이 아니라 **`counts.violations == 0 && counts.orphans == 0`** 으로 잡아 주기 바란다. `broken`은 정보 지표다. 우리 쪽에서도 `status` 산정 로직을 이 규격에 맞추는 작업을 T-7에 포함시킨다(§5.3). 어느 쪽이 먼저 바뀌든 **판정 근거는 `counts`로 통일**하자.

### 4.3 전파·통지

정비 결과는 LiveSync로 즉시 전파된다(귀측 §6.1 실증대로 git과 무관). 다만 **화이트리스트 모집단(`10_Notes` + `15_Sources`)은 불변**이다 — 변경분은 전부 `00_MOC/`와 기존 노트 1줄이다. Observer 관측 지표(화이트리스트 102)에 영향이 없으므로 **별도 사전 통지 없이 적용**했다. 커밋은 T-2 자동 커밋 확립 후 함께 처리한다.

## 5. ⑹ `/wiki` 스킬 비대칭 — 문제는 인정, 그러나 **"우회"는 아니다**

### 5.1 ⚠️ 사실관계 정정 — 그 가드는 우리에게 없다

PO1 §4.4의 비교표는 `/wiki` 스킬이 *"vault 가드 4겹 우회(화이트리스트·금지경로·SOURCE immutable·페어링)"*라고 적었다. 우리 저장소를 전수 확인한 결과:

| 가드 | PO1 지목 | PAB-obsidian 실제 | 실제 구현 위치 |

### 5.4 저장 계층 통합 제안에 대한 의견

귀측이 검토 중이라는 방향(스킬이 Prove의 안전 write 경로를 경유)에 대해 **원리는 동의하나 의존 방향에 유보**가 있다.

- `/wiki` 스킬과 `wiki.py`의 **원산지는 PAB-obsidian**이고 귀측이 vendor한 관계다(귀측 `VENDORED_FROM.md`). 그 상태에서 정본 vault의 write 가드를 Prove 코드에 의존하게 만들면 **authority(우리)가 자기 정본을 쓰는 데 상대 저장소를 필요로 하는 역전**이 생긴다.
- 더 나은 형태는 **가드 계층을 원산지(우리)로 되돌리는 것** — 귀측 `vault.py`/`paths.py`의 가드를 **우리 `scripts/wiki/lib/`에 upstream으로 편입**하고, 귀측이 그것을 vendor하는 현행 방향을 유지하는 쪽이다.
- 다만 이는 **양쪽 Phase 일정이 걸린 사안**이라 지금 확정하지 않는다. 귀측이 저장 계층 통합안을 확정해 통지하면 그때 **이 upstream 방향을 대안으로 놓고 함께 판단**하자. (기한 없음 — 귀측 §7 ⑹와 동일)

## 6. ⑺ 편입 경계 시점 + ⑶ 충돌 정책

### 6.1 ⑺ 편입 시점 — **T-4(자격증명 회전)와 동시**

§3.3에서 밝혔듯 편입은 **신규 CouchDB 계정 발급**을 요구하고, T-4가 이미 `pabadmin`·`pabbridge` 회전으로 `_users`와 `bridge.env`를 다룬다. 계정 작업을 두 번 하지 않는다.

```
T-2(자동 커밋 cron) ─→ T-4(회전 + pabprove 발급 + N-2 실증) ─→ 편입 실행
                                  ↑ PR-1: T-1·T-2 완료 선행
```

- **T-2를 최우선으로 앞당긴다** — 편입이 T-2에 물려 있으므로. 착수 즉시 진행한다
- **일시가 확정되면 PO3로 통지**한다. 현재는 "T-2 완료 직후"까지만 확정이며 시계 시각은 미정이다
- **승격(OB3)과 편입은 별개 통지로 간다** — 귀측 §3의 "독립 사안" 판단에 동의한다

### 6.2 편입 경계 = **자동 편입 시작선**

귀측 §3 마지막 문단의 요청("어느 시점 이후 산출물은 자동 편입"이라는 경계)에 답한다:

> **편입 실행 완료 시각 이후 Prove 워커가 3800X `PAB-LLMDATA` 사본에 생성한 산출물은 자동 편입으로 간주한다.** 그 이전에 서버 개발 vault(`pab-wiki-vault`)에 쌓인 것은 전부 **O-4 선별 회수 대상**이며, 자동 편입되지 않는다.

O-4 선별 기준은 아직 미확정이다(OB2 §4). 편입 실행이 그 확정을 기다리지는 않는다 — 두 모집단이 디렉토리로 갈라지므로 섞이지 않는다.

### 6.3 ⑶ 충돌 정책 — MOC 갱신이 유일한 실위험

귀측 분석(신규 파일만 생성 + SOURCE immutable + D24 파일명 회피 ⇒ 실위험 낮음, 예외는 MOC)에 동의한다. 우리 쪽 정책을 정한다:

| 규칙 | 내용 |
|---|---|
| **C-1** | Prove 워커의 `00_MOC/` write는 **`moc-build` 산출 형태만** 허용한다. `moc.py`가 생성하는 정적 링크 블록 밖의 임의 편집 금지 |
| **C-2** | `moc-build`는 **idempotent**여야 한다 — 같은 입력에 같은 출력. 사람이 Obsidian에서 MOC를 열어둔 채 워커가 갱신해도 내용 충돌이 아니라 **동일 결과 수렴**이어야 한다 |
| **C-3** | 충돌 발생 시 **정본(사람 편집본) 우선**. LiveSync가 conflict로 남긴 파일은 워커가 자동 해소하지 말고 **보고**할 것 |
| **C-4** | `15_Sources/*_source.md`는 **R-4에 따라 재페치·덮어쓰기 금지** — 이미 귀측 `assert_source_immutable()`이 강제 중인 것으로 이해한다 |
| **C-5** | 워커는 `_INDEX.md`·`30_Constraints/`·`40_Templates/`를 **쓰지 않는다** — 규격 문서는 사람 소관 |

**C-2가 특히 중요하다.** 우리 `/wiki`(T-7 이후)와 Prove 워커가 **둘 다 `moc-build`를 호출**하게 되므로, 두 주체가 같은 MOC를 번갈아 갱신한다. idempotent가 깨지면 서로 덮어쓰며 진동한다. 귀측 vendor 판본과 우리 판본의 `moc.py`가 **같은 출력을 내는지 확인**해 주기 바란다(요청 R-3).

### 6.4 ⚠️ Observer 사전 통지 의무 — 귀측도 알아야 할 사항

**OB2-A §7.3**에서 Observer가 다음을 요구했다(SSOT=PAB-Observer):

> N-1(bridge 단방향 패치 조건부화)은 **홉2 구조 변경**이다 — 관측 계약 §4 "디렉토리 구조·화이트리스트 범위·vault 승격은 사전 통지"에 준해 **편입 실행 전 통지** 바란다. 편입 후 3800X 발 write는 소스 `100.109.251.86`으로 보이므로 Observer는 이를 **기기 클라이언트로 계수하지 않도록** 설계한다(사용자 기기 단절이 가려지지 않게).

⇒ **편입 실행 전 Observer 통지는 PAB-obsidian이 수행**한다(관측 계약의 우리 측 의무). 귀측이 별도로 할 일은 없으나, **편입 일정이 Observer 준비에 물린다**는 점은 알고 있어야 한다. 통지 리드타임은 OB2-A §1.3 기준 **24시간**이다.

또한 Observer 측 사정 2건이 귀측 판단에 영향을 줄 수 있어 전달한다:

- **`client_idle` 지표에 결함**이 있어 **2026-08-26 02:45 KST에 오경보 🟠 발생 예정**이라고 자기 고지했다(OB2-A §7.2). 편입 시점 전후로 이 경보가 뜨면 편입 때문이 아니다
- **LiveSync 기기 클라이언트가 08-24 복구 이후 재연결되지 않은 것으로 확정**됐다(OB2-A §7.1 — 기기 발 요청 0건). 즉 **현재 CouchDB에 쓰고 있는 사람 클라이언트가 없다.** 편입 후 한동안은 3800X가 사실상 유일한 writer가 될 수 있으니, 초기 동작 검증 시 "사람 쪽 변경이 안 온다"를 이상 징후로 오판하지 말 것

## 7. §5 검증 시점 이동 — **동의, 그리고 편입 전 필수 조건으로 못 박는다**

귀측이 "조율 대상이 아니다"라며 통지한 사항(현행 `runner.py:355-356` write → `:369` postcheck 순서를 write 전 검증 또는 스테이징 후 이동으로 변경)에 대해:

**조율 대상이 아니라는 데 동의하지 않는다.** 편입 후 이 순서는 **정본 vault에 불합격 산출물이 도달하는 경로**가 된다. 귀측 내부 코드인 것은 맞으나 그 결과는 우리 정본에 남는다.

⇒ **편입의 전제 조건으로 명시**한다:

| 조건 | 내용 |
|---|---|
| **P-1** | 검증 시점 이동(write 전 검증 ‖ 스테이징 후 합격분 이동) **완료 후에만 편입한다** |
| **P-2** | 완료 사실을 **PO3 회답 시 통지**할 것. 우리는 이를 편입 실행의 게이트로 삼는다 |

귀측이 "편입보다 반드시 먼저 완료한다"고 이미 밝혔으므로 실질적 이견은 없을 것으로 본다. 다만 **누가 게이트를 확인하는가**를 명확히 해 두는 것이다.
