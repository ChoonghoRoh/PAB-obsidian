# 회원 데이터 룰 — 소유 규정 (v4 정본)

> **지위**: **PAB-v4 가 원본인 문서**다. 연계 프로젝트(PAB-Prove · PAB-Khala · PAB-Obsidian 외)는 **수신본**으로 보관하고 **수정하지 않는다.** 갱신은 v4 가 재전달한다.
> **결정**: 사용자, 2026-09-16 · **작성**: PAB-v4
> **적용**: 즉시. 이미 만들어져 돌고 있는 것도 이 규정에 따라 정합을 맞춘다.

---

## 1. 원칙

> **회원과 관련된 모든 데이터 룰은 PAB-v4 가 소유하고 책임진다.**
> **연계 프로젝트는 v4 의 룰을 따르며, 각자의 룰을 만들지 않는다.**
> **새 룰이 필요하면 만들지 말고 v4 에 문의한다.**

⚠ **예외**: 그 프로젝트 **내부에서만 닫히는 로직**은 각자 판단으로 쓴다(§3).

---

## 2. 왜 이 규정이 필요한가 — 관측된 사실

같은 대상에 **양쪽이 각자 룰을 갖고 있으면, 어긋나도 아무도 모른다.** 실제로 그랬다.

| 사례 | 형태 |
|---|---|
| **vault 경로** | v4 는 `provision_root / vault_id` 로 만들고 Prove 는 자기 env 로 조립했다. 두 값이 **우연히 같아서** 문제가 없었을 뿐, 어느 쪽도 상대 값을 확인하지 않았다 |
| **`vault_id` 발급** | v4 가 admin 계정에 `"vault-mirror"` 를 내줬고 Prove 는 규격대로 거절했다. **거절이 옳게 동작했지만**, 값이 왜 그런지는 양쪽 다 몰랐다 |
| **회원 식별** | v4 의 SSO `client_id` 는 **앱 식별자**인데 회원 식별자로 읽힐 수 있는 형태였다. 두 축이 문서에 나란히 있으면 반드시 섞인다 |

🔑 **셋 다 「누가 정하는가」가 안 적혀 있어서 생긴 일이다.** 값이 틀린 게 아니라 **주인이 없었다.**

---

## 3. 경계 — 무엇이 「연계」이고 무엇이 「내부」인가

| | 판정 기준 | 소유 |
|---|---|:-:|
| **연계** | 두 시스템이 **같은 값을 공유**하거나, 한쪽의 판단이 **다른 쪽의 회원 데이터에 영향**을 준다 | 🔴 **v4** |
| **내부** | 그 시스템 안에서 **닫힌다**. 밖에서 관측되지 않고 회원 귀속을 바꾸지 않는다 | 각자 |

### 예시

| 대상 | 판정 |
|---|:-:|
| 회원 vault 의 **경로·식별자 규칙** | 연계 → v4 |
| **회원 식별자**(누구의 데이터인가) | 연계 → v4 |
| 회원 데이터 **조회 스코프**(누구 것을 읽는가) | 연계 → v4 |
| **인증·위임** 형식(대리 조회 포함) | 연계 → v4 |
| 회원 **생성·삭제·비활성**의 파급 | 연계 → v4 |
| vault **표시명** 규칙 | 연계 → v4 |
| 워커 큐·재시도·동시성 제어 | 내부 → 각자 |
| 어떤 모델을 쓰는가, 프롬프트 구성 | 내부 → 각자 |
| 자체 캐시·로그 포맷·내부 지표 | 내부 → 각자 |

⚠ **애매하면 연계로 본다.** 판단이 갈리는 순간 그것은 이미 공유되는 값이다.

---

## 4. 절차

1. **새 룰이 필요하다고 느끼면 만들지 말고 v4 에 문의한다.** 회신 전까지는 **동작을 멈추거나 실패로 끝내고**, 그럴듯한 기본값으로 진행하지 않는다.
2. v4 는 룰을 정해 **이 문서를 갱신하고 재전달**한다.
3. 연계 프로젝트는 수신본을 보관만 하고 **고치지 않는다.**
4. 이미 만든 자체 룰이 있으면 **폐기 대상이 아니라 문의 대상**이다 — v4 가 흡수할지 대체할지 정한다.

⭐ **자동 생성·자동 폴백을 금지한다.** 값이 없거나 규격에 안 맞으면 **실패로 끝낸다.** 그럴듯한 값을 만들어 이어가면 오류가 조용해지고, 그 침묵이 이 규정이 막으려는 것이다.

| **R-6** | **대리 조회(on-behalf-of)의 형식은 v4 가 정한다.** 연계 측은 v4 가 발급한 것을 **운반만** 하고, 신원을 스스로 주장하지 않는다 | ✅ **형식 확정**(2026-09-17) · §5.8 |

| **R-8** | **회원 삭제·비활성의 파급 범위** · 🔴 **`vault_id` 교체 시 「경로 변경」과 「구 경로 처리」를 함께 정한다** | 🔴 **미정** |
| **R-9** | **회원 본인 쓰기 ↔ 시스템 쓰기의 충돌 처리** — 같은 노트를 양쪽이 고쳤을 때 무엇이 남는가 | ⚠ **부분 확정** — §5.4 |
| **R-10** | 🔴 **wiki 문서의 「편집·수정·삭제」 사용자 엔드 컨트롤 지점은 Obsidian app 하나다.** v4 는 읽기만 하고 편집 UI 를 제공하지 않는다 | ✅ **확정** · §5.5 |
| **R-11** | **MOC 분류 체계의 소유는 Obsidian 규정이다.** Prove 의 **신규 분류 생성 + 진입은 확장 계층(TOPICS)에만** 해당하고, **고정 어휘 계층(TYPES·DOMAINS)은 늘리지 않는다**(늘리는 것은 분류 추가가 아니라 **규격 변경**이다). **기존 분류의 수정도 하지 않는다** | ✅ **확정** · §5.5 |
| **R-12** | 🔴 **자동 생성 구간의 경계 표식(마커) 문자열은 양측 공통 계약이다.** 한쪽만 바꾸면 상대 도구에는 **「마커 없음」으로 보여 그 파일이 조용히 사람 영역으로 넘어간다** — 실패가 에러가 아니라 **소유권 이동**으로 나타난다. 변경은 **사전 통지 + 동시 적용** | ✅ **확정** · §5.4 |
| **R-13** | 🔴 **조회 스코프는 「요청자 본인의 지식」뿐이다.** 팀·공유·구입·공통·개방 등 확장 형태는 **미정**이며, 정해질 때까지 연계 측은 **본인 외 범위를 열지 않는다.** ⚠ **접근 범위를 토큰·세션에 굽지 않는다 — 조회 시점에 판정한다** | ✅ **확정**(현재 값) · §5.7 |

⚠ **R-6~R-9 는 「아직 없음」이지 「각자 정하라」가 아니다.** 필요해지면 §4 절차로 문의한다.

### 5.1 R-1 보충 — 소유·전달·검증을 가른다

| 층 | 누가 |
|---|---|
| 값을 **정한다** | 🔴 **v4** — 위 표에 명기한다. 변경은 §7 대로 **사전 통지** |
| 값을 **운반한다** | **각자의 배포 구성**(환경변수 등). 🔴 **런타임 원격 수신이 아니다** |
| 값이 **같은지 본다** | **각 프로젝트의 배포·기동 게이트** — 자기 구성값이 위 명기값과 다르면 **fail-closed 로 멈춘다** |

⚠ **베이스 경로를 런타임에 내려받게 하지 않는다.** 그렇게 하면 연계 측의 경로 가드(containment·심링크 거부)가 **「베이스는 자기 것」이라는 전제**를 잃어 전부 무의미해지고, **운영 writer 가 여는 경로를 원격이 정하게** 된다. R-4 가 지키려는 것과 같은 자리다.
⭐ **이 배치가 §2 의 «우연히 같을 뿐 아무도 확인하지 않는다»를 닫는다** — 「우연히 같다」가 **「확인된 같다」**가 된다.

**`vault_id` 의 형식**(`"v" + token_hex(16)`)은 **v4 가 만들고 v4 가 검증한다.** 연계 측은 그 형식 검사를 **자기 코드에 복제하지 않는다** — 복제하면 v4 가 형식을 바꿀 때 연계 측이 **유효한 id 를 거절**하게 되고, 그것이 §2 가 말한 「각자 룰」의 정확한 형태다.
⇒ 연계 측에게 `vault_id` 는 **불투명한 값**이다. 연계 측의 책임은 **그 값이 자기 베이스를 벗어나지 못하게 하는 것**까지다(경로 탈출·심링크·예약어 방어).

### 5.2 R-5 보충 — 「스코프를 넓힌다」의 뜻

R-5 가 금지하는 것은 **자기 역할 범위를 넘어 회원 데이터를 보는 것**이다.

| | 판정 |
|---|:-:|
| 자기 역할을 수행하려고 **그 대상 회원의 vault 하나**를 읽는 것(예: 수집 시 중복 검사) | ✅ **저촉 아님** — 내부 |
| 여러 회원 데이터를 **가로질러** 보거나, 자기 역할 밖(열람·검색 제공 등)으로 읽는 것 | 🔴 **저촉** |

⚠ 애매하면 **v4 에 선언**한다. 선언된 읽기는 감사에서 발견되는 것보다 낫고, 저촉 판정은 v4 가 한다.

### 5.3 R-4 보충 — 「writer」는 시스템 측만 센다

R-4 의 취지는 **시스템이 회원 vault 에 여러 경로로 쓰지 않는다**는 것이다. **회원 본인은 자기 데이터의 주인이고 writer 수에 포함되지 않는다.**

| 주체 | R-4 대상 |
|---|:-:|
| Prove 워커 | ✅ **대상** — 시스템 측 유일 writer |
| rsync | ✅ 대상 — **개발 전용 창구**이며 운영에서 쓰지 않는다 |
| **회원 본인**(Obsidian·WebDAV 등으로 자기 vault 에 직접 쓰기) | ⛔ **대상 아님** |

🔴 **따라서 쓰기 주체는 실제로 둘이고 충돌이 발생할 수 있다** — Prove 가 만든 노트를 회원이 고쳐 둔 상태에서 Prove 가 같은 노트를 갱신하면 한쪽이 덮인다.
⇒ 그 처리 규칙이 **R-9 이고 아직 미정**이다. **연계 측은 충돌 해결 규칙을 스스로 만들지 않는다** — 동기화 도구가 제공하는 기본 동작(예: 「더 최신/더 큰 쪽」)에 그대로 맡기는 것도 **선택이 아니라 미정 상태의 방치**로 본다. R-9 가 정해질 때까지 **그 조합이 실제로 발생하는 구성을 운영에 올리지 않는다.**

⚠ **이 보충은 규정 결함을 메운 것이다** — R-4 를 문면대로 읽으면 「writer 가 하나라 충돌이 없다」가 되는데, WebDAV 전환은 회원 본인 쓰기를 전제한다. **두 문서가 서로를 반증하고 있었다.**

### 5.3b R-12 의 근거 — 같은 규약을 두 벌이 들고 있다

마커를 다루는 도구가 **한 계열에서 갈라져 나온 독립 사본**으로 존재한다(vendored). 규약(마커 문자열·`_` 접두 제외 같은 관례)은 **승계했지만 코드는 각자 들고 있다.**

⇒ 🔴 **한쪽이 규약을 바꿔도 다른 쪽은 안 바뀐다.** 그리고 그 어긋남은 **에러로 나타나지 않는다** — 상대 도구에는 그저 「마커 없음」으로 보이고, ③-c 에 따라 **그 파일이 조용히 사람 영역으로 넘어간다.**
⚠ **지금은 문제가 아니다**(양측 문자열 동일 실측). **R-12 는 지금의 일치를 계약으로 고정하는 것**이지 현재 어긋남을 고치는 것이 아니다.

⭐ **관련 패턴** — 이번 왕복에서 **목록을 손으로 옮겨 적은 자리**가 세 번 어긋났다(집계에서 빠진 특수 파일 · 8종인데 4종만 적힌 문서 · 분기 셋 중 둘만 적은 보고). **정본을 지정하고 옮겨 적기를 금지하는 것**이 대응이다(예: 목록의 정본을 테스트 소스로 두기).

### 5.4 R-9 의 실제 충돌 표면 — **세 영역이 성격이 다르다**

회원 vault 에 쓰이는 것은 세 갈래이고, **충돌 위험이 같지 않다.**

| 영역 | 시스템 쓰기 | 회원 쓰기 | 충돌 |
|---|---|---|:-:|
| `15_Sources/` **원본** | **immutable** — 있으면 차단 | 🔴 동기화가 열려 있으면 **덮을 수 있다** | **차단 대상** |
| `10_Notes/` **요약** | 덮지 않고 **비켜서 새 파일**(`_2`) | 자유 | 낮음 |
| `00_MOC/` **목록** | 🔴 **덮어쓴다** — 재생성이 idempotent 라 비켜설 자리가 없다 | 자유 | 🔴 **여기가 진짜 표면** |

**확정 ①(원본)**: **원본은 서버 단독 쓰기 영역이다.** 클라이언트에는 내려보내되 **올려받지 않는다** — 동기화 범위에서 제외하거나 읽기 전용으로 묶는다.
⚠ **이것은 「원본 파일을 두지 말라」가 아니다.** 원본은 요약본의 근거이고 요약본 frontmatter·본문 앵커가 그것을 가리키므로 **빼면 산출물이 깨진다.** 막는 것은 **충돌 해결이 원본에 닿는 것**이다. 덮이면 복구 경로가 없다.

**확정 ②(요약)**: 시스템이 덮지 않는 현행 동작을 **규칙으로 승격한다.** 재수집이 같은 이름을 만나면 비켜선다.

**③(목록)**: 표면이 **「MOC 파일」이 아니라 「마커 사이 한 구간」**이다. 시스템은 파일 안의 마커 사이만 치환하고, **마커 밖은 보존**하며, **마커가 없으면 손대지 않고**, 내용이 같으면 **쓰지도 않는다**(mtime 불변).


**확정 ③-a**: **마커 사이는 시스템 영역이다.** 회원 편집이 보존되지 않는다.
⚠ **근거를 정정한다** — 처음엔 *"경계가 파일 안에 자구로 선언돼 있어 회원도 볼 수 있다"* 를 근거로 삼았으나, **마커는 HTML 주석이라 Obsidian 읽기 뷰에서 보이지 않는다.** 경계가 보인다는 전제는 **소스 모드에서만** 성립한다. ⇒ 규칙의 근거는 「회원이 볼 수 있다」가 아니라 **「시스템이 그 밖을 건드리지 않는다」**(③-b)에 둔다.

**확정 ③-b**: **마커 밖은 회원 영역이다.** 시스템이 보존한다. 🔴 **예외 없이 그렇다** — ③-c 참조.

**확정 ③-c**: **회원이 마커를 지우면 그 파일은 회원 것이 된다** — 시스템이 손대지 않는다. 대가는 자동 목록 갱신을 받지 못하는 것이다.

> 🔴 **판정(2026-09-16)**: 이 규칙이 **예외 없이 성립해야 한다.** 마커가 없을 때 **다른 단서(섹션 제목 등)를 보고 마커를 다시 넣는 경로를 두지 않는다.**
>
> 그런 경로가 있으면 ③-c 가 **조건부**가 되고, 더 나쁘게는 **③-b 도 깨진다** — 마커가 없는 상태에서 쓰는 것은 정의상 **회원 영역에 쓰는 일**이다.
> ⚠ 그리고 **회원은 자기가 지운 것이 돌아온 줄 모른다.** 마커가 읽기 뷰에 보이지 않으므로 **되살아나는 것도 보이지 않는다.**
>
> **이행이 필요한 기존 파일**(마커 규약 이전에 만들어진 MOC)은 **일회성 마이그레이션으로 처리**하고, **상시 경로에는 두지 않는다.** 일회성 의도가 항구적 동작으로 남으면 그것이 규칙을 조건부로 만든다.

✅ **확정 ③-0 (2026-09-16 사용자 결정)**: **회원은 `00_MOC/` 를 편집할 수 있다.** MOC 를 읽기 전용 생성물로 닫지 않는다.
🔴 **단 그 편집은 Obsidian app 에서 일어난다** — **v4 가 MOC 를 편집하는 것이 아니다**(R-10). v4 는 수집을 위해 읽을 뿐이고 편집 경로를 제공하지 않는다.
⇒ 따라서 ③-a·③-b·③-c 가 그대로 규칙이 되고, **아래 잔여가 실재하는 문제로 남는다.**

🔴 **미정 ③-d — 잔여 하나가 남는다.** 시스템의 보존은 **「읽은 순간 서버에 있던 내용」**에 대한 것이라, **회원 기기에만 있고 아직 올라오지 않은 마커 밖 편집**은 보호되지 않는다. 그 판본끼리 만나면 **「더 최신 쪽」에서 시스템이 이긴다.**
⇒ **이것은 동기화 도구가 파일 단위로 보는가, 구간 단위(3-way merge)로 보는가에 달렸다.** 파일 단위면 남고, 구간 단위면 마커 사이만 시스템 것으로 취해 정확히 닫힌다.
⚠ **충돌 창이 좁다는 것이 안전하다는 뜻은 아니다** — 쓰기는 그 MOC 그룹에 새 노트가 들어올 때만 일어나지만, **드물게 나는 충돌은 아무도 보고 있지 않을 때 난다.**
⇒ 동기화 방식이 정해지기 전까지 §5.3 대로 **그 조합이 발생하는 구성을 운영에 올리지 않는다.**

🔑 **③-0 을 「편집 허용」으로 정한 결과, ③-d 가 동기화 방식 선택에 조건을 건다**:

> **회원 vault 동기화 방식은 「파일 단위 최신 우선」으로 충돌을 해결해서는 안 된다.**
> 그 방식에서는 시스템 쓰기가 항상 이기므로 **회원의 MOC 편집이 유실된다.**

⇒ 선택지는 셋뿐이다: ⑴ **구간 병합(3-way)을 지원하는 동기화 방식**을 쓴다 · ⑵ **이력이 남아 복구 가능한 방식**(버전 관리 계열)을 쓴다 · ⑶ **유실을 감수**한다(⇒ 그러면 ③-0 의 「편집 허용」이 실질을 잃는다).
⚠ **⑵ 는 ⑴ 의 대체재가 아니라 보조재다** — 이력이 남는다는 것은 **복구 경로가 생긴다**는 뜻이지 **병합된다**는 뜻이 아니고, 되짚는 것은 사람이다. 게다가 자동 커밋을 거는 구성에서는 **편집이 아닌 것도 이력이 된다**(활성 탭 변경만으로 커밋이 생긴 실측 사례가 있다) — 이력이 많아질수록 **무엇이 실제 편집이었는지 찾기 어려워진다.**
⚠ **이 조건이 WebDAV 도입 방안의 선행 판단이 된다** — 클라이언트의 무료 티어 충돌 해결이 「더 최신 / 더 큰 쪽」이라면 ⑶에 해당한다.

### 5.5 R-10·R-11 보충 — 편집 지점과 분류 소유 (2026-09-16 사용자 결정)

**R-10 — 사용자 엔드 컨트롤 지점은 하나다.**

| 행위 | 어디서 |
|---|---|
| wiki 문서의 **편집·수정·삭제** | 🔴 **Obsidian app 하나** |
| 생성(수집) | Prove |
| 읽기·검색·조회 | v4 |

⚠ **v4 는 wiki 문서 편집 UI 를 만들지 않는다.** 화면에서 고칠 수 있게 하는 순간 **엔드 컨트롤 지점이 둘**이 되고, 그 둘이 같은 파일을 두고 만난다. 지금 규정이 R-9 로 붙들고 있는 문제(쓰기 주체가 둘)를 **하나 더 만드는 일**이다.
⚠ **이것은 v4 의 자기 제약이다** — 연계 측을 제약하기 전에 우리에게 먼저 적용된다.

**R-11 — MOC 분류 체계는 Obsidian 규정이 소유한다.**

🔴 **계층을 가른다.** 「신규 분류 생성」은 **확장 계층에만** 해당한다.

| 계층 | 성격 | Prove 신규 생성 |
|---|---|:-:|
| **TOPICS** | **확장 계층** — 수집을 따라 늘어난다(자동 승격) | ✅ **가능** |
| **TYPES · DOMAINS** | 🔴 **고정 어휘** — frontmatter 의 Critical 값이고 wikilink 가 MOC 파일명과 일치해야 한다 | ⛔ **불가** |

⚠ **고정 어휘를 늘리는 것은 분류 추가가 아니라 규격 변경**이다. 필요하면 §4 절차로 문의한다.
⚠ **「신규 생성」과 「수정」을 가른다.** 확장 계층이 수집을 따라 늘어나는 것은 정상 동작이고, **이미 있는 분류의 정의를 바꾸는 것**은 Obsidian 규정과 회원의 몫이다.
⚠ **분류 어휘의 실물과 규격 문서가 어긋나 있을 수 있다** — 그 경우 **실물을 사실로 보고**, 정리·통지는 소유자(Obsidian 규정)가 한다.
⚠ 마커 사이 목록의 **갱신**(항목 추가·재생성)은 여기서 말하는 「수정」이 아니다 — 그것은 §5.4 ③-a 의 시스템 영역이다. R-11 이 가리키는 것은 **분류 자체가 무엇인가**이다.

### 5.6 명칭 — 규칙 번호는 출처를 붙여 쓴다

번호 체계가 **셋**이고, 번호만 적으면 읽는 쪽이 **자기 것으로 읽는다.**

| 출처 | 표기 | 예 |
|---|---|---|
| 이 문서 | **「v4 규정 R-n」** | v4 규정 R-4 = 시스템 측 writer |
| PAB-Obsidian | **「Obsidian R-n」** | Obsidian R-1 = 단일 writer · Obsidian R-4 = SOURCE 불변 |
| PAB-Prove | **「Prove P-n」** | Prove P-3 = 단일 writer · Prove P-4 = SOURCE 불변 |

🔴 **v4 규정과 Obsidian 은 `R-` 접두가 같고 번호도 겹치며 주제까지 인접하다** — v4 규정 R-4(시스템 writer) ↔ Obsidian R-1(단일 writer), v4 규정 R-1(vault 경로) ↔ Obsidian R-4(SOURCE 불변). **가장 섞이기 쉬운 조합**이라 접두를 생략하지 않는다.
⚠ 이 문서 안의 `R-n` 은 전부 **v4 규정**을 가리킨다.

### 5.7 R-13 보충 — 조회 스코프의 현재 값과 확장 규율 (2026-09-16 사용자 결정)

#### 지금은 「개인」뿐이다

**요청자 본인의 지식만 조회된다.** 확장 형태(**팀 · 공유 · 구입 · 공통 · 개방(무료)** 등)는 **정의하지 않는다** — 형태가 다양할 것이고 **실사용 반응을 보고 정해야 하기 때문**이다.
⚠ **「아직 없음」이지 「각자 정하라」가 아니다.** 연계 측은 본인 외 범위를 여는 어떤 경로도 만들지 않는다(§4 절차).

#### 🔴 현재는 이 룰을 어기고 있다 — 실측

조회 스코프가 **요청자가 아니라 API 키 주인**으로 정해져 있어, 라이브에서 두 방향 모두 어긋난다:

| 요청 | 결과 |
|---|---|
| 회원이 **자기 brain 을 지정** | 🔴 「요청자 brain ∩ 키 주인 문서」가 비어 **`no_data`** — **자기 지식을 못 읽는다** |
| 회원이 **brain 미지정** | 🔴 **키 주인(관리자) 지식 전체가 응답에 실린다** — **남의 지식을 읽는다** |

⚠ 후자가 **`outcome: answered` 로 기록된다** — **성공으로 보이는 실패**다. 관리자 계정으로 쓰면 요청자와 키 주인이 같아 **어느 쪽도 드러나지 않는다.**
⇒ **R-6(대리 조회) 이 들어와야 고쳐진다.** 그때 기본값은 **「요청자 본인의 것 전부」**이고, **brain 미지정이 「스코프 없음」이 아니라 「본인 전체」**를 뜻해야 한다.

#### 🔴 접근 범위를 토큰·세션에 굽지 않는다

확장이 들어오면 「무엇을 볼 수 있는가」가 **시간에 따라 변한다** — 공유 해제, 구독 만료, 환불, 차단.

| | 범위를 **토큰에 담는다** | **신원만 담고 조회 시 판정** |
|---|---|:-:|
| 권한 회수 | 🔴 **토큰 만료까지 유효** — 취소·환불·차단이 **즉시 안 먹는다** | ✅ **즉시 반영** |
| 범위 변경 | 토큰 재발급 필요 | ✅ 자동 |
| 비용 | 조회 1회 절약 | 조회 1회 추가 |

⇒ **토큰은 「누구인가」만 담고, 「무엇을 볼 수 있는가」는 조회 시점에 판정한다.** 범위를 구우면 **유상 모델에서 환불이 반영되지 않는** 형태가 되고, 그것은 조용한 실패다.

#### ⚠ 검증 규율 — 권한이 높은 계정으로 스코프를 시험하지 않는다

위 유출이 **6일 넘게 재현되는 동안 아무도 몰랐던 이유**가 이것이다 — 관리자 계정으로 쓰면 **요청자와 키 주인이 같아** 두 결함이 **둘 다 정상으로 보인다.**

> 🔑 **테스트 계정의 권한이 높으면 스코프 결함이 관측되지 않는다.**

⇒ **스코프·격리를 시험할 때는 반드시 일반 회원 계정으로 한다.** 관리자 계정의 「잘 된다」는 **스코프에 대해 아무것도 증명하지 않는다.**

#### 판정 지점은 한 곳이다

**brain 접근 여부를 판정하는 자리를 하나로 유지한다.** 현재 그 자리는 **소유 검증 한 줄**(요청자 == brain 소유자)이고, 확장은 **그 한 줄을 「권한 판정」으로 넓히는 것**이지 다른 곳에 조건을 더하는 것이 아니다.
⚠ 판정이 두 곳으로 갈리는 순간 **한쪽만 고쳐져 권한이 새는 경로**가 생긴다 — 이 규정 §2 가 말한 형태 그대로다.

| # | 항목 | 확정값 |

| **F3** | 토큰 형태 | **불투명 문자열**(`token_urlsafe(32)`). 🔴 **연계 측은 안을 보지 않는다 — 볼 수 없다** |

#### 🔴 헤더 명명 규칙 (2026-09-17 확정 — Prove 제안 수용)

> **`X-PAB-<X>-…` 의 `<X>` 는 그 헤더를 「검증하는 쪽」을 가리킨다. 구간이 없으면 v4 가 검증한다.**

| 헤더 | `<X>` | 검증자 | 뜻 |
|---|:-:|:-:|---|
| `X-PAB-Key` | — | **v4** | v4 가 검증하는 호출자 키 |
| `X-PAB-**Prove**-Key` | Prove | **Prove** | **Prove 가 검증하는** 호출자 키 |
| `X-PAB-On-Behalf` | — | **v4** | v4 가 검증하는 위임 표시 |

🔑 **모호함의 정체는 이름이 아니라 「읽는 규칙이 안 적혀 있다」는 것이었다** — 사람들이 `Prove` 를 **소유격**(*"Prove 의 키"*)으로 읽는데 체계는 **검증자 표시**다. ⇒ **이름을 하나도 바꾸지 않고 셋이 한 규칙으로 읽히고, 넷째가 생겨도 자리가 정해진다.**
⚠ **`X-PAB-Prove-Key` 는 개명하지 않는다** — 계약 변경 비용을 치를 이유가 없어졌다. Prove 는 이미 상수 정의를 한 모듈(`proveauth.py`)에 모아 **방향을 파일 경계로** 가르고 있다(2026-09-09 양측 합의).
⚠ **세 헤더는 공존한다.** `X-PAB-Prove-Key`(장기 호출자 자격) 와 위임 토큰(단명)은 **대체가 아니라 두 겹**이다 — 키를 단명 형태로 통일하면 **「매 요청 v4 검증 0회」 계약이 깨져 v4 장애가 Prove 전면 정지로 전파된다.**

**연계 측 의무 — 세 줄이 전부다**

1. 🔴 **운반만 한다.** `metadata.on_behalf_of` 를 받은 그대로 `X-PAB-On-Behalf` 헤더에 싣는다. **값을 만들지 않고 해석하지 않는다**(R-6 본문).
2. 🔴 **동시 처리 시 토큰을 섞지 않는다.** 섞이면 그것이 **정확히 회원 간 유출**이고, **v4 는 검증할 수 없다.**
3. 🔴 **`member_id` 와 위임 토큰의 일치를 검증하지 않는다.** 검증하는 순간 그것이 인가 분기이고, Khala 가 스스로 막아 둔 상태가 된다. v4 가 **같은 `user_id` 에서 둘 다 파생**하므로 불일치가 구조적으로 생기지 않는다.

⚠ **구현 착수 조건은 별개다** — 회원 데이터에서 파생된 산출물이 무인증으로 읽히는 표면(`/v1/multipage/{status,artifacts}`)이 **닫힌 뒤**에 켠다. 순서를 뒤집으면 위임이 격리를 만드는 게 아니라 **누수 경로를 하나 더 여는 일**이 된다(R-5 — 파생물도 회원 데이터다).
⚠ **`outcome` 은 권한 축이 아니다** — 스코프가 좁아져 결과가 비어도 `no_data` 로 나오고, 그건 「권한이 없어서」가 아니라 「근거가 없어서」다. **권한 축은 v4 가 따로 만든다**(관측 `scope_source`). 연계 측은 `outcome` 의 의미를 넓히지 않는다.

### 5.9 R-7 — vault 표시명 **확정** (2026-09-17)

전문은 v4 `docs/phases/phase-6-5/reports/260917-R7-vault표시명-규칙안.md`. **여기에는 연계 측이 알아야 할 것만 적는다.**

| | 확정값 |
|---|---|
| **누가 정하는가** | 🔴 **vault 주인 본인.** 회원은 자기 것, admin 은 자기 것. **admin 도 남의 표시명을 고치지 않는다** |
| **어디서** | **v4 마이페이지**(`/account`) — 쓰기 주체는 **v4 하나** |
| **형식** | 트림 후 **1~64자** · 제어문자·개행 금지 · **빈 값 거부**(지우려면 명시적 null) |
| **중복** | 🔴 **허용.** 식별자는 `vault_id` 이고 표시명은 표시용이다. ⚠ **중복 금지는 「남이 그 이름을 이미 썼다」를 알려주어 다른 회원의 존재를 드러낸다** — 편의가 아니라 **격리**가 이유다 |
| **부재** | **NULL 이 정상.** *"아직 이름을 정한 적 없다"* — **조회 실패가 아니다** |
| **읽기 판정** | v4 `vault_display_name_for` 한 규칙: ① 행에 값 있으면 그것(**설정된 값 > 설정 기본값**) ② admin 이고 값 없으면 설정 기본값 ③ 그 외 **NULL**. 🔴 **경로 파생·username 합성·`""`→NULL 접기·`str(None)` 전부 금지** |

**연계 측 의무 — 두 줄**

1. 🔴 **표시명을 만들어 쓰지 않는다.** R-7 이 확정돼도 **쓰기 주체는 v4 뿐**이고, 연계 측은 **받은 값을 표시만** 한다.
2. **NULL 을 오류로 취급하지 않는다.** 「아직 안 정했다」이고 정상이다. 대체 이름을 **지어내지 않는다**(경로·username 파생 포함).

⚠ **R-10 과 충돌하지 않는다** — R-10 은 **wiki 문서**의 편집 엔드 컨트롤을 Obsidian 하나로 둔 것이고, **vault 표시명은 wiki 문서가 아니라 계정 설정**이다(노트 파일에도 frontmatter 에도 들어가지 않는다). ⇒ **v4 가 이 입력 UI 를 제공하는 것은 R-10 위반이 아니다.** 이 구분을 적어 두지 않으면 나중에 「v4 가 편집 UI 를 만들었다」로 읽힌다.

⚠ **예고 — `/ext` `meta.vault`**: 현재 전역 설정값 고정이라 **회원 문서를 조회해도 관리자 vault 이름이 나간다.** 표시명 쓰기 경로가 생기고 값이 들어간 뒤 **소유자 기준으로 바꾸고, 그때 `vault` 가 `null` 일 수 있다.** 🔴 **브레이킹이므로 사전 통지 후 적용한다**(§7).

### 5.10 R-13 보충 — **관리자 열람 범위 확정** (2026-09-17 사용자 결정)

R-13 이 *"확장 형태는 미정"* 이라 한 것 중 **첫 확정**이다.

> **관리자도 일상 조회는 「본인 것」이다. 운영·진단 목적의 전체 조회는 「명시적 별도 경로」로만 하고, 그 접근을 기록한다.**

| | |
|---|---|
| 현재(변경 전) | `scope_user_id(admin) = None` ⇒ 검색·LV1 조립·AI 찾아줘 **전 경로에서 회원 문서 전량 열람** |
| 확정 | **기본은 본인 것.** 전체 조회는 **별도 경로 + 접근 기록** |
| 이유 | 사용자 원칙 *"수집 자료는 개인 동의가 필요"* + R-13 |

⚠ **기록이 없으면 이 결정은 현행 유지와 같아진다** — 「의도를 드러낸다」가 장치가 아니라 문구가 된다.
⚠ **연계 측에 직접 걸리는 의무는 없다.** 다만 **R-13 의 확장이 하나 정해졌다**는 사실은 알려 둔다 — 앞으로의 확장(팀·공유·구입·개방)도 **같은 형태**(기본은 좁게, 넓힘은 명시적으로, 그리고 기록)로 정해질 것이기 때문이다.

### 6.1 🔴 실측 정정 (2026-09-17) — **낡은 기록으로 판정할 뻔했다**

R-6 확정안 초고는 *"`documents` 140건이 전부 `pab_default`(로그인 불가) 소유라, 위임만 켜면 답변이 비는 전환이 된다"* 고 적었다. **v4 내부 문서의 2026-09-08 기록을 근거로 쓴 것**이고, **Prove 가 자기 쪽 D38(09-14)의 다른 분포를 들어 물어 실측이 이뤄졌다.**

| id | username | role | 로그인 | `documents` | `brains` | 배정 |
|:-:|---|---|:-:|---:|---:|---:|
| 1 | `pab_default` | user | ⛔ 불가 | 🔴 **0** | 0 | 0 |
| 2 | `admin-super` | admin_system | ✅ | **140** | **7** | **67** |
| 3 | **`member_b`** | user | ✅ | 🔴 **181** | **1** | **12** |
| 4 | `pab_prove` | system | ⛔ 불가 | 0 | 0 | 0 |
| 7 | `member_c` | user | ✅ | 2 | 0 | 0 |

**합계 323건 · 소유자 NULL 0건 · brains 8개**

| 낡은 기록 | 실측 |
|---|---|
| *"140건 전부 `pab_default` 소유"* | **`pab_default` 는 0건.** 140 은 `admin-super` — **같은 숫자라 겹쳐 보였을 뿐 다른 축**이었다(Prove 의 ⒜ 가설이 맞았다) |
| *"실제 회원 0명"* | **`member_b`·`member_c` 실재.** `member_b` 는 **자기 문서 181건과 자기 brain** 을 갖고 있다 |

⇒ **R-8 은 「소유 이관」이 아니라 「빈 계정 정리」**로 격하되고, **R-6 의 선행 조건에서 빠진다.**
⇒ **R-6 은 서비스를 비우지 않는다** — `member_b` 에게 **자기 181건을 돌려주고**, 관리자는 자기 140건을 그대로 본다. 좁아지는 것은 **남의 것**뿐이다.

🔑 **이 정정이 일어난 경로를 규정에 남긴다** — 이 규정 §4 의 「애매하면 v4 에 문의한다」가 **반대 방향으로 작동했다.** 연계 측이 **자기 쪽 수치를 근거로 되물었고, 그래서 v4 의 낡은 기록이 드러났다.** ⇒ **문의 의무는 연계 측을 제약하는 장치가 아니라 양측의 대조 장치다.**
⚠ **서버 상태는 문서가 아니라 서버에 묻는다.** 이 규정을 포함해 **어떤 문서에 적힌 서버 수치도 「그때의 값」**이다.

⚠ **3번을 먼저 적는다** — 이 규정은 연계 측을 제약하기 전에 **v4 에게 의무를 지운다.** 룰을 정하지 않은 채 "각자 만들지 마라"만 말하면 상대는 멈춰 있어야 한다.
