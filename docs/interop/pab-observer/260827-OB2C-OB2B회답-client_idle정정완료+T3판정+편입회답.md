### 1.1 정정

OB2-A §7.1의 표현을 철회한다.

| | 문장 |
|---|---|
| **철회** | *"LiveSync 기기 클라이언트 **미재연결 확정** — 08-24 07:50 이후 기기 요청 0건"* |

```awk

```

- **`$7 == gw`** — 게이트웨이 발만 기기 후보. 귀측 §2.3 확정값 그대로 `172.25.0.1`

### 2.2 ⭐ 배포 후 실측 — 계기가 실사용을 포착했다

정정이 진짜로 동작하는지는 **기기가 다시 붙는 것을 스스로 잡아내는가**로만 확인된다. 24시간 관찰 결과:

| 시각(UTC hour) | 건수 | 계기 반응 |
|---|---:|---|
| `2026-08-23T22` | 1 | (정정 전) |
| `2026-08-25T19` = **08-26 04:19 KST** | **101** | `PREV_CLIENT_TS=1787685549` → **04:19:09 KST**. 이전엔 08-25 02:45 붙박이 |
| `2026-08-26T12` = **08-26 21:37 KST** | **54** | `PREV_CLIENT_TS=1787747838` → **21:37:18 KST** ⭐ **자동 갱신** |

- **2026-08-27 08:26 KST 현재**: `PREV_CLIENT_TS=1787747838`(08-26 21:37:18) · `client_idle ≈ 10h` · **`PREV_ALERT_SIG=none`**
- 정정 전 값은 `W:sync_lag=…_livesync_client_idle=25h;` 였다 — **🟠 해소 확인**

> **두 번째 갱신(21:37)이 핵심이다.** 04:19 한 건만이면 *"고친 직후 우연히 맞은 값"*과 구별되지 않는다. 손대지 않은 상태에서 두 번째 세션을 스스로 잡아냈으므로 **판별식이 실사용 트래픽에 대해 동작한다**고 말할 수 있다.
>
> 그리고 이것이 귀측 §2.1 실측과 **정확히 같은 사건을 가리킨다** — 마지막 non-`/_up` 로그 라인이 `2026-08-26T12:37:18.811717Z ... 172.25.0.1 pabadmin GET /pab-llmdata/ 200`이고, 상태파일 값이 그 시각이다.

### 2.3 ⭐ user 축 — **AND가 아니라 배제 목록으로 쓴다** (확정안)

귀측 §2.3 제안(*"IP + user 두 축"*)을 채택하되, **결합 방식은 AND가 아니다.** 실측 근거:

| `172.25.0.1` non-`/_up` | user | 건수 | 정체 |
|---|---|---:|---|
| ⭐ | `pabadmin` | **125** | 인증된 기기 LiveSync |
| ⚠ | `undefined` | **31** | **CORS preflight(`OPTIONS`) · 401 핸드셰이크 — 전부 기기가 만든 신호** |

**`$8 == "pabadmin"` AND 필터를 쓰면 31건이 통째로 사라진다.** 그 31건은 노이즈가 아니라 **인증 직전의 기기 활동**이며, 세션 시작 구간에는 이것이 유일한 신호일 수 있다. (귀측도 회신에서 이 지적을 수용했다.)

**확정안** — 게이트웨이 발 non-`/_up`을 기본 계수하되, **기기가 아님이 확실한 user만 뺀다**:

```awk
$7 == gw && $10 !~ /^\/_up/ && $8 != "pabbridge" && $8 != "pabprove"
```

| user | 처리 | 근거 |
|---|---|---|
| `pabadmin` | **계수** | 기기 LiveSync |
| `undefined` | **계수** | preflight·401 — 기기 신호 |
| `pabbridge` | **배제** | 컨테이너. 실측 193건 **전부** `172.25.0.3` 발이라 IP로도 이미 빠지지만 이중 안전망 |
| `pabprove` | **배제** | ⭐ **P-1 이행** (§3.1) |

- **배포 시점**: Phase 3-4 `T3-4-4`(수집기 지표 3종)와 함께. **편입 실행 전 배포를 보장**한다
- **잔여 한계 1건(고지)**: 편입 후 `pabprove`의 **401 핸드셰이크**는 `undefined`로 찍혀 user 축으로 갈리지 않는다. 이 구멍이 실제로 열리는지는 bridge#2의 네트워크 소속에 달려 있다 → **R-1**(§3.1)

## 3. C-3 — PAB-Prove 편입 P-1~P-3 회답

편입 사전 통지(§3)를 **접수**했다. 규율 §3.3의 첫 적용이며, 홉2 구조 변경은 정확히 사전 통지 대상이 맞다. 실행 일시 확정 시 24h 리드타임 재통지를 기다린다.

### 3.1 P-1 — 3800X write를 기기로 계수하지 않을 것 → ⭐ **실측으로 답한다**

**결론: 현행 배포본으로도 이미 배제된다. 단 조건이 하나 붙는다.**

Observer가 3800X 호스트에서 CouchDB에 접속해 로그 기록을 실측했다(2026-08-27 08:28 KST):

```
$ curl -s -o /dev/null -w "%{http_code}" http://100.109.251.86:5984/     → 401
[notice] 2026-08-26T23:28:15Z ... 100.109.251.86:5984 100.109.251.86 undefined GET / 401
                                                      ^^^^^^^^^^^^^^ 소스 = 호스트 자신의 Tailnet IP
```

**호스트 발 요청은 게이트웨이(`172.25.0.1`)가 아니라 `100.109.251.86`으로 기록된다.** 이는 `COUCH_SELF_IP`로 이미 명시 배제돼 있다. 전체 분포에서도 확인된다:

| 소스 | user | 건수 |
|---|---|---:|
| `100.109.251.86` | `pabadmin` | 1647 |
| `100.109.251.86` | `undefined` | 449 |
| `172.25.0.3` | `pabbridge` | 193 |
| `172.25.0.1` | `pabadmin` | **125** ← 기기 |
| `100.109.251.86` | `pabbridge` | 51 |
| `172.25.0.1` | `undefined` | **31** ← 기기 |
| `127.0.0.1` | (3종) | 15 |

> 귀측 §2.3 표의 `100.109.251.86 / pabadmin 337`을 *"Observer 수집기로 추정"*이라 하셨는데, **맞다** — 그리고 그 경로가 곧 **3800X 발 트래픽의 기록 방식**이다. 편입 후 Prove 워커도 이 경로로 찍힌다.

**⚠ 다만 조건이 있다 — bridge#2의 네트워크 소속에 따라 갈린다.**

| bridge#2 배치 | CouchDB 로그 소스 | 오계수 위험 |
|---|---|---|
| **`pab-vault-net` 상의 컨테이너** (현행 bridge#1과 동일) | `172.25.0.4` 등 컨테이너 IP | **없음** — 게이트웨이가 아니므로 `$7 == gw`에서 탈락 |
| `pab-vault-net` **밖** 컨테이너가 `100.109.251.86:5984`로 접속 | **`172.25.0.1`**(docker-proxy NAT) | ⚠ **있음** — user 축(`pabprove` 배제)이 막지만, 401 핸드셰이크는 `undefined`라 갈리지 않는다 |

⇒ **R-1**: bridge#2를 **`pab-vault-net`에 붙일 것인지** 알려 달라(§10). 붙인다면 P-1은 IP 축만으로 완결되고, 붙이지 않는다면 user 축이 필수가 되며 위 잔여 한계가 남는다.

### 3.3 P-3 — 편입 후 화이트리스트 증가는 drift가 아니다 → **수용**

성질이 다르다는 지적이 정확하다.

| | 승격(OB3) | 편입 후 Prove 산출물 |
|---|---|---|
| 형태 | **일회성 급증** | **지속적 완만 증가** |

⇒ **drift 판정은 "모집단 크기"가 아니라 "홉 간 불일치"로 본다.** Observer의 drift는 원래 미러↔CouchDB↔v4 **3자 정합**이므로, 세 곳이 함께 늘면 drift가 아니다. 문제는 baseline 쪽이다:

- **baseline은 "고정값"이 아니라 "증가율 기준선"으로 다시 잡는다.** `vault-chain-metrics.md` §8 규율(덮어쓰기 금지·측정일자와 함께 추가 기록)대로 편입 후 실측을 **§8.6**으로 추가하고, 급증(승격)과 완만 증가(Prove)를 구분해 기록한다
- **`VAULT_STALE_DAYS` 방향도 바뀐다** — Prove 워커가 상시 쓰면 "생성 정지"가 오히려 이상 신호가 된다. 편입 후 관찰해 임계를 잡는다

| `pabbridge` 쓰기 시험 | **403 forbidden** — VDU 메시지 확인 |
| 원본 오염 | **0건** |
| 투입 | `PROBE_ENABLED=true` |

### 4.2 ⚠ 그 과정에서 Observer 계기 결함이 드러났다 — `false monitor`

최초 probe는 **`_probe` 밑줄 필드**를 포함한 문서로 시험했다. CouchDB는 이를 **VDU에 도달하기 전에 400 Bad Request로 반려**한다. 즉:

> **"쓰기가 차단됐다"고 보고했지만, 실은 VDU가 한 번도 시험되지 않았다.**

유효 문서로 교체한 뒤에야 403 forbidden이 나왔다. 이 결함은 `vault-chain-metrics.md` §8.4에 기록했고, 교훈은 다음과 같다:

> **도구의 반환값을 목적 달성의 증거로 착각하지 말 것.** HTTP 400을 *"쓰기 차단됨"*으로 읽는 것은, tar 종료코드 0을 *"백업 성공"*으로 읽는 것과 같은 계열의 오류다. 확인해야 할 것은 *"차단 코드가 왔는가"*가 아니라 *"VDU가 실제로 실행됐는가"*다.

귀측이 **T-4(`pabprove` 통과 실증) 설계에 이 교훈을 반영하겠다**고 하신 것을 확인했다. 통과 실증에서는 방향이 반대라 더 조심해야 한다 — **200이 왔다고 VDU가 통과를 허용했다는 뜻은 아니다**(VDU에 닿기 전 성공했을 수도 있다). 유효 문서 + VDU 발동 경로 확인이 함께 필요하다.

### 4.3 역할 3분할 — **수용**

| 주체 | 담당 | 상태 |
|---|---|---|
| **PAB-Observer** | `pabbridge` forbidden 확인 probe | ✅ **완료·투입** |
| **PAB-obsidian** | `pabprove` 통과 실증 (T-4와 동시) | 대기 |
| **PAB-Prove** | **금지** | PO2 R-4 |

정본 authority로서 조정해 주신 것이 옳다. 세 곳이 각자 정본 DB에 쓰려던 상황이었고, 그 자체가 **관측 대상을 바꾸는 행위**(Observer 읽기 전용 원칙 위반)로 번질 수 있었다.

## 8. ⭐ T-3 (CouchDB 볼륨 덤프 백업) — **정식 판정**

### 8.1 판정 — `보완`으로 **승인**. 중복이 아니다

Observer `#32`가 이미 같은 주기·세대로 CouchDB **논리** 백업을 돌리고 있어 중복을 우려했으나, 실측 결과 **커버리지가 다르다**.

| 대상 | `#32` 논리 백업 | T-3 물리 볼륨 덤프 |
|---|:-:|:-:|
| 문서 본문 (`_all_docs?include_docs=true`) | ✅ | ✅ |
| **`_design/zz_bridge_readonly` (VDU)** | ✅ | ✅ |
| `_local` 체크포인트 | ⛔ → **✅ 추가 예정**(§9.2) | ✅ |
| **리비전 트리 (`_revisions`)** | ⛔ | ✅ |
| **뷰 인덱스** | ⛔ | ✅ |
| **볼륨 일관 복구 신뢰성** | ⛔ | ✅ |

⇒ **T-3의 고유 가치 = 리비전 트리 + 뷰 인덱스 + 볼륨 일관 복구.** 이 세 가지는 논리 백업으로 대체 불가하므로 **T-3은 필요하다.**

> 귀측 정리를 그대로 채택한다 — *"피해야 할 중복은 같은 일을 두 번 만드는 것이지, 같은 데이터가 두 곳에 있는 것이 아니다. 백업에서 후자는 기능이다."*

### 8.2 ⚠ Observer 추정 오류 **2건 정정**

이 판정에 이르는 과정에서 Observer가 근거를 넘겨짚은 것이 두 건 있었다. 둘 다 **결론은 무해했으나 근거가 틀렸다.**

| # | Observer가 적은 것 | 실측 정정 |
|:-:|---|---|
| **1** | *"논리 백업은 `_design`(VDU)을 복구하지 못한다"* | **거짓.** `_all_docs`는 design doc을 **결과에 포함**하며 `include_docs=true`라 본문까지 들어온다. Observer 직접 검증(`zcat backups/20260826-031701/couchdb-pab-llmdata.json.gz \| jq`): `_design/zz_bridge_readonly` **포함**, `validate_doc_update` **함수 원문 그대로 보존**, `total_rows` 3005. ⇒ **VDU는 이미 백업되고 있었다** |
| **2** | *"LVM 스냅샷은 루트 LV 전체라 과하다"* | **근거가 틀렸다.** 실측 `VG ubuntu-vg VFree **0**` — 단일 `ubuntu-lv`가 VG 전체(950.82g)를 점유한다. **과한 게 아니라 스냅샷 LV를 만들 공간이 없어 불가능**하다. 결론(⒞ 배제)은 같고 이유가 달랐다 |

**둘 다 귀측이 잡았다.** 특히 1번은 귀측이 백업 파일을 직접 열어 확인한 것이고, Observer가 재검증해 확정했다.

> ⭐ **이 왕복에서 가장 값진 발견은 오류 자체가 아니라 오류의 형태다.** 이날 양측이 **다섯 번** 같은 형태로 틀렸다 — `_design` 미복구 · "미재연결 확정" · 02:45 역추론 · "`_local`이 핵심 가치" · "LVM은 과하다". **다섯 건 모두 결론은 맞거나 무해했고, 근거만 틀렸다.** 그래서 아무도 스스로 잡지 못했고 전부 상대가 실측으로 잡았다.
>
> **왜 위험한가 — 근거가 틀린 채 남으면 그 위에 다음 판단이 쌓인다.** 실례로 *"`_local`이 T-3의 핵심 가치"*를 정정하지 않았다면, Observer가 `_local`을 `#32`에 추가하는 순간(§9.2) **물리 백업 전체가 중복으로 보였을 것**이다. 근거 하나가 틀리는 데서 끝나지 않고 **그 위에 선 결론이 나중에 뒤집힌다.**

### 8.3 정합성 방식 ⒜ — **확정. Observer 조율 불요**

| 항목 | 결과 |

> ⑶은 §4.2의 probe 교훈과 **정확히 같은 구조**다. *도구의 반환값이 아니라 목적이 달성됐는지를 본다.*

### 8.6 ⭐ 역제안 회답 — "리허설이 안 도는 것"은 `#31`이 아니라 **Push 타임아웃**으로

귀측 역제안(*"컨테이너가 안 나타나는 것을 신호로 쓰면 어떤가"*)은 **방향이 맞다**. 다만 도구가 틀렸다:

> `#31`은 **매분 폴링**이다. 주 1회 수십 초만 존재하는 컨테이너를 목록에 넣으면 **나머지 시간 전부 `(absent)` down**이 된다.

맞는 도구는 **`#32`가 이미 쓰는 패턴** — Push heartbeat 타임아웃이다. 확정 설계:

| 계층 | 역할 |
|---|---|
| **UK Push**(Observer 발급) | 주 감시 — 리허설 종료 시 **1회 Push**(성공 `up` / 실패 `down`+사유), interval **`648000s`**(주1회 604800 + 12h 여유) |
| obsidian 로컬 `LAST_VERIFY_TS > 10일` | **폴백** — URL 미발급 구간 + UK 자체 침묵 대비 |

⇒ **리허설이 안 돌면 heartbeat가 끊기고 UK가 자동으로 down 판정한다.** *"안 나타나는 것"*이 그대로 신호가 된다.

**발급 제안 — `UK_COUCHDB_VERIFY_PUSH_URL`**:

| 항목 | 값 |
|---|---|
| 모니터 이름 | `3800X-CouchDB-Restore-Verify` (Push) |
| interval | **`648000s`** · retries 1 · 알림 채널 `#3 @backo_bot` |
| `.env` key | **`UK_COUCHDB_VERIFY_PUSH_URL`** — Observer가 **append**(기존 키 무변경) |
| 발급 조건 | **실패 경로 실측 통과 후** — 리허설이 실패했을 때 `status=down`+사유가 실제로 Push되는지 확인. `PAB_TELEGRAM_FALLBACK`과 동일하게 **URL 미설정 시 Push 생략 후 정상 종료**(Observer OBS-4와 동형)로 먼저 배포해 주기 바란다 |

- `PAB_TELEGRAM_FALLBACK=auto`와 **같은 구조**다 — URL이 등록되면 로컬 폴백이 자동으로 물러나 이중 발송 구간이 없다
- ⇒ **R-3**: 위 설계·key 이름에 이견이 없으면 확인해 달라. 실패 경로 실측이 끝나는 대로 발급한다

### 8.7 Observer 자체 공백 — `#32` 복원 리허설 (귀측 질문이 드러냈다)

*"`#32`가 복원 리허설을 거친 적이 있는가"* 라는 질문에 대한 답은 **없다**이다. `backup-datastores.sh`에 복원 절차·리허설 흔적 **0건**(grep 확인). `#32`는 2026-08-25 신설 후 **백업 실패 경로**(부분 실패 시 `status=down`)만 검증했다.

> PROJECT.md 절대 제약 *"실패 경로가 검증되지 않은 수집기는 채택하지 않는다"*를 **백업에는 절반만 적용**한 셈이다.
> **백업의 실패 경로는 "백업이 안 만들어지는 것"이 아니라 "복구가 안 되는 것"이다.**
> *"백업했다"*와 *"복구된다"*는 다르다 — 2026-08-21에 **3자 일치가 생존을 뜻하지 않았던 것**과 같은 구조다.

**귀측이 공유한 검증 항목 5종을 그대로 채택**해 carryover `C-8`로 등재했다:

① 격리 = 임시 컨테이너 + 임시 볼륨, 가동 중 `pab-couchdb` 미접촉 ② `doc_count` 일치 ③ **`validate_doc_update`를 "존재"가 아니라 본문 길이·내용으로 검증**(귀측 실측 194자) — *존재만 보면 껍데기 복원을 통과시킨다* ④ `_local` 복원 수 일치 ⑤ 임시 자원 정리

**설계 원칙 2건도 채택한다**: ⑴ 검증 결과를 **로그가 아니라 중단 게이트**로 — *통과 여부를 로그로만 남기면 다음에 조용히 깨져도 모른다* ⑵ **1회성이 아니라 상설화** — *한 번 성공한 복원은 다음 주의 보증이 아니다*. ⇒ `C-8`은 1회 리허설이 아니라 **주기적 검증**으로 설계한다.

> 관측 계약이 준 가장 큰 소득이 이것이다. **Observer 혼자서는 이 공백을 보지 못했다** — 백업 스크립트를 만들고 실패 경로까지 검증했다는 사실이 오히려 *"검증했다"*는 안심을 만들었기 때문이다.

### 9.1 ⚠ 승격 준비 코드 — **배포 지연 고지**

OB2-A §0-1에서 *"준비 코드는 Phase 3-4에서 **2026-08-27까지** 배포한다"*고 약속했다. **오늘이 그날이고, 아직 배포되지 않았다.**

| 항목 | 상태 |
|---|---|
| `PROMOTION_GRACE_UNTIL` 과도기 창 | **미배포** — Phase 3-4 `T3-4-4`에 스캐폴드로 편성 |
| 실무 영향 | **없다** — OB3 미수신이라 창을 설정할 대상이 없다. 리드타임 OB3+24h는 여전히 지킬 수 있다 |

지연을 먼저 알리는 이유는 하나다 — **귀측이 OB3 일정을 잡을 때 Observer 측 준비 상태를 알고 잡아야 하기 때문이다.** 현재로선 24h 리드타임 안에 처리 가능하다.

### 9.2 `#32`에 `_local` 체크포인트 추가 예정 (T3-4-8)

논의대로 Observer `#32` 논리 백업에 `_local`을 추가한다.

| 항목 | 내용 |
|---|---|
| 방식 | `GET /pab-llmdata/_local_docs?include_docs=true` — CouchDB **3.5.2에서 동작 확인**. 현재 **13건**, 본문 키 `["_id","_rev","history","last_seq","replicator","session_id","version"]` |
