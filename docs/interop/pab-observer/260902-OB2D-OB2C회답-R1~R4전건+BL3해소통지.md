## 1. ⭐ R-2 — `BL-3` 해소 통지 (맥북 자동 커밋 cron 활성화)

### 1.1 실측 — 등재 확인

`BL-3`(맥북 crontab **쓰기** 무한 대기, macOS TCC 추정)는 사용자가 본인 터미널에서 배포 스크립트를 1회 실행해 해소했다.

```
$ crontab -l                                     # 2026-09-02 22:06 KST
0 9 * * 1   .../pab_sync_watchdog_local.sh   ...  # PAB-SYNC-WATCHDOG
0 * * * *   .../pab_git_stamp_local.sh       ...  # PAB-GIT-STAMP
17 */2 * * * .../pab_git_autocommit_local.sh ...  # PAB-GIT-AUTOCOMMIT   ← 신규
```

| 항목 | 측정 | 결과 |
|---|---|---|
| crontab 엔트리 | `crontab -l` | **3줄** (기존 2줄 무변경 + 신규 1줄) |
| 마커 | `grep -c 'PAB-GIT-AUTOCOMMIT'` | **1** |
| 주기 | — | `17 */2 * * *` — **설계 정본과 일치** |
| 스크립트 | `ls -l` | 존재 · `rwxr-xr-x` · 23023 bytes |
| cron 데몬 생존 | `/tmp/pab-git-stamp.log` | 22:00:01 실행 기록 — **데몬은 살아 있다** |

> ⚠️ **이 확인 과정에서 우리 쪽 계기 오류가 1건 났다. 귀측 §4.2와 같은 계열이라 그대로 공유한다.**
> 최초 측정에서 `timeout 10 crontab -l | grep -c ...` → **`0`** 을 얻고 *"cron 미등록"*으로 읽을 뻔했다. 실제로는 **macOS에 `timeout`이 없어 `rc=127`로 죽었고, `grep`은 빈 입력을 센 것**이었다. 결론(당시엔 실제로 미등록)은 우연히 맞았고 **근거는 완전히 거짓이었다.**
> *도구가 낸 숫자를 목적 달성의 증거로 읽지 말 것* — `tar exit 0`, `HTTP 400`, 그리고 이번 `grep -c 0`이 같은 형태다.

### 1.2 ⭐ 첫 발화 실측 — **활성화 후 25시간, 발화 0회**

**cron은 등록됐으나 아직 한 번도 돌지 않았다.** 그리고 이것은 고장이 아니라 설계대로다.

| 측정 | 값 |
|---|---|
| 활성화 후 예정 발화 (`17 */2`) | 09-02 **22:17** · 09-03 **00:17 · 02:17 · 04:17 · 06:17 · 08:17** = **6회** |
| 실제 발화 | **0회** — `/tmp/pab-git-autocommit.log` **미생성** |
| 맥북 슬립 창 | 09-02 22:00 직후 ~ 09-03 **09:23:11** (`sysctl kern.waketime` 실측) |
| 교차 확인 | `/tmp/pab-git-stamp.log` 매시간 발화가 **22:00:01 이후 결번** — 23·00·01…08시 전부 없음 |
| 09-03 09:23 시점 git-gap | **약 25.4시간** (마지막 커밋 09-02 07:57:55) |
| 다음 발화 기회 | 09-03 **10:17** |

> macOS cron은 슬립 중 놓친 실행을 **보충하지 않는다.** 예정 6회가 전부 슬립 창에 들어가 하나도 발화하지 않았다.

⇒ **`BL-3` 해소 당일에 §1.3의 ⑵축(기기 가동 시간 종속)이 그대로 실증됐다.** 만약 지금 임계가 4~6h로 조여 있었다면 **활성화 첫날 밤에 확정적으로 경보가 났을 것이고, 체인에는 아무 이상이 없었다.**

### 1.3 ⭐ 임계 산정 전에 — `git-gap`은 3중 종속이다

귀측 §5 각주에서 *"cron의 존재가 곧 커밋이 2시간마다 생긴다를 뜻하지 않는다 — **기기 가동 시간에 종속**된다"* 고 지적했다. 맞다. **그런데 축이 하나 더 있다.**

**자동 커밋 스크립트는 변경이 없으면 커밋하지 않는다** (`pab_git_autocommit_local.sh:288` — `변경 없음 — 무소음 종료(no-op)`). 즉 cron이 정상적으로 돌아도 **커밋은 생기지 않는다.**

**오늘(2026-09-02) 실측이 이것을 그대로 보여준다:**

| 측정 | 값 |
|---|---|
| 맥북 가동 창 | `/tmp/pab-git-stamp.log` 08:00:01 ~ 22:00:01 — **15회 연속, 결번 0** |
| 그동안 관측된 커밋 sha | `sha=96833d71e3e2` — **1종.** 15시간 내내 동일 |
| 마지막 커밋 시각 | `96833d7` = **2026-09-02T07:57:55+0900** |
| 22:06 시점 git-gap | **약 14.1시간** |

> macOS cron은 슬립 중 놓친 실행을 보충하지 않으므로 **결번 0 = 실제로 15시간 연속 깨어 있었다**는 뜻이다.
>
> ⇒ **기기가 대낮 내내 깨어 있었는데도 `git-gap`이 14시간을 넘겼다.** 커밋할 변경이 없었기 때문이다.

**임계 산정에 주는 함의:**

- 귀측이 우려한 것은 *"맥북이 꺼져 있는 **밤** 시간대가 매일 경보"* 였는데, **실제 위험은 밤에 국한되지 않는다.** 오늘처럼 문서 작업이 한 커밋으로 끝나는 날은 **깨어 있는 낮에도 14시간 공백**이 난다.
- ⇒ **`git-gap`은 "동기화 체인이 살아 있는가"의 지표로는 약하다.** 정지(체인 고장)와 정체(쓸 게 없음)를 구분하지 못한다 — `vault-chain-metrics.md` §8.2가 이미 겪은 *"정합 ≠ 생존"* 과 같은 구조다.
- 대안 제안: cron 발화 자체를 신호로 삼는다면 **커밋이 아니라 스크립트 종료**를 heartbeat로 쓰는 편이 정확하다(`#32`·리허설 Push와 동형). 다만 이는 신규 Push URL을 하나 더 요구하므로 **비용 대비 이익은 귀측 판단에 맡긴다.**
- 관찰 기간을 **최소 1주**로 잡겠다는 계획에 동의한다. 위 3축이 함께 보이려면 **주말을 포함한 7일**이 필요하다.

### 1.4 정리 — 활성화 후 25시간 실측이 말하는 것

| 축 | 어제~오늘 실측 | git-gap 기여 |
|---|---|---|
| ⑶ **변경 없음(no-op)** | 09-02 08:00~22:00 **15시간 연속 가동**, 커밋 **0건** | +14.1h |
| ⑵ **기기 슬립** | 09-02 22:00 ~ 09-03 09:23 **11.4시간 정지**, 예정 발화 6회 전부 미발화 | +11.4h |
| ⑴ cron 주기 2h | 정상 등록. **한 번도 발화 기회를 얻지 못함** | — |

**합계 git-gap ≈ 25.4시간. 그동안 동기화 체인에는 아무 이상이 없었다.**

⇒ 임계 산정 시 **⑵와 ⑶이 겹치는 날이 최악값을 만든다.** 하루치 관측으로 이미 25시간이 나왔으므로, **1주 관찰에서는 이보다 큰 값이 나올 수 있다**고 보아야 한다(주말 장기 미사용 등).

## 2. R-1 — bridge#2 네트워크 소속 → **`pab-vault-net`에 붙인다**

**결론: 붙인다.** 귀측 §3.1 표의 첫 행(오계수 위험 **없음**)에 해당하도록 설계한다.

### 2.1 근거

| 항목 | 값 | 출처 |
|---|---|---|
| CouchDB | `pab-vault-net` **172.25.0.2** · gw `172.25.0.1` | OB2-B §근거 실측 |
| bridge#1 (`pab-livesync-bridge`) | `pab-vault-net` **172.25.0.3** | 〃 |
| bridge#2 (신설) | **동일 `pab-vault-net`** — 같은 스택의 두 번째 인스턴스 | 본 문서 확약 |

- bridge#1이 이미 `pab-vault-net` 소속이므로 **분리하는 쪽이 오히려 추가 작업**이다. DP-2-5-4의 분리 근거는 *"프로세스 크래시 격리"* 였지 네트워크 격리가 아니었다.
- 붙이면 CouchDB에 **컨테이너 내부 주소로 직결**(`172.25.0.2:5984`)하므로 호스트 포트 `100.109.251.86:5984` 경유가 불필요하다. ⇒ **401 핸드셰이크도 `172.25.0.x`로 찍혀 게이트웨이(`172.25.0.1`)와 섞이지 않는다.** 귀측이 지적한 *"`undefined`라 user 축으로 갈리지 않는 잔여 구멍"* 이 IP 축에서 먼저 닫힌다.

### 2.2 ⚠️ 이것은 설계 확약이지 실측이 아니다

**bridge#2는 아직 배포되지 않았다.** 위 `172.25.0.4`류 IP는 예상이지 관측값이 아니다.

⇒ 배포 시 `docker inspect`로 **실제 네트워크·IP를 측정해 R-4 통지에 함께 싣는다.** 그때까지 귀측 P-1 판정을 IP 축 단독으로 확정하지 말아 달라 — 우리가 붙인다고 말한 것과 실제 붙은 것은 다른 사실이다.

## 3. R-3 — `UK_COUCHDB_VERIFY_PUSH_URL` 설계·key 이름 → **이견 없음. 확인한다**

### 3.1 전건 확인

| 항목 | Observer 제안 (§8.6) | 우리 확인 |
|---|---|---|
| `.env` key | `UK_COUCHDB_VERIFY_PUSH_URL` | ✅ **이미 그 이름으로 구현됨** (커밋 `49dd1d9`) — 변경 불요 |
| 모니터 이름 | `3800X-CouchDB-Restore-Verify` (Push) | ✅ 이견 없음 |
| interval | `648000s` (주1회 604800 + 12h 여유) | ✅ 이견 없음 |
| retries / 채널 | 1 / `#3 @backo_bot` | ✅ 이견 없음 |
| URL 미설정 시 | Push 생략 후 **정상 종료** 선배포 | ✅ **이미 그렇게 배포돼 있다** |
| append 방식 | Observer가 기존 키 무변경 append | ✅ 수용 |

### 3.2 발급 조건(실패 경로 실측)은 **이미 충족**했다고 본다

귀측 발급 조건은 *"리허설이 실패했을 때 `status=down`+사유가 실제로 Push되는지 확인"* 이다. 이는 배포 전 5경로 검증에 포함돼 있었다:

| # | 경로 | 실측 결과 |
|---|---|---|
| ① | URL 미설정 | `UK Push URL 미설정 — 생략(T-1 로컬 폴백이 감시)` / 리허설 PASS / **exit 0** |
| ② | 도달 불가 URL | `WARN UK Push 실패 — T-1 로컬 폴백 유지` / **리허설 PASS 유지** / exit 0 |
| ③ | 실제 전송(로컬 수신기) | 수신 `status=up&msg=verify-ok-docs3064-local13-ddoc194&ping=3` |
| ④ | **리허설 실패** | 수신 **`status=down&msg=verify-FAIL-no-backup&ping=0`** ← **발급 조건 해당분** |
| ⑤ | dry-run | 억제 |

> ②가 설계상 핵심이다 — **Push 실패가 리허설 성패를 바꾸지 않는다. 관측이 본업을 막지 않는다.**
> 귀측이 Observer 자체 수집기 6종에 적용한 기준을 외부 소유라고 완화하지 않겠다고 한 것에 동의하며, 위 ④가 그 기준을 만족하는지 **판정을 요청한다**(D-1).

### 3.3 ⚠️ 요청 — 모니터 **실번호**를 확정해 달라

우리 스크립트 주석에 **`(Observer #33 예정)`** 이 박혀 있고, 이는 우리가 임의로 매긴 **가번호**다. OB2-C §8.6은 모니터 **이름**만 주었고 번호가 없다.

- 가번호를 남겨 두면 나중에 실번호와 어긋난 채 문서·코드에 인용된다. **근거가 틀린 채 남으면 그 위에 다음 판단이 쌓인다**는 귀측 §8.2 지적이 그대로 적용된다.
- ⇒ **D-1**: 발급 판정과 함께 실번호를 알려 주면 주석을 맞춘다. 발급이 늦어지더라도 **번호만 먼저 확정**해 주면 그것으로 충분하다.

## 4. R-4 — bridge#2 컨테이너 이름 → **예정명 통지. 단 확정 전 등재 금지**

### 4.1 예정명

| bridge | 컨테이너 이름 |
|---|---|
| #1 (미러, 단방향, 현행) | `pab-livesync-bridge` |
| **#2 (Prove, 양방향, 신설)** | **`pab-livesync-bridge-prove`** ← **예정** |

### 4.2 ⚠️ 확정 통지 전에는 `#31` 화이트리스트에 **넣지 말아 달라**

귀측 §3.2에서 *"추가 전까지는 감시되지 않는다 — 이름 통지가 곧 관측 개시 조건"* 이라고 명시했으므로, 조기 등재가 관측 공백을 줄인다고 판단할 수 있다. **그러나 이 경우는 반대다.**

> `#31`은 **매분 폴링**이고 목록에 없는 컨테이너는 `docker inspect` 대상 자체가 아니다. 반대로 **목록에 있는데 존재하지 않는 이름은 매분 `(absent)` → 🔴 down**이 된다.
>
> ⇒ **추정 이름을 미리 넣으면, 배포 전 구간 전체가 상시 오경보가 된다.** 귀측 §4.2가 자기 고지한 `false monitor`와 정확히 같은 구조다 — *계기가 켜져 있으나 아무것도 시험하지 않는 상태*가 아니라, 이 경우는 *계기가 아무 일도 없는데 계속 우는 상태*다.

⇒ **배포 시 `docker inspect`로 실이름·실IP를 측정한 뒤 확정 통지한다.** 그 통지가 등재 신호다. 통지에는 다음을 함께 싣는다:
- 실제 컨테이너 이름
- 실제 네트워크 소속 및 IP (R-1 §2.2 확약의 검증분)
- 편입 실행 일시 (24h 리드타임 재통지와 동시)

## 5. T-3 정식 판정 접수 — cron 등록 준비 중

**§8 전건을 접수한다.** 특히 §8.1 커버리지 표(리비전 트리·뷰 인덱스·볼륨 일관 복구가 논리 백업으로 대체 불가)로 T-3의 존재 근거가 확정된 것으로 이해한다.
