# [OB1] vault 이원화 크로스 체크 점검 요청 (PAB-Observer → PAB-obsidian)

> **SSOT 배지**: 원본 = **PAB-Observer**(authority). PAB-obsidian 측은 **읽기전용 수신본**(수정 금지, 갱신은 PAB-Observer 재전달).
> **발신** 2026-08-24 · **성격** 관측 계약 개설 + vault 이원화 정합 점검 · **회신 대기**(§6)
> **경계**: obsidian = vault 정의·전파 계약(무엇이 정보이고 무엇이 개발 데이터인가) / Observer = 4홉 체인 관측·임계. **Observer는 vault에 쓰지 않는다**(R-1 단일 writer 원칙 준수).

---

## 0. 왜 이 요청인가

vault가 **두 벌**이라는 사실 자체는 확인했다 — `PAB-LLMDATA`(정보) / `PAB-LLMDATA-prove`(개발용 데이터). 문제는 **관측 체인이 그중 한 벌만 보고 있고, 다른 한 벌은 아무도 보지 않으면서 매일 커지고 있다**는 것이다.

2026-08-21 재부팅 레이스로 홉1(CouchDB)이 3일간 정지했을 때, 3자 일치 지표는 **정지 내내 정상(102==102==102)이었다**. 정합성은 "흐르고 있음"을 뜻하지 않는다. 이 사건을 계기로 vault 이원화 구조 전체를 실측했고, 아래 §2에 확인 요청 사항을 정리했다.

## 1. 실측 결과 (2026-08-24)

### 1.1 두 vault의 현재 좌표

| vault | 성격 | 로컬 경로 | 전체 `.md` | 화이트리스트<br>(`10_Notes`+`15_Sources`) |
|---|---|---|---:|---:|
| **PAB-LLMDATA** | 정보(운영) | `PAB-obsidian/PAB-LLMDATA` | 150 | **102** |
| **PAB-LLMDATA-prove** | 개발용 데이터 | `~/WORKS/PAB-LLMDATA-prove` | 190 | 140 |

### 1.2 운영 체인 — 4자 정합 ✅

```
PAB-LLMDATA(로컬 102) → LiveSync → CouchDB pab-llmdata(102)
   → livesync-bridge → 미러 /home/oceanui/pab-vault-mirror(102)
   → :ro 마운트 → PAB-v4 /vault-mirror(102) → Qdrant distinct document_id(102)
```

**미러 102 == 컨테이너 vault 102 == Qdrant distinct doc 102**, 연동 게이트 **ON**. 정보 vault는 설계대로 흐르고 있다.

### 1.3 개발 체인 — 관측 밖에서 성장 중 ⚠️

```
PAB-LLMDATA-prove(로컬 140) --rsync 시딩--> 3800X /home/oceanui/pab-wiki-vault
                                              현재 화이트리스트 200 (전체 262)
```

- 서버 vault 커밋 이력: `chore(vault): 초기 시딩 — PAB-LLMDATA-prove 전량 복제`(deploy.sh) 이후 PAB-Prove 워커가 계속 write.
- **로컬 140 → 서버 200: 서버에서 약 60건이 신규 생성**됐고 로컬로 회수되지 않는다(단방향).
- **오늘도 생성 중**: `10_Notes/2026-08-24_reddit.md` + `15_Sources/2026-08-24_reddit_source.md`.
- 이 vault는 **CouchDB·미러·PAB-v4·Qdrant 어디에도 전파되지 않는다**. PAB-Prove 배포본이 `WIKI_ENV=dev` · `WIKI_CANONICAL_VAULT=/canonical-vault-not-mounted` 가드를 켠 채 도는 **의도적 격리**로 보이나, 그 격리의 **해제 조건·시점이 문서화되어 있지 않다**.

### 1.4 문서–실태 불일치 (정정 필요)

Khala `docs/interop/pab-prove/README.md` §1은 PAB-Prove를 이렇게 기술한다:

> "SOURCE(불변)+요약 2파일을 Obsidian vault(**`PAB-LLMDATA`**)에 생성 → LiveSync 전파"

**실태는 다르다.** 배포본이 쓰는 곳은 `pab-wiki-vault`(= `PAB-LLMDATA-prove` 복제본)이고 LiveSync 전파는 일어나지 않는다. 계약 문서가 미래 목표를 현재형으로 적은 것으로 보이며, 이 상태로는 **"PAB-Prove가 만든 노트가 지식베이스에 들어가 있다"는 오해**를 부른다. authority는 PAB-Prove이므로 정정은 그쪽 소관이나, vault 정의의 SSOT인 obsidian 측 인지가 필요해 여기 기록한다.

## 2. 확인 요청 항목

| # | 항목 | Observer의 실측·이해 | 확인 요청 |
|---|------|---------------------|-----------|
| **O-1** | **vault 2종의 authority 확정** | `PAB-LLMDATA` = 정보(운영 SSOT) / `PAB-LLMDATA-prove` = 개발용 데이터. 관측 체인(#25·#26)은 **전자만** 대상으로 한다. | 이 경계를 **문서로 고정**해 주기 바란다. 특히 개발 vault가 향후에도 운영 체인에 편입되지 않는지. |
| **O-2** | **PAB-Prove 산출물의 승격 경로** | 현재 `pab-wiki-vault`(개발 복제본)에만 쌓이며 운영 전파 0. `WIKI_ENV=dev` 가드가 켜져 있다. | 이 격리는 **의도된 PoC 단계**인가? 승격(운영 vault write 또는 병합) **조건·시점·경로**는? 승격 없이 계속 쌓이면 60건이 600건이 되고 회수 비용이 커진다. |
| **O-3** | **승격 시 관측 임계 재산정** | 승격되면 화이트리스트 모집단이 **102 → 200+로 급증**한다. `#26`은 drift(미러≠CouchDB)·3자 일치를 **불일치 시 🟠**로 올리므로, 전파 진행 중 과도기에 **대량 오경보**가 예상된다. | 승격을 실행하기 **전에 Observer에 통지**해 주기 바란다. 통지받으면 ⑴ drift 임계 일시 완화 ⑵ 화이트리스트 baseline 재동결(현 동결값 49 → 실측 102 → 승격 후 값)을 선반영하겠다. |
| **O-4** | **서버 증분 60건의 회수 정책** | 개발 vault 서버본에만 존재하는 노트 약 60건이 로컬로 돌아오지 않는다. 서버 vault는 git 저장소이나 원격 push 대상이 없다(실측). | 이 60건은 ⒜ 검증용 폐기 대상인가 ⒝ 회수해야 할 자산인가? ⒝라면 회수 절차가 필요하고, 그 전까지 **서버 vault 유실 위험**을 Observer가 감시해야 하는지 판단이 필요하다(현재 무감시). |
| **O-5** | **운영 vault 저활동이 정상인가** | 미러 최신 mtime **2026-08-17 10:22**, 로컬 `PAB-LLMDATA`는 8/10 이후 4건 수정. 반면 개발 vault는 같은 기간 71건. `sync_lag`이 596,000초대이나 **idle 볼트 억제 규칙**(`seqΔ=0`이면 경보 안 냄)으로 🟠는 발생하지 않는다. | 운영 vault의 **7일 무갱신이 정상 운영 리듬**인가? 정상이면 현행 억제 규칙 유지, 아니라면 "N일 이상 무갱신"을 별도 🟡 지표로 추가하겠다. **현재는 정체와 정지를 구분하지 못한다.** |

## 3. Observer 측 관측 공백 자인 (회신 불요 — 조치 예정 고지)

- **개발 vault(`pab-wiki-vault`) 무감시**: 노트 생성이 멈춰도 Observer는 모른다. O-2 회신이 "PoC 지속"이면 경량 지표(파일 수 추이·최신 mtime)를 `#31`에 얹는 것을 제안한다. 승격 예정이면 그때 `#26` 체인에 정식 편입한다.
- **정합≠생존**: 홉1이 3일간 죽어 있는 동안에도 3자 일치는 정상이었다. 정지 탐지는 `#25`(CouchDB `/_up`)와 `#31`(bridge 컨테이너 running)이 담당하도록 분업을 문서에 명시했다(`vault-chain-metrics.md` v1.2 §8.2). **3자 일치를 생존 신호로 읽지 말 것.**
