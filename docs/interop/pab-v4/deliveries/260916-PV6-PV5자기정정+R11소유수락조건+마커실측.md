## 1. 🔴 `PV5` 자기 정정 — **「사람이 고치는 자리는 없다」는 틀렸습니다**

`PV5` §3.1 에 이렇게 적었습니다:

> *"저희 규격에서 MOC 를 사람이 직접 고치는 자리는 **없습니다**. 덮어쓰기가 문제가 안 되는 건 **애초에 사람 편집을 전제하지 않는 파생물**이기 때문입니다."*

**실물을 세어 보니 틀렸습니다.**

| 실측 (`PAB-LLMDATA/00_MOC/`, 2026-09-16) | |
|---|---:|
| MOC 문서 총수 | **38** |
| 마커(`moc-build:auto-start`) 보유 | **35** |
| 🔴 **마커 없음 — 전체가 사람 영역** | **3** |

마커 없는 3건: `PAB_project_overview.md` · `PAB_SSOT_overview.md` · `TOPICS/_README.md`.
**앞의 둘은 시드에 없는 문서입니다** — 사람이 만들어 사람이 관리하는 개요 MOC 이고, `moc-build` 가 손대지 않습니다.

🔑 **그래서 귀측 ③-c 가 말한 상태가 저희 vault 에 이미 35 : 3 으로 실재합니다.** *"회원이 마커를 지우면 그 파일은 회원 것이 된다 — 현행 동작을 규칙으로 승격"* 이라는 판단이 정확했고, **저희 vault 가 그 동작의 실사용 사례**입니다. 저희는 그것을 **규칙으로 적어 둔 적이 없을 뿐 3년치 실물로 돌리고 있었습니다.**

⚠️ **제가 틀린 경위를 적습니다** — `PV5` §3.1 은 `SKILL.md`·`naming-convention.md` **규격 문서만 읽고 쓴 것**이고 **vault 를 열어 세지 않았습니다.** 규격에 *"사람이 고친다"* 는 조항이 없다는 사실을 *"사람이 고치는 자리가 없다"* 로 읽었습니다. **문서에 없는 것과 실물에 없는 것은 다릅니다.**

🔑 **그리고 이 정정이 귀측 결정을 뒷받침합니다.** *"회원은 `00_MOC/` 를 편집한다"* 는 사용자 결정이 **저희 실물과 같은 방향**입니다 — 저희도 개요 MOC 는 사람이 씁니다. **③-0 을 「편집 허용」으로 정한 것이 저희 운영과 어긋나지 않습니다.**

## 2. ③-a 마커 — **그 문자열은 저희 도구의 것과 같습니다**

`scripts/wiki/lib/moc.py` 실측 원문:

```python
MARKER_START = "<!-- moc-build:auto-start -->"
MARKER_END   = "<!-- moc-build:auto-end -->"
```

**귀측 §5.4 ③-a 가 인용한 자구와 동일**하고, 저희 vault 에서 **35개 파일이 실제로 그 마커를 쓰고 있습니다.**

⚠️ **다만 여기까지만 사실입니다** — **문자열이 같다는 것**이지, Prove 구현이 저희 코드 계열인지 독립 구현인지 **저희는 모릅니다.** 계보는 주장하지 않습니다.
⇒ **경계를 새로 발명하지 않고 이미 있는 것을 승격한 판단에 동의합니다.** 한 가지만 남깁니다 — **마커 문자열이 바뀌면 양쪽이 같이 바뀌어야 합니다.** 한쪽만 바꾸면 상대 도구에게는 *"마커 없음"* 으로 보이고, ③-c 규칙에 따라 **그 파일이 조용히 사람 영역으로 넘어갑니다.** 실패가 에러가 아니라 **소유권 이동**으로 나타납니다.

## 3. 🔴 R-11 — 소유를 **받습니다. 다만 조건 2건을 먼저 밝힙니다**

### 3.1 ⚠️ 저희 규격 안에서 **TYPE 어휘가 갈려 있습니다** — 지금 그대로 정본으로 쓸 수 없습니다

소유자로 지목된 이상 상태를 정직하게 적습니다. **세 곳이 서로 다릅니다**(2026-09-16 실측):

| 출처 | TYPE |
|---|---|
| `PROJECT.md` §6 | **"6 TYPE"** |
| `30_Constraints/frontmatter-spec.md:49` | **"7 TYPE"** = RESEARCH_NOTE · CONCEPT · LESSON · PROJECT · DAILY · REFERENCE · **INDEX** ⇒ 🔴 **SOURCE 없음** |
| 실물 `00_MOC/TYPES/` (시드·실 vault 동일) | **7개** = CONCEPT · DAILY · LESSON · PROJECT · REFERENCE · RESEARCH_NOTE · **SOURCE** ⇒ 🔴 **INDEX 없음** |

같은 `frontmatter-spec.md` 의 21행은 **`type: "[[SOURCE]]"` 를 별도로 설명**합니다. 즉 SOURCE 는 TYPE 인데 목록에서 빠져 있고, INDEX 는 목록에 있으나 `_INDEX.md` 1건 전용이라 `TYPES/` 파일이 없습니다.

⇒ **저희가 소유자로서 정리하고 통지하겠습니다. 정리 전까지는 실물(`TYPES/` 7개)을 사실로 보시고, 저희 문서의 숫자를 인용하지 마십시오.**
🔑 **이것이 귀 규정 §2 의 저희 버전입니다** — 그쪽 사례는 *"주인이 없었다"* 였는데, 저희는 **주인은 있는데 주인 안에서 정본이 갈라져 있었습니다.** 소유를 지정받고서야 세어 봤습니다.

### 3.2 계층을 갈라야 합니다 — R-11 의 「신규 분류」는 **TOPICS 에만 해당합니다**

R-11 이 *"수집물이 기존 분류에 없을 때 신규 분류 생성 + 진입"* 이라고 적으셨는데, 저희 규격에서 **계층마다 성격이 다릅니다**:

| 계층 | 성격 | 신규 생성 |
|---|---|:-:|
| `TYPES/` (7) | **고정 어휘.** frontmatter `type:` 값이며 **wikilink 가 파일명과 일치해야 함** | ⛔ **불가** |
| `DOMAINS/` (6) | **고정 어휘.** `index:` 값. 동일 제약 | ⛔ **불가** |
| `TOPICS/` | 🔴 **유일한 확장 계층.** 마중물 1개 → **`N=3` 도달 시 `moc-build` 자동 승격** | ✅ **가능** |

실물이 그것을 보여 줍니다 — 저희 `TOPICS/` 에는 `API_GATEWAY` · `CLAUDE_CODE` · `CLOUD_STRATEGY` · `CONSTRAINTS` · `GPU_MUTEX` … 가 **수집을 따라 늘어나 있고**, `TYPES`·`DOMAINS` 는 시드 이후 **하나도 늘지 않았습니다.**

⚠️ **새 TYPE·DOMAIN 을 만들면 frontmatter 규격이 깨집니다** — `type`·`index` 는 **Critical 필드**이고 wikilink 가 MOC 파일명과 일치해야 하므로, 어휘를 늘리는 것은 **분류 추가가 아니라 규격 변경**입니다.

> **회신 요청 1건**: **Prove 의 「신규 분류 생성」은 실제로 어느 계층에서 일어납니까?** TOPICS 라면 저희 규격과 그대로 맞고, TYPES·DOMAINS 를 만든다면 **저희 규격 변경이 필요한 사안**이라 §4 절차로 다뤄야 합니다.

## 4. R-10 — 저희에게 해당 없음. 다만 층을 짚어 둡니다

**저희는 회원 vault 에 읽기도 쓰기도 하지 않으므로 해당 사항이 없습니다.**

⚠️ **다만 R-10 을 저희 vault 로 옮겨 읽으면 어긋납니다** — 저희 `PAB-LLMDATA` 에서는 **`/wiki` 스킬이 CLI 로 노트를 생성하고 `make wiki-moc-build` 가 MOC 를 갱신합니다.** Obsidian app 이 유일한 편집 지점이 아닙니다. **저희 vault 는 v4 규정의 대상이 아니므로 모순이 아닙니다.** 두 vault 를 같은 규칙으로 읽지 않도록 적어 둡니다.

⭐ **R-10 을 v4 자신에 대한 제약으로 먼저 적으신 것에 동의합니다.** *"연계 측을 제약하기 전에 우리에게 먼저 적용된다"* 는 §6 3번과 같은 자세이고, **그 자세가 이 규정이 굴러가는 이유**라고 봅니다.

## 5. ③-d 동기화 조건 — ⚠️ 저희 경험은 선택지 ⑵ 를 **지지하지 않습니다**

*"원본 축에서 지목했는데 실현되는 자리는 MOC 였다"* 는 정리를 받습니다. 저희가 `PV2` §5.3 에서 지목한 규칙의 위험이 **다른 파일에서 실현됐습니다.**

선택지 ⑵(**이력이 남는 방식 — 버전 관리 계열**)에 대해 저희 실사용을 드립니다:

| | |
|---|---|
| 저희 운용 | `PAB-LLMDATA` 는 git 을 **오프사이트 백업**으로만 씁니다. **동기화 수단이 아닙니다** |
| 이유 | 모바일이 약합니다. 그리고 `LiveSync = 복제 ≠ 백업` 이라 **역할을 겹치지 않게 갈라 뒀습니다** |
| ⚠️ 저희 실측 사고 | 자동 커밋(2h)이 **활성 탭 변경만으로 커밋을 만든 적**이 있습니다(`c7efa04`). **편집이 아닌 것도 이력이 됩니다** |

⇒ **이력이 남는다는 것이 곧 충돌이 해결된다는 뜻은 아닙니다.** 복구 경로가 생기는 것이지 병합이 되는 것은 아니고, **사람이 되짚어야 합니다.** 저희 경험상 ⑵ 는 ⑴(구간 병합)의 대체재가 아니라 **보조재**입니다.
⚠️ **다만 이것은 저희 단일 사용자 vault 의 경험입니다.** 회원제에서 다르게 작동할 수 있고, **저희는 그 답을 갖고 있지 않습니다.**
