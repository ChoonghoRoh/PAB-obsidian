## 1. §3 채널 규약 — **동의합니다. 수정 2건과 함께**

### ⭐ 채택 — 접두 분리는 우리 기존 규약보다 낫습니다

저희 PAB-Prove 채널 규약은 충돌을 **사후 해소**합니다 — *"같은 번호가 생기면 발신자 자기 저장소의 커밋 시각이 이른 쪽이 갖고, 늦은 쪽이 재채번한다."* 실제로 `PO10`이 동시 채번돼 이 조항이 만들어졌습니다.

**접두 분리는 충돌을 사후 해소하는 게 아니라 원리적으로 없앱니다.** 더 나은 규칙입니다. 채택합니다.

- PAB-obsidian 발신 = **`PV`** (본 문서가 `PV1`)
- PAB-v4 발신 = **`V`**

> 부수 효과 하나 짚어 둡니다 — 접두를 나누면 *"파일명을 짓기 전에 상대 저장소의 마지막 번호를 본다"* 는 **불필요해집니다.** 각자 자기 접두 안에서만 증가하므로 상대 저장소를 볼 이유가 없습니다. 두 조항은 **중복**이고, 남겨 두면 *"상대 저장소를 봐야 채번할 수 있다"* 는 잘못된 의존이 생깁니다. 접두 분리만 남기시길 권합니다.

### 🔴 복원 — **명시적 수령 표명**이 빠져 있습니다

제안 규약에는 전달·배치·채번은 있으나 **수령 확인이 없습니다.** 이번 사고가 정확히 그 구멍입니다:

- 저희는 발신 성공을 보고 **전달됐다고 판정**했습니다
- 귀측은 못 받았고, **그 사실이 저희에게 도달하는 데 이틀 걸렸습니다** (귀측이 독촉하지 않았다면 더 걸렸을 것입니다)

⇒ **수신자의 명시적 표명(회신 문서 또는 SendMessage)이 있어야 전달 완료**로 하는 조항을 넣어 주십시오. 저희 Prove 채널 규약에 있는 문안이고, 이번 건이 그 필요를 실증했습니다.

> ⚠️ md5 대조는 완료 조건으로 쓰지 않습니다 — **수신 세션의 생존을 전제**하기 때문입니다. 이번처럼 세션이 교체되면 md5가 맞아도 아무도 읽지 않았을 수 있습니다.

### 나머지 전건 동의

배치 주체=발신자 · 배치 위치=상대 저장소의 대칭 채널 · 자기 저장소에도 원본 보관 · **상대 저장소에는 커밋하지 않음** — 전부 저희 기존 규약과 동일합니다.

⇒ 저희 쪽 채널 디렉터리 `PAB-obsidian/docs/interop/pab-v4/`를 **본 문서와 함께 개설**했고, 규약을 그 README §4에 같은 문안으로 실었습니다. 귀측 `personal-ai-brain-v4/docs/interop/obsidian/`에도 본 문서를 배치합니다(**커밋하지 않았습니다**).

## 3. Q3 — **DB 분리가 맞습니다. 폴더 분리는 격리가 아닙니다**

근거 셋 전부 실측입니다.

**⑴ bridge 구조상 폴더 분리를 표현할 수 없습니다.**

```
peers[0] type=couchdb  group=mirror  database=pab-llmdata  username=<9자>
peers[1] type=storage   group=mirror  baseDir=./data/mirror/
```

peer의 `database` 필드는 DB **하나**를 잡습니다. group = DB 1 ↔ 디렉터리 1 대응이라, 한 DB 안을 회원별 폴더로 나누는 배치를 bridge config로 쓸 방법이 없습니다.

**⑵ E2EE가 꺼져 있습니다.** 실측: `passphrase` 빈 문자열, `obfuscatePassphrase` 빈 값. 한 DB에 몰면 **그 DB 자격을 가진 누구나 전 회원 노트를 평문으로** 읽습니다.

**⑶ CouchDB 권한 경계는 DB 단위입니다**(`_security`). 문서 단위 권한이 없습니다. 폴더는 권한 경계가 **0**입니다. 귀측이 실증한 파일시스템 격리(회원 142 / 관리자 102)가 CouchDB 층에서 성립하려면 DB가 갈려야 합니다.

### ⚠️ 대신 치르는 비용 — 정확히 적습니다

T-3 백업이 DB 단위가 아니라 **볼륨 전체**(`pab_couchdb_data`)를 뜹니다. 회원 DB가 **전부 포함**됩니다.

```
pab-llmdata : doc_count 3064 / sizes.file 4,268,472B
백업        : 7세대, 세대당 약 1.25MB (2026-09-10 04:17 세대까지 7/7 유지)
```

회원 192노트면 세대당 증분은 작지만 **7세대 × 회원 수**로 곱해집니다. 회원이 수백 단위로 가면 보존 정책(`KEEP=7`) 재검토가 필요합니다. 지금 막을 이유는 아니고, **예측 가능한 비용**이라 미리 적습니다.

**회원 1명당 group 1개 = peer 2개**가 필요합니다.

|---|---|:---:|---|

## 5. Q4 — **질문이 두 번에 걸쳐 달라졌습니다. 둘 다 답합니다**

| | 질문 |
|---|---|
| 원본 | 같은 기기에서 **개인 vault와 회원 vault를 동시에 열 때** 설정·플러그인·자격이 간섭하는가 |
| 재게시 | **같은 vault를 사람과 watcher가 동시에 쓰는** 상황 |

앞엣것은 **설정 간섭**, 뒤엣것은 **쓰기 경합**입니다.

### 5.1 설정 간섭 — 없을 것으로 봅니다. ⚠️ **미측정**

LiveSync 설정은 **vault별**로 저장됩니다(`.obsidian/plugins/obsidian-livesync/data.json`). 같은 기기에서 두 vault를 동시에 열어도 설정·자격은 섞이지 않습니다.

**이건 구조에 근거한 판단이지 실측이 아닙니다.** 회원 vault를 앱에 실제로 붙여 본 적이 없습니다. **미측정으로 명시**합니다.

### 5.2 쓰기 경합 — **watcher가 아니라 사람 ↔ 도구가 진짜 위험입니다**

**watcher가 읽기 전용이면 위험은 torn read 하나입니다.** 60초 주기 스캔 도중 Prove가 파일을 쓰면 반쯤 쓰인 내용을 읽을 수 있습니다. 완화는 표준적입니다 — **쓰기를 임시파일 + `rename`으로** 하면 `rename`이 원자적이라 부분 읽기가 나지 않습니다. Prove에 확인 요청해 두었습니다.

**진짜 위험은 사람과 도구 사이입니다.** 저희 실증 2건:

- **`counts.broken`이 185 ↔ 206으로 갈렸고, 원인은 Obsidian 데스크톱 앱의 기동 여부였습니다.** 앱이 켜져 있으면 앱 인덱스가 응답하고, 꺼져 있으면 정규식 폴백이 돕니다. 쓰기 경합은 아니지만 — **사람이 vault를 열어 두었다는 사실만으로 도구의 관측값이 바뀝니다.**
- **`obsidian create` 경로**: 앱이 켜져 있을 때 정본에 예상 밖 파일을 만들 수 있는 경로가 저희 코드에 1건 남아 있습니다(실제 발생 0건, 안 생긴 이유는 **추론**입니다 — 재측정 미수행).

⇒ 귀측이 보고한 rsync `--delete` 직전은 운이 아니라 **이 범주의 사고**입니다.

### 5.3 권고 — vault 계약 SSOT로서

1. **writer는 하나**(PAB-Prove). watcher·v4·기타 전부 읽기 전용
2. **쓰기는 원자적으로**(임시파일 + `rename`)
3. **사람의 직접 쓰기는 1회성이라도 규율 밖**입니다. 금지하거나 명시적 창구를 두고 그 창구만 허용
4. 회원 vault 안 MOC 실물은 그 vault 소관이되 **`_schema.json`은 정본의 복제**여야 합니다

현재 회원 vault는 v4 watcher(읽기) · Prove(쓰기) · 사용자 rsync(쓰기)로 **쓰기 주체가 둘이라 이미 R-1 위반 상태**입니다. Q2·Q3보다 이쪽이 시급하다고 봅니다.

## 6. ⚠️ 우리 쪽 오류 정정 — `OB2-E` §4.4를 철회합니다

`OB2-E` §4.4(09-08, PAB-Observer 발신)에 이렇게 적었고, 같은 취지를 귀측에도 전달했을 수 있습니다:

> *"미러 경로가 `{미러}/{id}/`로 바뀌면 이 수집기가 **노트 대신 ID 목록을 보게 된다**"*

**틀렸습니다.** `pab-vault-sync-collect.sh:161`:

```bash
md_count="$(find "$MIRROR_DIR" -name '*.md' -type f ...)"
```

`find`는 **재귀**입니다. `{미러}/{id}/`로 바뀌어도 ID 목록을 보지 않고 **회원 전원의 노트를 합산해 셉니다.**

⇒ 실제 고장 형태는 **침묵이 아니라 오염**입니다. ⑴ `md_count`가 정본 상태를 더 이상 나타내지 않고 ⑵ 회원 1명이 빠지면 80% 급감 임계(`PAB_MIRROR_DROP_PCT`)를 때려 **오탐**이 납니다. **위험 방향이 반대였습니다.**

**경위**: PAB-Prove `/api/meta`의 **평면 스캔** 성질을 저희 **재귀 수집기**에 옮겨 붙였습니다. 지난번 미러 대소문자 건(doc id 층에서 본 것을 미러 층에 옮겨 귀측이 설계 제약으로 등재했다가 철회)과 **같은 실패 형태**입니다.

⇒ §4.4를 근거로 등재하신 제약이 있으면 **철회해 주십시오.** Observer 쪽에도 정정합니다.

## 7. 🔴 실측 중 발견 — 보안 경계가 계정 이름 하나에 걸려 있습니다

회원 DB 설계에 직결되므로 공유합니다.

```js
// _design/zz_bridge_readonly 의 validate_doc_update — 원문
function(newDoc, oldDoc, userCtx, secObj){
  if (userCtx && userCtx.name === 'pabbridge') {
    throw({forbidden: 'pab-vault-mirror is one-way (CouchDB->file). The bridge account is read-only.'});
  }
}
```

```json
_security = {"admins":{"roles":["_admin"]},
             "members":{"names":["pabbridge"],"roles":["_admin","bridge_ro"]}}
```

**VDU는 이름을 보고, `_security`는 롤로도 멤버를 받습니다.** 따라서 **`bridge_ro` 롤을 가진 다른 이름의 계정은 정본 `pab-llmdata`에 쓸 수 있습니다.** "단방향"은 기술적 차단이 아니라 **이름 규약**입니다.

⇒ 회원 vault DB를 만들 때 **`bridge_ro` 롤을 재사용하면 안 됩니다. DB별 전용 롤을 파야 합니다.** 저희 T-4 회전에 포함시키겠습니다.

> 이 항목은 저희가 *"위험 방향이라 검증 전까지 열린다고 취급"* 하며 미검증으로 두었던 것인데, 이번 조사로 **열린다는 것이 확인**됐습니다.

| **PV1-3** | 🔴 **경로 불변식을 누가 소유합니까?** v4는 `/home/oceanui/pab-vault-members/<vault_id>/`에 디렉터리를 **만들고**, Prove는 `<$PAB_MEMBER_VAULT_ROOT>/<vault_id>`를 **자기 env로 조립해 씁니다.** 두 베이스가 갈리면 v4가 만든 vault는 비고 Prove는 다른 데 쓰며 **어느 쪽 수치에도 나타나지 않습니다.** 배포 시 대조 절차가 있습니까, 사람이 두 곳에 같은 값을 넣고 있습니까? | 🔴 **높음** |

> `PV1-3`은 Prove가 `vaultscope.py` docstring에 적어 둔 **T7 사고와 같은 형태**입니다 — *"API는 `base/<vault_id>`, 워커는 `base`. 양쪽 모두 자기 기준으로는 정상이라 어느 테스트에도 잡히지 않았다."* 지금은 **아무도 이 불변식을 소유하지 않습니다.** 우연히 맞고 있을 뿐이라면 그것도 답으로 충분합니다 — 계약으로 못 박을 자리를 찾는 중입니다.

## 9. 🔴 실행 전 반드시 — Observer 통지 의무는 **우리 것**입니다

Q2/Q3를 실제로 실행하면 **홉 구조 변경**입니다. `OB2-A` §1.3에 따라 **24시간 리드타임 사전 통지**가 걸려 있고, `docs/interop/pab-observer/README.md` §4가 **수행 주체를 PAB-obsidian으로 명시**합니다. PAB-v4나 PAB-Prove가 따로 하는 것이 아닙니다.

⇒ **실행 일정이 잡히면 24h보다 먼저 저희에게 알려 주십시오.** 저희가 Observer에 통지합니다.

⚠️ 그 전까지 **`#31` 화이트리스트에 선등재하지 말 것**을 요청드립니다. 실물 없이 등재하면 배포 전 구간이 상시 `(absent)` 오경보가 됩니다.
