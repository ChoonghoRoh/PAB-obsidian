## 1. PV1-1 — 회원 vault 읽기 경로·모드·루프·prune

**⑴ 경로와 모드** (2026-09-15 `docker inspect` 실측)

```
/home/oceanui/pab-vault-mirror   → /vault-mirror    rw=false   ← 미러: 읽기전용
/home/oceanui/pab-vault-members  → /vault-members   rw=true    ← 🔴 회원: 쓰기 가능
```

🔴 **회원 루트는 `rw` 로 마운트돼 있습니다. 미러와 다릅니다.** 숨기지 않고 적습니다.
**이유**: v4 가 **가입 시 디렉터리를 만들기** 때문입니다(`member_vault_provisioning_service` — `mkdir`·`chmod`). ⚠ **그러나 노트 파일 쓰기는 0건입니다** — 수집 서비스에서 `.md` 를 쓰는 경로가 없습니다(코드 확인). **쓰기 권한은 있고 쓰기는 하지 않습니다.**

**⑵ 같은 루프입니다** — 별도 루프가 아닙니다.

```
vault_mirror_watcher._run_sync_cycle()
    for member in list_enabled_member_vaults():
        _run_sync_if_changed(member.vault_path, user_id=member.user_id)
```

미러와 **동일 주기(60s)·동일 파이프라인**(`run_sync_pipeline`)이고, 회원 1명에서 예외가 나면 **로그 남기고 다음 회원을 계속**합니다. 시그니처 캐시(`_last_signatures`)는 **`vault_path` 별 키**라 서로 덮지 않습니다.

**⑶ prune 가드는 회원 vault 에도 **같은 값으로** 걸립니다.**

| 가드 | 값 |
|---|---|
| `VAULT_MIRROR_PRUNE_MAX_RATIO` | **0.5**(기본) — 회원별로 동일 적용 |
| `VAULT_MIRROR_PRUNE_MIN_DOCS` | 동일 적용 |
| **사전 차단** | `_collect_folders_missing_precheck(vault_path)` 가 의심되면 **그 주기의 prune 을 끕니다**(회원 단위) |

⚠ **한 가지 알려 드릴 것** — 이 가드는 **「의도된 대량 삭제」와 「사고」를 구분하지 못합니다.** 회원이 Obsidian 에서 노트를 대량 정리하면 가드가 발동해 DB 에서 지워지지 않습니다. 🔴 **§4 의 WebDAV 전환에서 이것이 정책 과제로 남습니다.**

## 2. PV1-2 — Prove 에 주는 값

**⑴ `POST /oauth/token` 응답 전체** (2026-09-15 3800X 라이브 실측)

```
{ user_id, username, vault_id, vault_name }
```

- `vault_id` — 필수(`str`). **경로가 아니라 마지막 세그먼트만** 갑니다
- `vault_name` — **2026-09-15 추가**(nullable, additive). 사람이 읽는 표시명이고 **현재 전 회원 `null`** 입니다(쓰는 경로가 아직 없습니다)
- 🔴 **경로 성격의 값은 없습니다** — 귀측이 *"없어야 정상"* 이라고 적은 그대로입니다

**⑵ `vault_id` 의 영구성 — 「영구」가 아닙니다. 정확히 적습니다.**

| | |
|---|---|
| 회원당 **활성** vault | **최대 1개**(PostgreSQL 부분 UNIQUE `uq_member_vaults_user_id_active`, `WHERE enabled = true`) |
| 비활성 행 | **여러 개 가능**(이력 보존) |
| ⇒ | **`vault_id` 는 「활성 vault 1개」에 1:1 이고, vault 가 교체되면 새 값이 됩니다** |

⚠ **그래서 「회원 계정에 영구 귀속」은 아닙니다.** 현재 교체 경로는 구현돼 있지 않지만 **스키마가 그것을 허용**합니다. 귀측이 `vault_id` 를 **불변 키로 캐시하면 교체 시 어긋납니다** — 캐시하지 마시고 매 교환 때 받은 값을 쓰십시오.

## 3. 🔴 PV1-3 — **경로 불변식은 v4 가 소유합니다** (사용자 결정 2026-09-15)

귀측 질문: *"경로 불변식을 누가 소유합니까? … 지금은 아무도 이 불변식을 소유하지 않습니다. 우연히 맞고 있을 뿐이라면 그것도 답으로 충분합니다."*

**답 ⑴ — 우연히 맞고 있었습니다.** 귀측 판독이 정확합니다. 배포 시 대조 절차가 없었고, 사람이 두 곳(v4 설정 · Prove env)에 같은 값을 넣고 있었습니다.

**답 ⑵ — 🔴 소유자를 정했습니다: `v4` 입니다.**

| 주체 | 역할 |
|---|---|
| **PAB-v4** | 🔴 **경로를 정한다**(소유자). 회원 vault 루트와 `<vault_id>` 조립 규칙의 정본 |
| PAB-Prove | **v4 가 정한 값을 받아 쓴다** |
| (신규) WebDAV | 같음 — v4 가 정한 값을 받는다 |

⚠ **결정과 현재 코드가 아직 다릅니다** — Prove 는 여전히 `PAB_MEMBER_VAULT_ROOT` 를 **자기 env 로 조립**합니다. **결정은 났고 계약으로 못 박는 작업이 남았습니다.** 그 작업 전까지는 **여전히 우연히 맞는 상태**이므로, 저희가 배포 시 **대조를 절차로 넣습니다**(경로 실측 1줄).

🔑 **귀측이 지적한 형태가 그대로입니다** — Prove `vaultscope.py` 의 *"API 는 `base/<vault_id>`, 워커는 `base`. 양쪽 모두 자기 기준으로는 정상이라 어느 테스트에도 잡히지 않았다."* **소유자를 정하지 않으면 테스트가 잡을 수 없는 종류의 어긋남**이고, 그래서 소유자를 정한 것이 답입니다.

## 4. 🔴 방향 전환 통지 — **회원별 CouchDB DB·bridge group 을 만들지 않습니다**

PV1 §4 가 회원 편입 5단계(DB·계정·group·재시작·Setup URI)를 정리해 주셨고, 저희는 그 노선으로 검토했습니다. **철회합니다.**

**⑴ 철회 이유 — 확장되지 않습니다** (저희 사용자 판단 2026-09-15)

PV1 §4 ⑷ 가 *"재시작 필요 여부 미확인"* 으로 남긴 것을 **저희가 측정했습니다**:

```ts
// livesync-bridge main.ts — 실측
const confText = await Deno.readTextFile(configFile);   // 기동 시 1회
config = JSON.parse(confText);
const hub = new Hub(config); hub.start();
```

**`watchFile`·`reload` 코드 0건.** ⇒ **group 추가는 bridge 재시작이 필요하고, 그 순간 미러 + 기존 회원 전원의 동기화가 끊깁니다.**

🔑 **가입은 가장 흔한 사건입니다.** 그때마다 전체를 흔드는 구조라 회원이 늘면 성립하지 않습니다. ⇒ **이것이 철회의 이유입니다.**

**⑵ 대신 갈 길 — 파일을 그대로 노출합니다**

```
회원 Obsidian(Remotely Save, WebDAV)
      │ HTTPS + v4 회원 자격
      ▼
nginx(dav) ──auth_request──► v4 가 신분 확인 → vault_id 반환
      ▼
/home/oceanui/pab-vault-members/<vault_id>/   ← v4 가 이미 읽는 그 디렉터리
```

| 왜 이쪽인가 | |
|---|---|
| **가입 무중단** | 회원 디렉터리는 **가입 시 이미 만들어집니다** ⇒ 동기화용 추가 프로비저닝 **0** · 재시작 **0** |
| **저장소가 하나** | 회원이 편집하는 실체 = v4 가 읽는 실체 = **같은 파일**. 물질화 장치(bridge)가 **필요 없습니다** |
| **자격이 하나** | v4 회원 인증 재사용 ⇒ **가입·탈퇴가 그대로 접근 제어**. 별도 자격 저장소를 동기화하지 않습니다 |

**⑶ 🔴 귀측에 실질적인 영향 — 대기 항목에서 빼셔도 됩니다**

| PV1 항목 | 상태 |
|---|---|
| 회원별 CouchDB DB 생성(§4 ⑵) | ⛔ **불필요** |
| 회원별 CouchDB 계정 + **DB 전용 롤**(§4 ⑶) | ⛔ **불필요** ⇒ **T-4 자격증명 회전에 회원 계정을 포함시키지 않으셔도 됩니다** |
| `pab-vault-members` 를 bridge 에 마운트(§4 ⑴) | ⛔ **불필요** ⇒ compose 변경·컨테이너 재생성 **없음** |
| bridge config group 추가(§4 ⑷) | ⛔ **불필요** |
| Setup URI(§4 ⑸) | ⛔ **불필요** |

🔑 **T-4 가 저희 쪽 선행 차단이었는데, 그 의존이 사라집니다.** T-4 는 **그쪽 일정대로** 진행하십시오. 저희가 기다리지 않습니다.
⚠ **지금 도는 관리자 미러(`pab-llmdata`)는 그대로 유지**해 주십시오 — wiki(CLI 스킬) 경로이고 회원 경로와 섞지 않습니다.

## 5. 🔴 정정 2건

### 5.1 PV1 §5.3 「이미 R-1 위반」 — **전제가 정정됐습니다** (사용자 결정 2026-09-15)

귀측: *"현재 회원 vault 는 v4 watcher(읽기) · Prove(쓰기) · 사용자 rsync(쓰기)로 **쓰기 주체가 둘이라 이미 R-1 위반 상태**"*.

**rsync 는 상설 writer 가 아니라 개발 쪽 전용 창구입니다**(개발 마이그레이션 사유). ⇒ **운영 writer 는 Prove 하나이고 R-1 은 운영에서 성립합니다.**

⚠ **다만 귀측 §5.3 의 권고 4개는 그대로 유효하다고 봅니다** — 특히 **⑵ 쓰기를 원자적으로(임시파일 + `rename`)** 는 WebDAV 를 열면 **더 중요해집니다**(사람이 쓰는 주체가 되므로). 그 확인을 §7 실험에 넣었습니다.

### 5.2 저희가 공유할 발견 — **단방향이 두 겹입니다**

PV1 §7 은 CouchDB 쪽 VDU(`userCtx.name === 'pabbridge'`)를 다뤘고, *"단방향은 기술적 차단이 아니라 이름 규약"* 이라고 적으셨습니다. **맞습니다. 그런데 한 겹이 더 있습니다** — `Hub.ts` 에 **PAB 자체 패치**가 있습니다(실측 원문):

```ts
// [PAB 단방향 패치] storage -> couchdb 역방향 전파 차단
if (source.config.type === "storage" && peer.config.type === "couchdb") continue;
```

⇒ **VDU 를 풀어도 bridge 가 전파하지 않습니다.** 두 겹을 함께 알고 계셔야 §7 의 위험 평가가 정확해집니다.
🔑 **역으로, 저희 WebDAV 노선은 이 두 겹을 건드릴 이유가 없습니다** — bridge 를 경로에서 빼기 때문입니다.

### 5.3 PV1 §6 `OB2-E` §4.4 철회 — **저희 쪽 조치 0**

*"§4.4 를 근거로 등재하신 제약이 있으면 철회해 주십시오."*
⇒ **확인했습니다. 저희 문서에 그 취지로 등재한 제약은 없습니다**(전수 grep — PV1 본문 외 히트 0). **철회할 것이 없습니다.** 정정 자체는 감사히 받습니다.

## 6. 🔴 회신 요청 1건 — Observer 통지 주체

PV1 §9: *"Q2/Q3 를 실제로 실행하면 홉 구조 변경이고, `OB2-A` §1.3 에 24h 리드타임 사전 통지가 걸려 있으며 **수행 주체는 PAB-obsidian**"*.

**저희 WebDAV 노선은 성격이 다릅니다** — CouchDB·bridge 를 **쓰지 않고**, 추가되는 것은 **v4 쪽 자산**(nginx dav + v4 인증 엔드포인트)입니다.

> **질의**: 이 경우에도 **홉 구조 변경**으로 보아 Observer 24h 통지 대상입니까?
> 그렇다면 **수행 주체가 PAB-obsidian 입니까, PAB-v4 입니까?** (귀측 자산이 아니므로 저희가 하는 것이 맞아 보이나, `OB2-A` 의 문면은 저희가 갖고 있지 않습니다)

⚠ **답을 받기 전에는 Observer 통지가 필요한 단계로 넘어가지 않습니다.** §7 실험은 **회원 1명·테일넷 내부**라 노출 변경이 없다고 판단하고 진행합니다 — **이 판단이 틀렸다면 알려 주십시오.**
⚠ **`#31` 화이트리스트 선등재 금지**(PV1 §9) 준수합니다.
