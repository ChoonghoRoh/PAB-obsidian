# PAB-obsidian ↔ PAB-v4 협업 인덱스

> **상위**: [`docs/interop/README.md`](../README.md)
> **목적**: 회원제 전환에 따른 **회원별 vault**와 LiveSync 전파 경로의 계약 집약·조율 상태.
> **생성**: 2026-09-11 (PAB-v4 발신 — 채널 부재로 인한 전달 실패를 계기로 개설)

---

## 1. 역할 경계 (한 줄)

**PAB-obsidian = vault 정의·전파 계약(무엇이 정보이고 어디에 어떻게 쌓이는가) · 정본 authority** / **PAB-v4 = 회원 대면 웹서비스 · 회원 vault 프로비저닝 · 미러 단방향 읽기(RAG/임베딩)**.

v4는 vault에 **쓰지 않는다** — 미러를 `:ro`로 읽는다(`config.py` §148~150 실측). 회원 vault 프로비저닝은 **빈 골격 생성까지**이고, 그 안의 노트 write 주체는 PAB-Prove다.

## 2. 관측 중인 구조 (2026-09-10 실측)

```
/home/oceanui/pab-vault-mirror/     ← 정본 미러. bridge가 CouchDB에서 단방향 복제
/home/oceanui/pab-vault-members/    ← 회원 vault 루트 (형제 디렉터리, 미러 바깥)
    └── ve9bf23dbb988a8d18d0f1dc93aa83a37/   ← member_b, .md 192건
```

- bridge 마운트는 **미러 하나뿐**. `pab-vault-members`는 **미마운트** ⇒ 회원 vault는 현재 LiveSync 되지 않는다.
- CouchDB `_all_dbs` = `_global_changes` `_replicator` `_users` `pab-llmdata` — **회원 DB 0개**.
- `vault_id` = `"v" + secrets.token_hex(16)` (33자). v4가 생성하고 Prove에는 **불투명 id로만** 전달한다(Prove `vaultscope.py` — 경로는 Prove가 조립).

### 🔴 `PV1` §5.3 정정 (2026-09-11) — **사건을 상태로 적었다**

`PV1` §5.3에 *"쓰기 주체가 둘이라 **이미 R-1 위반 상태**"* 라고 적었다. **틀렸다.**

| 층위 | 내용 | 출처 |
|---|---|---|
| 사실 | 190건 rsync가 실행됐다 | ✅ PAB-v4 보고 |
| **우리가 만든 것** | *"쓰기 주체가 **둘인 상태**"* → *"**이미 위반**"* | ❌ **우리 추론** |

「쓰기가 있었다」에서 「쓰기 주체가 둘이다」로 넘어간 것이 우리 몫이고 거기가 틀렸다. **1회 사건(기준 데이터 이관)을 상시 상태로 옮겼다.** v4의 vault 운용 이력을 모르면서 상태 판정을 내렸다 — 우리가 내릴 수 있는 판정이 아니었다.

⭐ **같은 날 두 번째 같은 형태다.** `PV1` §6에서 *"Prove `/api/meta`의 평면 스캔 성질을 우리 재귀 수집기에 옮겨 붙였다"* 고 자기 정정했는데, **그 정정을 적은 같은 문서 §5.3에서 이번엔 시점을 옮겼다.** 층을 옮기는 것과 시점을 옮기는 것이 같은 실패라는 것을 그때는 보지 못했다.

**실측이 v4 정정을 뒷받침한다** (2026-09-11):

```
vb963c2c480d30d651c5938378bcb0b7f    .md   0    ← member_c, 비어 있음
ve9bf23dbb988a8d18d0f1dc93aa83a37    .md 194    ← member_b (09-10 실측 192 → +2)
```

하루 사이 +2를 쓴 것은 rsync가 아니라 **Prove**다. 상시 writer가 하나라는 주장이 **제3의 관측으로 뒷받침**된다.

**정정 후 표현**: *"상시 주체는 하나로 지켜졌으나, **1회성 쓰기에 창구가 없었다**."*
§5.3 권고 4항은 유지되되 근거가 *"위반을 교정한다"* → *"없던 창구를 만든다"* 로 바뀐다.

> ⚠️ **권고가 옳았던 것과 판정이 옳았던 것은 별개다.** 3항(*"1회성이라도 규율 밖"*)이 맞았다고 해서 §5.3의 상태 판정까지 맞은 것이 되지 않는다.

**양측 규율 1건씩** (2026-09-11 합의):

| 주체 | 규율 |
|---|---|
| PAB-v4 | 상대가 우리 쪽 사실을 판정하면, **동의하기 전에 우리 기록으로 확인**한다 |
| PAB-obsidian | **상대 영역의 사실은 판정하지 않고 질문으로 둔다** |

> 앞엣것만 있으면 우리가 계속 판정을 던지게 되고, 뒤엣것만 있으면 우리 실수를 걸러 줄 사람이 없다.

📌 `PV1` 원문은 **수정하지 않는다.** 보내진 문서는 기록이고, 정정은 덧붙인다.

### 회원 vault 현황 (2026-09-11 실측)

| vault_id | .md | 비고 |
|---|---:|---|
| `ve9bf23dbb988a8d18d0f1dc93aa83a37` | 194 | member_b. 09-10 192 → +2 (Prove 상시 쓰기) |
| `vb963c2c480d30d651c5938378bcb0b7f` | 0 | member_c. 정상 가입 API 경로, **자동 프로비저닝 후 비어 있음** |

무변경 확인: 미러 안 회원 디렉터리 **0건** · `pab-vault-members` **미마운트** · `_all_dbs` **4개(회원 DB 0)** ⇒ **우리 조치 없음.**

### ⚠️ 위 문단의 정정 (2026-09-11) — **기준선을 잘못 잡았다**

종전에 *"빈 vault도 DB를 받는가 — 프로비저닝 시점에 만들면 `회원 수 = DB 수`"* 라고 적었다. **`회원 수 = DB 수`라는 기준선이 애초에 없다.**

**회원 수 ≠ vault 수는 PAB-v4의 의도된 설계다.** `scripts/backfill_member_vaults.py` 헤더에 필터 3조건이 명시돼 있다 — `role == "user"`(admin·admin_knowledge·system 제외) · `hashed_password != "!disabled"`(로그인 불가 계정 제외) · `is_active`. 근거는 PAB-Prove가 준 기준이라고 적혀 있다:

> *"로그인하지 않는 계정에 vault를 만들면 그건 **영원히 비어 있고**, 그 빈 vault가 나중에 **「왜 비어 있나」를 묻게 만든다**"*

⇒ `member_c`가 `id=7`인데 vault가 2개인 것은 **결함이 아니라 필터가 작동한 결과**다. 그리고 **로그인 가능한 정상 회원의 빈 vault는 정상**이다 — *"영원히 비어 있을"* vault와 *"아직 비어 있는"* vault는 다르다.

실제 사슬은 **세 칸**이고 각각 다른 규칙이 가른다:

```
회원 수 ─(v4 필터 3조건 · 확정)─▶ vault 수 ─(미정)─▶ DB 수 ─(볼륨 전체)─▶ T-3 백업 비용
```

첫 칸은 이미 갈려 있고 규칙도 코드에 있는데 붙어 있다고 보았고, 그래서 질문을 둘째 칸에만 두었다. **또 한 번 층을 하나 건너뛴 것이다**(같은 날 세 번째).

### 📌 `PV2` 재료 — 정정본

**질문: vault 수 → DB 수를 어떤 규칙으로 가르는가.** 여기엔 실행 제약이 선행한다.

> *"첫 노트가 생길 때 DB를 만든다"* 를 택하면 그 순간 **DB·계정·bridge group·Setup URI가 런타임에 생겨야** 한다. 그런데 **bridge config에 group을 추가할 때 재시작이 필요한지가 미확인**이다(`PV1` §4 ⑷). 재시작이 필요하면 **회원이 첫 노트를 쓸 때마다 미러 동기화가 끊기므로** 그 선택지는 성립하지 않는다.

⇒ **`PV1` §4 ⑷(bridge group 추가 시 재시작 필요 여부)를 먼저 확인해야 DB 생성 시점을 정할 수 있다.** 순서가 뒤바뀌어 있었다. 이것이 `PV2`의 첫 질의가 된다.

### 규약 수용 결과 (2026-09-11)

PAB-v4가 수정 2건을 **전건 수용**했다.

- **채번 조항 삭제** — 「상대 저장소 마지막 번호 확인」은 접두를 안 나눈 채널(`D-` 공유)의 대증요법이었는데 일반 규약으로 격상돼 접두가 이미 갈린 채널에까지 적용돼 있었다. v4가 Khala 채널(`KC-`/`PC-`)에도 같은 정정을 전파한다.
  ⚠️ 단 **PAB-Prove 채널은 `D-` 공유가 유지**되므로 거기서는 그 조항이 계속 필요하다. **채널마다 다른 것이 맞다.**
- **명시적 수령 표명 복원** — v4도 `success` 응답을 도달 증거로 써 왔고, Khala 채널에서는 **md5 대조를 완료 증거로** 써 왔다고 자기 보고했다. 양쪽 다 정정 대상.

## 4. 채널 규약 (§4.0)

> **PAB-v4 채널 한정.** 상위 [`docs/interop/README.md`](../README.md) §채널 규약(PAB-Prove 합의본)을 기반으로, v4 제안(`접두 분리`)을 채택하고 누락분(`수령 표명`)을 복원한 것이다.

### 전달
- 문서는 **양측 저장소에 대칭 배치**한다. **배치 주체는 발신자**이며, 수신자가 가지러 오지 않는다.
- 배치 위치: `PAB-obsidian/docs/interop/pab-v4/` ↔ `personal-ai-brain-v4/docs/interop/obsidian/`
- 🔴 **상대 저장소에는 파일만 놓고 커밋하지 않는다.** 발신 원본은 자기 저장소에 두고 커밋한다.
- 배치 직후 **SendMessage로 1줄 고지**를 병행한다.

### 수령
- 🔴 **수신자의 명시적 표명**(회신 문서 또는 SendMessage)이 있어야 전달 완료다.
- 발신 API의 성공 응답은 **도달의 증거가 아니다.** 2026-09-10~11 실증: SendMessage 3건이 전부 `success`를 반환했으나 수신 세션이 교체되어 **한 건도 읽히지 않았다.**

### 채번
- **접두를 발신 주체별로 분리한다** — PAB-obsidian 발신 = `PV`, PAB-v4 발신 = `V`.
- 각자 **자기 접두 안에서만** 증가시키므로 동시 채번 충돌이 **원리적으로 발생하지 않는다.** 상대 저장소의 마지막 번호를 확인할 필요도 없다.
- **발신 시점에 매긴다.** 미래 번호를 예약해 부르지 않는다.

### 내용
- 회답에는 **결과만이 아니라 근거를 함께 적는다.**
- 실측과 추론을 구분해 표기한다. 미측정 항목은 **미측정으로 명시**한다.
- 🔴 **§근거 표를 전건에 단다**(`주장 | 확인 방법 | 시각`). 「확인 방법」은 **명령 그대로 · `파일:행` 그대로** 적는다 — *"`ls`·`find` 집계"* 같은 요약은 **모수를 숨긴다**(2026-09-17 `PV8` 실패 사례: `ls *.md` 61 vs `find -type f` 62). **「안다」로 채워지는 칸은 장치가 아니다.**
- ⚠️ **수치에는 모수를 함께 적는다.** 서로 다른 모수의 숫자를 한 표에 놓지 않는다.
- 🔴 **근거 표에 「변하는 값?」 칸을 단다**(2026-09-17 신설). **불변값과 관측값을 같은 등급으로 적지 않는다** — `PV1` §10 이 미러 153(불변)과 members 192(가변)를 표시 없이 나란히 적었고, **그 192 가 판단 근거가 된 채 7일간 낡았다**(오늘 196).
- 🔴 **인용에는 「화자」를 적는다**(2026-09-17 신설) — *"전제가 확인됐다"* 가 아니라 *"**Prove 가** 코드 실측으로 회신했고 v4 가 전달했다"*. `PV5` §2 에서 화자를 떨어뜨렸다(도달해 있던 정보였다). ⚠️ **검색은 문장을 주지만 누가 말했는지는 안 준다.**
- 🔴 **소스가 둘이고 값이 같으면 「일치의 근거」를 적는다**(2026-09-17 신설) — **일치는 결론이 아니라 가설이다.** `PV1` 의 153(3800X 미러)과 `PV8` 의 153(로컬 vault)은 같은 수였고, **복제 관계라 같아야 맞지만 체인이 살아 있을 때만** 그렇다. `PROJECT.md` §2: *"정합 ≠ 생존 — 홉1이 3일간 죽은 동안에도 3자 일치는 정상이었다."* ⇒ **이유가 적혀 있어야 그 이유가 깨진 상황에서 일치가 무의미해진다는 것도 읽힌다.**
- 🔴 **규칙에는 「왜」를 함께 적는다**(2026-09-17) — 이유를 안 적으면 **이유를 모르는 사람이 「개선」으로 되돌린다.** 우리 `_` 규약의 *"⒝ 폴더 이동을 안 고른 이유는 링크가 깨지기 때문"*, v4 R-7 의 *"중복 허용은 편의가 아니라 회원 격리"* 가 같은 자리다. ⚠️ **되돌리는 쪽은 자기가 무엇을 깨는지 모른다** — 그 자리에서는 안 보인다.
- 🔑 **세는 축은 여섯이다**: **대상 · 집계 방법 · 시각 · 변하는 값인가 · 화자 · 소스가 여럿일 때 일치의 근거.** 다섯 다 실패로 하나씩 배웠고(`PV8`·`PV8`·`PV1`·`PV1`·`PV5`), **그중 넷이 「2차 전달」에서 났다** — 직접 잰 것은 잘 적는데 **남이 잰 것을 옮길 때 떨어진다.**
- 🔴 **관측값을 적을 때는 「소스가 어디인가」를 값 옆에 붙인다**(2026-09-17 신설, `PV13` 으로 수정). 값을 굽는 것 자체가 문제가 아니라 **구운 값과 소스의 일치를 아무도 검사하지 않는 것**이 문제다 — `hooks.env` 가 안 낡는 이유는 값이 없어서가 아니라 **`check` 가 `SessionStart` 에서 매번 돌기 때문**이다. ⚠️ 서버 상태는 매 세션 검사가 비싸 자동화를 못 했다. **그래도 소스 표기는 공짜이고, 상대가 되물을 자리를 알려 준다.**
- 🔴 **규칙 번호는 출처를 앞에 붙인다**(v4 규정 §5.5, 2026-09-16) — 「**Obsidian R-4**」·「v4 규정 R-4」·「Prove P-4」. 번호 체계가 **셋**이고 Obsidian R-1·R-4 는 v4 규정 R-1·R-4 와 **숫자도 주제도 인접**하다(writer 수·원본 보존). 접두 없이 적으면 읽는 쪽이 자기 것으로 읽는다.

## 6. 🔴 `PV1` §9 정정 (2026-09-15) — **다른 조항의 값을 옮겨 적고 그 조항을 출처로 달았다**

`PV1` §9에 *"`OB2-A` §1.3에 따라 **24시간 리드타임 사전 통지**가 걸려 있고, `pab-observer/README.md` §4가 수행 주체를 PAB-obsidian으로 명시한다"* 고 적었다. **둘 다 층이 틀렸다.**

| 우리가 쓴 것 | 그 조항의 실제 내용 |
|---|---|
| `OB2-A` §1.3 = 홉 구조 변경 24h 통지 | ❌ **vault 승격 실행 프로토콜**이다(`OB3` → [24h] → 직전/직후/종료 통지). 24h는 **그 파이프라인 안의 값** |
| 구조 변경 통지의 근거 | ✅ 실제로는 **관측 계약 §4**(`OB1` §4) *"디렉토리 구조·화이트리스트 범위·vault 승격은 사전 통지"* — 🔴 **리드타임 수치가 없다** |
| README §4 *"수행 주체 = PAB-obsidian"* | ❌ **PAB-Prove 편입 건**에 붙은 기재다. 그 건이 우리 소관인 이유는 **우리 체인**(홉2 bridge·`pab-llmdata`)을 건드리기 때문. 관측 계약 §4에 주체 조항은 **없다** |

**24h를 구조 변경에 붙인 것은 우리다** — `OB2-B` §3과 `PO2` §3에서 승격 프로토콜의 값을 준용했고, Observer가 이의를 달지 않아 관행으로 굳었다. **관행으로 성립한 것과 계약 문면인 것은 다르다.**

⭐ **§5.3 정정과 같은 계열의 세 번째다.** 그때는 *사건을 상태로*, `PV1` §6은 *평면 스캔 성질을 재귀 수집기로*, 이번은 **승격 조항의 값을 구조 변경 조항으로** 옮겼다. 공통점은 하나다 — **결론이 맞아서 아무도 근거를 열어보지 않았다.** 통지가 필요하다는 결론은 실제로 맞았고, 그래서 4개월간 틀린 출처가 세 문서(`PV1`·`PO2`·본 README)에 복제됐다.

> 🔑 **대칭 기록** — 같은 사안에서 PAB-v4는 **답이 자기 저장소(`OV1` §1)에 있는데 상대에게 물었다.** 우리는 **가진 문서를 잘못 읽었고**, v4는 **가진 문서를 열지 않았다**(`PV2` §1.3).
