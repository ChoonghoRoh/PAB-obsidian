# 단계 단위 — VERIFYING (verifier)

## 1. G2 판정 기준

| 게이트 | 판정 기준 | 결과 |
|--------|----------|------|
| **G2** | Critical 0건 · 입력 검증(백엔드) · XSS 방지(프론트엔드) · 정본 컴포넌트 재사용(프론트엔드, REUSE-1) · 보안 취약점 없음 · 주석 규격 NOTE-1~6(제품 코드) | PASS → TESTING / PARTIAL·FAIL → REWINDING → BUILDING (지적 범위 수정 후 재검증) |

- 이 행은 요약이다. 세부 판정 항목은 `ROLES/SUB-SSOT/VERIFIER/verification-procedure.md` §G2 판정 기준(G2_be · G2_fe · G2_DS)이 정본이고, 등급은 그 절의 「등급 산출」 표가 정본이다. 세부 항목은 그곳에만 두고, 이 요약과 rules-index 요약은 LOCK-7 순서로 따라 고친다(LOCK-6).

## 2. 병렬 BUILDING 뒤 통합 재검증

병렬 BUILDING을 쓴 Phase는 Team Lead가 Phase 전체 변경 파일을 넘긴다. verifier는 그 전체를 대상으로 G2를 한 번 더 판정한다. BE·FE를 나눠 검증했으면 결과를 합친다.

## 3. 판정 요청 · 결과 파일

- **요청**(Team Lead): `대상 SHA` · worktree 경로 · 기준 커밋 · 변경 파일 목록을 적는다(HANDOFF-6). 판정 범위에 다른 Task 커밋이 있으면 「커밋 ↔ Task 표」(`<커밋>=<Task>` 쌍 목록)도 적는다 — verifier가 파일 소유를 이 표와 기계 대조한다. [DOC] Task는 편집자 DoD 결과(LOCK-7)를 붙인다. 완료 기준 · 판독 항목은 규칙 ID만으로 가리키지 않고 뜻을 본문에 적는다(위치 · 예/아니오 질문 · 판정 문장).
- **판정**(verifier): 대상 SHA로만 읽는다(`git show <SHA>:<경로>`). 작업 트리를 읽지 않는다. git 문맥이 필요한 실행 검사(예: `lint --changed`)는 그 worktree의 HEAD가 대상 SHA이고 변경이 없을 때만 거기서 돌린다.
- **결과 파일**: `/tmp/agent-messages/<phase>-verifier-<task>-r<회차>.md`(REPORT-1 결과 파일을 Task · 회차로 나눈 이름). 머리에 `대상 SHA`를 적고, 결함은 `## 결함` 절에 아래 표로 적는다(집계 명령이 이 절 이름으로 범위를 좁힌다). `원인` 칸은 짝 문구 · 3자 정합 · 명세 해석 · 구현 누락 · 그 밖 중 하나를 고른다 — High 이상 결함이 어디서 되풀이되는지 추적하는 칸이다. `원인` 값은 이름만으로 판독 기준을 가리키지 않는다 — 결함 요지 칸에 그 결함이 위치 · 예/아니오 질문 · 판정 문장(예: 「`worktree.md:191`에 같은 뜻의 표기가 있는가 — 있고 뜻이 다름 → FAIL」)으로 풀리도록 적는다. `원인` 값의 뜻: **짝 문구** = 같은 커밋에 들어온 같은 뜻의 다른 표기를 놓침 · **3자 정합** = 정본 · rules-index 요약 · 인용이 서로 다름 · **명세 해석** = Task 지시를 다르게 읽음 · **구현 누락** = 지시한 항목을 하지 않음 · **그 밖** = 위 네 가지에 들지 않는 원인(직접 서술).
- 결함이 아닌 관찰은 `## 관찰` 절에 번호로 적는다. Team Lead는 받은 회차에 처리 경로(정정 · tech-debt · 사용자 확인 · 수용 한 줄)를 status 로그에 적는다(OPS-2). 사용자 결정과 닿는 관찰은 수용으로 닫지 않는다.
