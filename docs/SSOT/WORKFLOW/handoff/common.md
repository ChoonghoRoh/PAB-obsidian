# 팀원 공통

Team Lead가 모든 팀원에게 base로 넘기는 단위다.

## 1. SSOT 추가 로드 요청

- base 밖의 SSOT가 필요하면 읽기 전에 Team Lead에게 요청한다: `[SSOT 요청] {문서·절} — {사유}`
- Team Lead가 지정한 파일:절만 읽는다.
- 요청 없이 base 밖을 읽었다면 보고의 「지시와 다르게 한 것」 칸에 적는다.

## 2. 경계

- 지시에서 정한 담당 구역 밖의 파일은 편집하지 않는다. 필요하면 멈추고 Team Lead에게 묻는다.
- 지시받은 범위(파일:라인 · 블록명 · `point-N`) 안에서만 탐색·작업한다. 개방형 전체 파악은 하지 않는다(DELEGATE-3).

## 3. worktree 자율 사용 (WT-8)

worktree는 git으로 개발 기능을 분리해, 메인 작업 공간과 떨어진 별도 공간에서 구현·테스트하는 격리 공간이다. 아래 Task에서는 팀원이 Team Lead 승인 없이 만들어 쓸 수 있다.

| 담당 | 자율로 쓸 수 있는 Task |
|------|----------------------|
| **backend-dev** | Spike(선행 테스트) · 라이브러리·의존성 교체 검증 · DB 마이그레이션 리허설 · 리팩토링 전후 비교 · 성능 측정(구현 전 대안 비교만 — 판정 수치 · 기준선 측정은 tester, ASSIGN-2) |
| **frontend-dev** | Spike · UI 구현 대안 비교 · 공용 컴포넌트 변경의 영향 확인 · 의존성·빌드 설정 변경 검증 |
| **designer** | 현행 디자인 검수 때 이전 버전 화면과 비교 (과거 커밋을 별도 공간에 띄움) |

**조건**:

1. 만든 즉시 Team Lead에게 한 줄 보고한다: `[WT 생성] {경로} · {브랜치} · {Task}`
2. 경로는 `../{저장소}-wt-phase-{X}-{Y}-{역할}-{Task}` 형식을 따른다 (WT-2).
3. 메인 작업 공간과 다른 팀원 구역은 건드리지 않는다.
4. 병합·커밋하지 않는다. 결과는 보고로 넘기고, 채택되면 Team Lead가 반영한다 (REPORT-5).
5. 역할별 병렬 정책의 상한을 따른다 — 빌드를 쓰는 작업은 동시 2명 이하.
6. Spike worktree의 코드는 버리는 것을 전제로 한다. 채택된 설계는 BUILDING에서 담당 구역에 다시 구현한다.
7. 끝나면 보고 블록에 경로·브랜치·결과를 적고, worktree를 제거하거나 Team Lead 지시를 기다린다.

## 4. 보고

| 규칙 ID | 규칙 | 설명 |
|---------|------|------|
| **REPORT-1** | 보고 경로 | 보고 본문은 `/tmp/agent-messages/<phase>-<role>.json`(또는 `.md`) 파일에 기록한다(빈 파일 금지). SendMessage로는 결론 요지 + **결과 파일 경로**를 통지하고, Team Lead는 통지를 받으면 그 파일을 읽는다(감시 도구가 있으면 보조 — 선택). **전 역할 의무**다(짧은 보고 포함 — 완화 조건은 운용하며 향후 정한다). 파일 본문 형식은 지시에서 정한 고정 블록을 따른다 |
| **REPORT-2** | 필수 칸 | 한 일 · 결과(검증 명령과 출력 요지) · 안 본 것 · 지시와 다르게 한 것 · 막힌 것 · 다음 제안. 빈 칸은 「없음」으로 적는다 |
| **REPORT-3** | 중간 보고 | 지시에서 정한 시점에 보낸다 (예: 착수 직후 한 줄, 작업 완료 직후 한 줄) |
| **REPORT-4** | 핵심 먼저 | 결론을 앞에 둔다. 길면 나눠 보낸다 |
| **REPORT-5** | 커밋은 Team Lead | 팀원은 커밋·스테이징하지 않는다. 지시로 위임받은 경우만 예외 |

**보고 블록**:

```
## 한 일
## 결과 (검증 명령 · 출력 요지)
## 안 본 것
## 지시와 다르게 한 것 (추가로 읽은 SSOT 포함)
## 막힌 것
## 다음 제안
```

이 블록은 **결과 파일**(`/tmp/agent-messages/<phase>-<role>.json`(또는 `.md`))에 기록하고, SendMessage에는 결론 요지와 그 **결과 파일 경로**를 담아 통지한다(REPORT-1, ①A 전면 의무).

## 5. 주석

| 규칙 ID | 규칙 | 설명 |
|---------|------|------|
| **COMMENT-1** | 주석은 최소한으로 | 코드·문서에 새로 쓰거나 고치는 주석은 코드만 읽어서는 알 수 없는 동작의 이유·제약만 적는다. 참조(「X 참조」·출처·계획서 절), 과거 이력(Phase·날짜·결함 ID·변경 경위), 개발 과정·이슈 서술(무엇을 시도했고 무엇이 문제였는지), 개수·버전, 코드를 되풀이하는 설명, 주석 안의 코드 예시(검사가 실제 코드로 오판한다), 주석 블록 머리·꼬리 표지(구분선 `# ====`·`# ----`, 제목 장식 `# --- 제목 ---` 포함)는 쓰지 않는다. 규격 표지(`Name : 한글명 · YYMMDD`)의 작성일 · 수정일 칸은 이력이 아니다. `PROJECT.md` §4에 주석 규칙이 있으면 그것을 따른다. 이는 하네스(SSOT·훅·스킬·스크립트)와 scratchpad 임시 도구의 **베이스(최소)**다 — 구역 밖 하네스는 COMMENT-1로 판정한다. 등급은 `ROLES/SUB-SSOT/VERIFIER/verification-procedure.md` §G2 판정 기준 「등급 산출」 표. 적용 기준은 작성자가 아니라 파일 위치다 — 제품 코드 구역(`PROJECT.md` §3)에 있는 코드·마크업의 주석은 누가 쓰든(하네스 파일이라도 그 구역에 있으면) 형식·포인터 운영을 `docs/comment-policy/comment-policy.md`로 따르고, 그 위반은 NOTE-1~6이다(등급은 같은 표) |
| **COMMENT-2** | 기존 주석은 건드릴 때 정리 | 기존 주석을 한꺼번에 정리하지 않는다. 개선 · 추가 개발로 **건드리는 블록만** 규격으로 바꾸고(touch-and-clean), 의도 · 이력 서술은 `point-N` 리포트로 옮긴다. 남은 규모는 `scripts/comment/comment-lint.py scan`으로 재고 부채 레지스트리에서 소진을 추적한다. 적용 기준은 작성자가 아니라 파일 위치다 — 제품 코드 구역(`PROJECT.md` §3)의 주석에 적용한다. 구역 밖 하네스는 COMMENT-1만 따른다. 판정 범위: `lint <대상> --changed <기준 커밋>` 위반 0이 기준이며 위반이 있으면 결함(건드린 블록 — comment-policy §3), 파일 전체 위반 수가 부채 레지스트리 기준선보다 늘어도 결함이다 — 등급은 verification-procedure.md §G2 판정 기준 「등급 산출」 표. 기준 커밋은 Task 지시에 적는다. 절차: `docs/comment-policy/comment-policy.md` §3. 예외: 사용자가 파일을 지정해 요청하면 그 파일의 주석 전체를 정리한다(COMMENT-3) |
| **COMMENT-3** | 주석 전체 정리 게이트 | 사용자가 파일(또는 파일 목록)을 지정해 요청할 때만 그 파일의 주석 전체를 규격(NOTE-1~6)으로 정리한다. Team Lead · 팀원은 발동하지 않는다 — Team Lead는 부채 레지스트리를 근거로 제안만 한다. 요청은 status 로그와 task 파일 「COMMENT-3 요청」 칸(일시 · 요청 요지 · 대상 파일 목록)에 적는다. 대상 파일마다 담당 구역 dev(마크업 시안은 designer)에게 주석 전용 Task · 커밋으로 맡기고 기능 변경과 섞지 않는다. 판정은 이 게이트 안에서만: `lint <파일>`(`--changed` 없이) 위반 1건 이상 · 주석 외 변경 · 요청 기록 없음은 결함이고, 새로 옮긴 `point-N`이 고아로 남거나 정리 중 기존 `point-N` 참조를 지워 그 항목이 `points <root>`에서 고아가 되어도 결함이다(diff의 삭제 줄 `point-N`을 고아 목록과 대조한다). 등급은 verification-procedure.md §G2 판정 기준 「등급 산출」 표. 게이트 밖에서는 파일 전체 lint 위반을 결함으로 올리지 않는다. `points <파일>` 죽은 참조는 게이트와 무관하게 파일 단위로 결함이다(NOTE-6). 절차: Team Lead 쪽 `ROLES/SUB-SSOT/TEAM-LEAD/orchestration-procedure.md` §업무 지시 규약 · dev 쪽 `docs/comment-policy/comment-policy.md` §3 |

## 6. 통신

| 규칙 ID | 규칙 | 설명 |
|---------|------|------|
| **COMM-1** | 착수 확인 | 지시 메시지를 받으면 **즉시 한 줄 ack**("수령·착수합니다")를 보낸다. REPORT-3(착수 직후 한 줄)·SPAWN_GATE 준비 신호와 연계한다 |
| **COMM-2** | Hub-and-Spoke | 모든 통신은 **Team Lead 경유**다. 팀원끼리 직접 메시지를 주고받지 않는다 |
| **COMM-3** | 송신 규약 | 한 통에 한 과업을 담고 지시마다 ID를 붙인다. 받는 쪽은 ack에 그 ID를 복창한다(COMM-1 보강). Team Lead는 한 팀원에게 처리 중인 지시가 있으면 겹쳐 보내지 않는다. 보류 · 취소는 파일 신호(`/tmp/agent-messages/<phase>-<role>.hold`)로 하며, 팀원은 작업 경계(Task 착수 전 · 완료 직후)마다 그 파일 존재를 확인한다. 지시 ID가 현재 진행 중인 지시와 다른 옛 메시지는 따르지 않고 수신 사실만 보고한다 |
| **COMM-4** | 범위 축소 금지 | 팀원은 지시 범위(대상 · 항목 · 지표)를 스스로 줄이거나 넓히지 않는다. 줄여야 하면 착수 전 · 중에 `SCOPE_REDUCTION_PROPOSAL`로 Team Lead에게 묻고 답을 받은 뒤 진행한다 |

## 7. 컴포넌트 재사용

| 규칙 ID | 규칙 | 설명 |
|---------|------|------|
| **REUSE-1** | 정본 재사용 | 정본 컴포넌트가 있는 유형은 정본을 쓴다. 재사용하지 않거나 유사 컴포넌트를 새로 만들면 결함이다(등급은 `ROLES/SUB-SSOT/VERIFIER/verification-procedure.md` §G2 판정 기준 「등급 산출」 표 — G2_fe · G2_DS) |
| **REUSE-2** | 신규는 사유 + Team Lead 선행 선택 | 새로 만들어야 하면 착수 전에 재사용 불가 사유(정본 부재 증거 또는 기능 차이 근거)를 Team Lead에게 보고한다. Team Lead가 심사해 선택하고 레지스트리에 `LEAD_SELECTED`로 표기하면 개발한다. 사유가 요건을 채우지 못하면 무효다. 팀원 자기 선택은 인정하지 않고, `LEAD_SELECTED`를 `HUMAN_APPROVED`로 기록 금지다. 정본 존재 유형의 미재사용은 REUSE-1 결함, 정본 부재 유형에서 선택 표기(`LEAD_SELECTED`)가 없으면 결함이다 — 등급은 `verification-procedure.md` §G2 판정 기준 「등급 산출」 표. 사용자는 사후에 검토하고, 결과(`HUMAN_APPROVED` 또는 변경)는 레지스트리(사용자 검토 · 변경 이력 칸)에 남는다. 심사 기준: `verification-procedure.md` §재사용 불가 사유 심사 · `ROLES/SUB-SSOT/DEV/fn-procedure.md` GATE 5 |
| **REUSE-3** | 레지스트리 단일 원본 | 무엇이 정본인지는 `PROJECT.md` §3.1 정본 컴포넌트 레지스트리가 정한다. 선택된 신규 컴포넌트는 Team Lead가 레지스트리에 `LEAD_SELECTED`로 등록하고, 사용자 검토 결과와 변경 이력을 쌓는다. planner는 `[FE]` `[DS]` `[FS]` Task에 쓸 정본 목록을 적는다(`ROLES/planner.md` §7) |

## 8. 도구 사용 (TOOL-GUARD)

| 규칙 ID | 규칙 | 설명 |
|---------|------|------|
| **TOOL-1** | 기존 도구 우선 | 기존 도구로 먼저 해결한다 — `PROJECT.md`의 `build_cmd` · `test_cmd` · `lint_cmd`, `scripts/comment/comment-lint.py`, `refactor-scan`. 탐지를 기계화할 때도 기존 도구를 확장하고 새 도구를 만들지 않는다 |
| **TOOL-2** | 신규 임시 도구는 승인 | 새 임시 도구(스크립트 · 하네스 · 생성기)는 기존 도구로 안 되는 이유를 Team Lead에게 보고하고 승인받은 뒤 만든다 |
| **TOOL-3** | scratchpad 한정 · 수명 | 임시 도구는 scratchpad에만 두고 수명(언제 지우는지)을 적는다. Phase가 끝나면 폐기하거나 정식 편입을 판정한다 |
| **TOOL-4** | 정본 승격 | 세 번 이상 재사용된 도구만 정본 도구로 승격을 검토한다 |
| **TOOL-5** | 과업 치환 방지 | 도구 개선이 필요해 보여도 본과업을 먼저 끝낸다. 개선 요청은 tech-debt로 넘긴다 |
| **TOOL-6** | 되돌리기 어려운 조작 사전 확인 | 조작 위험 등급별 확인 수준 — **가역**(읽기 · 사본 편집): 확인 없음. **되돌리기 어려움**(설치 · 삭제 · 커밋 · 프로세스 종료 · 라이브 경로 쓰기): 한 줄 계획을 보내 ack를 받은 뒤 실행하고 전후 상태를 기록한다. **외부 게시**(push · 알림 · 원격 쓰기): 사용자 확인(Team Lead 경유) |
