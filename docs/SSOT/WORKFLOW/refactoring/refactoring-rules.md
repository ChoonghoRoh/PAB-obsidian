# 리팩토링 규정 (Rules Index)

---

## 0. 실행 규칙 (REFACTOR-1~3)

| 규칙 | 시점 | 조치 |
|------|------|------|
| **REFACTOR-1** | Phase X-Y 완료(DONE) | 코드 스캔 → 500줄 초과 파일 레지스트리 **등록만** (phase-chain.md §3 Step [4]) |
| **REFACTOR-2** | Master Plan 작성 | 레지스트리 읽기 → 700줄 초과 시 Lv1 분리 편성 (분리가 맞지 않으면 [예외]) |
| **REFACTOR-3** | PLANNING/BUILDING/G2 | 신규 파일 500줄 초과 **사전 방지**. 기존 파일을 늘려 500줄을 넘기면 사전 방지 대상이 아니라 REFACTOR-1 관심선 등록 대상이다 |

### 0.1 점검 프로토콜 — 2단계

**단계 1**: Phase X-Y 완료 → 코드 스캔 → 레지스트리 등록·갱신만 (계획 삽입 안 함)
**단계 2**: Master Plan 작성 → 레지스트리 읽기 → 700줄 초과 파일을 Lv1 선행 sub-phase로 편성

---

## 1. 용어 정의

| 용어 | 정의 |
|------|------|
| **단일 파일 줄 수** | 빈 줄·주석 포함 전체 줄 수 (`wc -l` 기준) |
| **개발 파일** | *.py, *.js, *.css, *.html (테스트·설정·문서 제외) |
| **연관 파일** | import/호출/include 관계로 직접 연결된 개발 파일 |
| **밀접 파일** | 연관 파일 중 양방향 참조 또는 공유 상태가 있는 파일 |

---

## 2. 임계값

| 기준 | 줄 수 | 의미 |
|------|------:|------|
| 관심선 | **500줄** | 레지스트리 등록, 모니터링 시작 |
| 경고선 | **700줄** | 리팩토링 검토 대상, Level 분류 |
| 위험선 | **1000줄** | 즉시 리팩토링 대상 (다음 Master Plan 최우선) |

---

## 3. Level 분류

### 3.1 Lv1 — 단일 파일 분리

| 항목 | 기준 |
|------|------|
| 조건 | 700줄 초과 파일이 **독립적으로 분리 가능** |
| 판별 | 해당 파일의 연관 파일 중 500줄 초과가 **0개** |
| 작업 규모 | 대상 파일 1개, 변경 파일 1~3개 |
| 편성 | 다음 Master Plan 내 **선행 sub-phase**로 처리 |

### 3.2 자동 판별 기준

```
700줄 초과 파일 발견
  │
  ▼
해당 파일의 import/호출 대상 파일 목록 스캔
  │
  ▼
그 중 500줄 초과 파일이 있는가?
  │
  ├── 없음 → Lv1
  └── 있음 → 해당 파일도 역방향 참조하는가?
                │
                ├── 단방향만 → Lv1 (분리해도 영향 제한적)
                └── 양방향 (밀접) → 함께 분리를 검토하고, 맞지 않으면 §5 [예외]
```

## 4. Lv1 프로세스

```
[1] 레지스트리 Lv1 등록
  │
  ▼
[2] 다음 Master Plan 작성 시 선행 sub-phase로 편성
  │
  ▼
[3] 구현 — 파일 분리
  │   → 클래스/함수 단위, 응집도 기반 분리
  │   → 분리 후 각 파일 500줄 이하 목표
  │
  ▼
[4] 검증 — 기존 테스트 통과 + import 정상
  │
  ▼
[5] 레지스트리 갱신 (상태: 해소)
```

## 5. [예외] 확정 조건

"분리 불가" 선언은 아래 **3요건을 모두 충족**해야 한다:

| # | 요건 | 설명 |
|---|------|------|
| 1 | 영향도 조사 **실시** | 조사 없이 예외 선언 금지 |
| 2 | 분리 시도 또는 아키텍처 검토에서 **순환 의존/응집도 파괴 입증** | 구두 판단 금지, 근거 필수 |
| 3 | 사용자 **승인** | 개발자 단독 판단 금지 |

**영향도 조사**:

```
[1] 대상 파일 기준 import/호출 그래프 전체 매핑
  │   → 500줄 초과 연관 파일 모두 포함
  │   → 2차 연관 (연관 파일의 연관 파일)까지 탐색
  │
  ▼
[2] 산출물: 영향도 리포트
      ├ 파일 목록 + 줄 수
      ├ 의존성 방향 (단방향/양방향)
      └ 변경 시 영향받는 파일 범위
```

예외 확정 시 레지스트리 기재 항목:
- `[예외]` 태그
- 사유 (1~2문장)
- 영향도 리포트 참조
- 승인일

## 6. 초기 개발 시 적용 (REFACTOR-3)

| 시점 | 조치 |
|------|------|
| **PLANNING** | 신규 파일 설계 시 500줄 이하로 모듈 분할 계획 |
| **BUILDING** | 구현 중 신규 파일이 500줄에 가까워지면 분리 검토 (완성 후가 아니라 작성 중에). 기존 파일 확장은 관심선 등록(REFACTOR-1) |
| **VERIFYING (G2)** | 500줄 초과 신규 파일이 있으면 코드 리뷰에서 지적 |

## 7. 해소 이력 추적

리팩토링 완료(해소) 후 이력을 추적하여 재발 감지·원본 추적을 보장한다.

### 7.1 해소 이력 기록 (레지스트리)

리팩토링이 완료되면 레지스트리 `해소 이력` 섹션에 **1행**으로 기록한다:

| 필드 | 내용 | 필수 |
|------|------|:----:|
| 원본 파일 | 리팩토링 전 파일명 + 줄 수 | ✅ |
| 결과 파일 | 분리 후 파일명 + 줄 수 + 관계(독립/참조) | ✅ |
| 수행 Phase | `phase-X-Y` | ✅ |
| 해소일 | 리팩토링 완료 날짜 | ✅ |

**관계 표기**:
- `독립` — 다른 결과 파일과 import 없음, 단독 수정 가능
- `참조:파일명` — 해당 파일을 import, 수정 시 함께 확인 필요

### 7.2 재발 감지

Phase X-Y 완료 시 코드 스캔(REFACTOR-1)에서:

1. 500줄 초과 파일이 해소 이력의 **결과 파일**에 해당하는지 확인
2. 해당 시 → `[재발]` 태그 부여 + 원본 이력 참조 기재
3. `[재발]` 파일은 일반 신규보다 **우선 검토** (구조적으로 커지는 경향 신호)

### 7.3 추적 흐름 요약

```
리팩토링 완료
  │
  ▼
[1] 레지스트리 700줄+ 테이블: 상태 → "해소"
  │
  ▼
[2] 해소 이력 테이블에 1행 추가
  │   (원본, 결과 파일+관계, 수행 Phase, 해소일)
  │
  ▼
이후 Phase X-Y 완료 시 코드 스캔
  │
  ▼
[3] 결과 파일이 다시 500줄 초과?
      ├── YES → [재발] 태그 + 우선 검토
      └── NO  → 정상 모니터링
```
